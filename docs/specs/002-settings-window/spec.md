# 002. A settings window where every change shows on the real overlay

**Status**: done

**Budget**: 490 .NET and 80 page cases

The settings window sets thermi up visually: which sensors each overlay shows, their thresholds over the values they guard, where the overlays sit and how they look. Nobody has to know sensor ids or edit JSON. It follows four rules. **The overlay is the preview**: every change shows on the real overlay at once, and there is no Save button, since undo replaces confirmation. **Real data everywhere**: every choice shows its live value. **Nothing can break it**: the window writes only valid settings, and hand edits keep working. **Free when closed**: the window is a process of its own, and the overlay pays nothing for it.

With the window come what it edits: up to four overlays, looks, gestures on the desktop, tray icons and menus, and new sensors (network, disk, battery and three of Windows' own).

## Requirements

### Opening the window

- R1. "Settings…" in the overlay's menu and in thermi's tray menu opens the window. In the overlay's menu it is the default entry, in bold, the one a double-click runs. The file itself opens from the window's "Open in editor" (R152).
- R2. A double-click on an overlay opens the window with the item under the pointer selected, or the overlay when the pointer is on no value.
- R3. `thermi settings` opens the window.
  Release check: Open the window every way.
- R4. Only one window exists: asking again brings it to the front.
- R151. Starting thermi while it runs opens the window, or brings it to the front, and starts no second overlay.
- R5. The first frame shows within 1 s of the request when the window was opened before in this sign-in, and within 2 s the first time.
  Release check: The window's speed.
- R6. Without the overlay running, the window still works, and offers to start it.
- R155. Closing the window leaves no process of it behind, WebView2's included.
  Release check: The window's speed.

### Live editing and undo

- R7. A change shows on the real overlay within 300 ms of the input, also while a slider moves. There is no Save button.
  Release check: The window's speed.
- R8. Ctrl+Z and Ctrl+Y, and the Undo and Redo buttons of the title row, undo and redo the window's changes since it opened, also while a slider has the focus. One gesture is one step: a drag from press to release, typing until the field loses focus, and repeated changes of one control within 1 s. The page has the keyboard's focus as the window opens and each time it is activated, so Ctrl+Z works without a click in it first.
- R9. Undo never reverts a change made outside the window's history, a hand edit of the file or a drag while the window was closed, even of the same item: a step whose target no longer holds what the window left there is skipped, and the window says so.
- R206. Each slider, Size, Background opacity and the gap between pills, shows its value beside it in a box that takes a typed number, as "137" or "137 %", and each text size's box lists its sizes and takes one typed too, as "23", as a word processor's does: Enter or the focus leaving keeps it, and Esc puts the value back. Any number in the field's range is kept, not only its steps or the sizes listed, rounded as its field is kept, to a whole percent, a whole pixel or, for a text size, a half; one outside the range is held at its nearest end, and text that is no number leaves the value as it was, and Narrator says either. C# reads what was typed, in Windows' number format, and decides all of it.
- R106. The Undo and Redo buttons name their step in their tooltip, as "Undo Critical 84 → 85 °C", and stay in the Tab order, marked unavailable, when there is nothing to undo or redo. After an undo or a redo, a toast says what changed back, as "Undone: Critical back to 84 °C.", "Undone: Theme back to Dark." or "Undone: Separate pill is Off again.", or, for a step that is an action, its name alone, as "Undone: Hide this overlay."; after a redo it says "Redone: …", as "Redone: Critical back to 85 °C."; and the window shows the overlay or the item it changed.
- R108. Passing news, as an undo, a removal or an import, shows for 6 s as a toast floating at the pane's foot, so nothing moves when it comes, and the control that has the focus is scrolled clear of it, so it never covers what was just edited, and while it shows the pane's view ends above its band, so no control shows half under it; it waits while the pointer or the focus is on it. Bars show only for problems that last, each with its fix.

### The window's layout

- R97. The window is a list beside a pane. The list holds each overlay as a row, each of its pills as a row under it, named as "CPU pill, 4 items", and each item under its pill; "Settings" is a row of its own below the list. The pane shows what is selected: an item's page, an overlay's page with its Appearance and Placement, or Settings.
- R116. The first time, the window opens at 90 % of the work area, up to 1500 × 900, centered on the first overlay's monitor; where 90 % of the width is under 860 px and the whole is not, it takes the whole width. Later it opens at the size and place it had, remembered for each setup of monitors. The window moves, resizes from any edge or corner down to 760 × 560 (or the work area, when smaller), maximizes, and snaps to halves like any window; its system menu (Alt+Space) and Win+arrows work. Its first place and the remembered one stay off thermi's overlays that are not on a taskbar, shortening on their side while it keeps its minimum.
- R118. While the window is the active window, it sits above thermi's overlays, except the one being edited, which stays above it unless it would cover the window's caption buttons.
  Release check: Narrator, themes and the window's frame.
- R119. From a window of 1500 px, the list is 344 px wide; from 860 px to 1499 px, it is 32 % of the window, at least 240 px and at most 296 px. Under 860 px, the list folds into a button in the title row and opens over the pane, 320 px wide or 85 % of the window when that is less, and the pane then takes no input; choosing a row, or Esc, closes it. One column of the pane is at most 720 px wide. From 864 px of pane, the pane shows two columns of at least 420 px that share its whole width, the chart taking three fifths of a pane from 1400 px, the item's chart staying in view beside its rows as they scroll: Appearance beside Placement, with "Text and colors" under Placement, the chart beside the item's rows, and General beside About. In a card under 520 px wide, a row's controls wrap among themselves at its end; under 420 px, a control goes under its name, except a switch or a row that is clicked as a whole, which keep their control on the right. In a window under 640 px tall, bars keep their title and action, without the rest of their sentence.

### The list

- R11. Items move with a drag of their row, or with Alt+Up and Alt+Down on the focused row, within their overlay, and pills move whole the same ways among their overlay's pills, Alt+Up and Alt+Down stopping at either end. A row dropped on another overlay's moves there, before the item or pill it lands on, or past the overlay's last on its heading; "Move to" in the row's menu does it by keys (R101). Delete on a row removes the item, from the list only; "Add item" and Ctrl+N add one. A move is one undo step, shows on the overlay at once (R7), and is announced, as "CPU power moved, 2 of 4, in its own CPU pill" or "GPU pill moved, 1 of 3".
- R99. While the window is open, a click on a value of a real overlay selects that item, and a click on an overlay's edge selects that overlay. Pointing at a row marks its value on the overlay, and pointing at a value marks its row.
- R100. The list is one Tab stop. Up and Down move and select; Home and End go to the first and last row; Left folds a row or goes to its parent; Right unfolds it or goes to its first child; Enter goes into the pane; letters typed in a row go to the next row whose name starts with them; F2 renames; Shift+F10 or the Menu key opens the row's menu. The arrows never leave the list, and Settings is a Tab stop of its own.
- R101. An item's row menu holds Rename, Edit pill label, Separate pill (as R54 says), Tray icon, "Move to" each other overlay, "Move to a new overlay" while there are fewer than 4, and Remove. A pill's row menu holds Edit pill label, "Move to" each other overlay, and Collapse or Expand. The title row's "…" menu holds "New overlay", off once there are 4, "Keyboard shortcuts" (F1), and "Exit thermi".
- R102. Items and overlays have names, renamed with F2, a double-click on the name, the row's menu, or a click on the pane's title; Enter keeps the name and Esc goes back. A new item is named like the defaults, as "GPU temperature": a temperature, power, clock or fan by its device and kind, a load so only on a CPU or GPU, anything else by its readable name with its device before it, as "SSD free space" or "Virtual memory used"; with its sensor's own name in brackets when that name is taken, or a number when an item already shows that name, and a number when the same sensor is added again. A name thermi gives, told apart or numbered too, is kept out of the file, as the defaults' are, so the item reads in the window's language, a GPU fan's in Spanish too, and is told apart and numbered in it, after the items before it; only a name the user typed, or gave its sensor, is kept. Spanish names a device as its metrics do: "Ventilador de la GPU", as "Carga de la GPU". What tells it apart, its sensor's name or its device's, goes in brackets without brackets of its own or a maker's marks, as "CPU temperature (CCD2)" or "GPU load (AMD Radeon Graphics)"; a second GPU's item is told apart by its device alone, numbered only when that name is taken too. An overlay without a name typed by the user reads by where it sits, as "Taskbar", "Top right" or "Floating", in the window's language, with a number when two would read the same; moving it renames it, and the file keeps no name for it. A typed name stays wherever the overlay goes.
- R103. An item's row is named by the item's name alone; its value and its level are its description, so the live refresh does not read the row again. They are the overlay's at the same moment: the overlay paints each snapshot as it comes, as the window shows it, never a second behind. An overlay's row says its name, whether it is hidden, its place when its name does not say it, and how many items it has.
- R104. While the window is open and shows, not minimized, the overlay being edited marks the selected value with a 16 × 3 px rounded bar in the accent color lying centered under it, as a tab's mark, which steps down while the value shows its level. The other overlays fade only their frame to 30 %, so their values and levels read as before; one whose theme is the opposite of the taskbar's fades whole to 50 %.
- R105. Ctrl+F goes to the list to type a name, Ctrl+N adds an item, Ctrl+, opens Settings, and F1 or ? shows a sheet of every shortcut in a dialog that fits in the window.

### Keyboard, focus and screen readers

- R47. Every action of the window, of thermi's menu and of the overlays' menus can be done with the keyboard alone, and so can every desktop gesture's result, through the list: Alt+arrows move a floating overlay, "Move to a new overlay" takes an item off, "Merge into" joins overlays, and the Size slider resizes.
- R48. Narrator reads a name and a role for every control of the window, and its value where it has one: a level in words ("CPU temperature 96 °C, critical"), a color button its color, a shortcut its keys.
- R123. After any action, the focus is on a control, never on the page: a control that goes away hands it to the one the action names, else to what opened it, else to the list's current row. The live refresh changes values in place, so a focused control keeps its focus, and whatever gets the focus comes into view.
- R124. Dialogs take the focus, keep Tab inside, run their main button with Enter and cancel with Esc, giving the focus back to what opened them; a dialog that destroys shows its action then Cancel, as [Reset] [Cancel], with Cancel on the right as its focused accent button. Menus put the focus on the current choice, take the arrows and typed letters, close with Esc giving the focus back, and close with Tab, moving on.

### The window's theme

- R49. The window follows Windows' light or dark mode, unless Settings chose its own (R193), its accent color and high contrast; under high contrast every part of it, the chart and the level marks included, takes the system's colors.
- R193. Settings' General has "Theme", a segmented choice of "Windows" (the default), "Light" and "Dark", for the window alone: the overlays, their tooltips and thermi's menus keep their own, and so do the window's samples of a look, whose "Match taskbar" pills take the taskbar's mode as the overlay's do. It applies at once, without reopening, to the whole window: the page, its title row and caption buttons, Mica behind them, and Edge's own scrollbars and controls, and the window's first frame is already in it, never a white flash before a dark page. "Windows" keeps following Windows' mode as it changes. High contrast wins over any choice. Undo takes it back, and Reset keeps it.
- R50. With animation effects off in Windows, nothing animates.

### The catalog and the search

- R13. "Add item" opens the catalog, which lists every sensor the service reads, one row each, grouped by device, with its live value, and says how many it lists. With several overlays, it names the overlay the item goes to, and another can be picked there.
- R14. Typing filters the catalog by words in any order, each matching where a word starts in a sensor's name, its second line, its device, its type, or a common synonym, as "temp", "graphics", "ssd" or "rpm"; a word that names one item, as "uptime", finds that item, not every item of its device; chips filter it by type, and in a panel too short for them, as at 200 % text in a small window, a Types dropdown does. With no match, it says so and suggests one word close to what was typed that finds something, or none. Esc first clears the search, then closes the catalog. Enter in the search adds the first match, Down moves into the rows, and Ctrl+Enter on a row adds it and keeps the catalog open; as the search changes, the count is announced, as "12 sensors. Down arrow to browse, Enter adds the first." or "No sensor matches. Try one word, like gpu."
- R15. Each sensor shows a sparkline of its values since the window opened, up to the last minute, drawn over at least its type's least span (10 °C, 20 %, 20 W, 300 RPM, 500 MHz), so a small change looks small, in the green of a normal level (R24), as a sensor has no lines.
- R16. A sensor without a usable value says why in its row: "Needs the driver" for a CPU temperature, power or clock of exactly zero, "Stopped or not connected" for a fan at 0 RPM, and "Reads nothing" for any other. A GPU's fan at 0 RPM is no fault: a GPU stops its fans while it is cool, so its row shows its 0 RPM as any value, with the quiet note "Stops while the GPU is cool", or, when an item shows it already, the items that do. The overlay uses the same rule, so only those CPU sensors treat zero as missing.
- R17. Any sensor can be added as an item, shown in the unit of its type. It joins the pill of its device's kind (CPU, GPU, RAM, BOARD or SSD) after that pill's last item, or goes at the end when the overlay has none. With two GPUs, as a CPU's graphics chip beside a graphics card, the GPU pill reads the card, and a sensor of the chip is named after it and joins an "iGPU" pill of its own, so the card's sensors added after it still join the GPU pill; it is selected, brought into view and announced. When thresholds judge its type, it is warned by its own reading, with its type's thresholds (R27), as a GPU temperature's 80 and 88 °C, and draws what its overlay's Graph says (R90).
- R18. An item's sensor is changed in its Sensor dropdown, which lists Auto first, for an item made from a metric, then every sensor of the item's type on the device it reads now with its live value, and a last choice, "Show all", that lists the other devices' sensors of that type too (of an amount of data, only its own kind of device's), with a filter when there are more than 6. It leaves out what the catalog hides whatever was seen, as a GPU's D3D loads, and a second sensor of a device with the type and name of one before it, but keeps the item's own. Each sensor reads by the name the catalog gives it (R178), as "CPU fan", with its device after it in a quieter color; a name the device gives sensors of other types too says its type after it, as "GPU Core (load)". When a fan item warned by a fan's duty changes its fan, by hand or by the finder, it is warned by the new fan's own duty, which shows as missing if that fan has no duty sensor.
- R192. Every search of the window, the catalog's and the Sensor dropdown's filter, is one search, which C# decides: words in any order, without accents or case, each where a word starts, and once nothing matches as typed, a word of five letters or more with one letter wrong, added, dropped or two swapped. The best come first: a name that starts with what was typed, then one that holds every word, then some, then a sensor found only by its second line, its device, its type, a synonym or the metric it feeds, as "cpu temperature" finds the CPU's "Core (Tctl/Tdie)", then a typo forgiven; the catalog keeps its groups, each where its best sensor is. Each result marks what matched, in its name, its second line or its device, on a faint accent that keeps the text's own color, and a sensor found by the metric it feeds names it in its second line. The Sensor dropdown's filter says in a status line how many match, a row says when none does, and Enter takes the first.
- R178. A sensor that a board's Super I/O chip names only by its input, as "Temperature #3" or "Fan #2", shows in the catalog under a probable name where the chip's usual wiring says it: on Gigabyte's ITE chips (IT8686E, IT8688E, IT8689E and IT8696E), temperatures 1 to 5 are likely System, Chipset, CPU, PCIe slot and VRM, and fans 1 to 3, with their duties, likely the CPU fan and system fans 1 and 2, a duty named as one, as "CPU fan duty". A probable name never claims to be sure: its second line says "Likely" with the chip's own name for it, as "Likely · Temperature #3", and its tooltip says why. Any other such sensor keeps the library's name, and its second line names the chip and the input, as "ITE IT8689E · input 6". The search finds a sensor by its probable name too.
- R179. The catalog hides what nobody would add: a sensor that reads nothing (a CPU sensor that needs the driver still shows, since R16 says how to fix it), a fan at 0 RPM that has not turned since the window opened (never a GPU's, which R16 says is at rest), a network adapter that has moved no data since then, as Windows' virtual "Local Area Connection*" ones, a temperature that has read only 0 °C since then, a GPU's D3D engine loads, which Windows' counters repeat beside the GPU's own, and each CPU core's effective clock, which the cores' average says once. A drive's fixed limits ("Warning Temperature", "Critical Temperature") and wear counters (life, spare), and a memory module's limits, resolution and capacity, are not sensors at all and never show; nor does an Intel core's "Distance to TjMax", how far it is under its limit, which the library reports as a temperature but falls as the core heats, so a meter or a line would read it backwards: no metric picks it either, and the default lines of an Intel CPU's temperature read it only to find the limit (R27); the CPU's bus speed and every effective clock are hidden, and the type that reads MHz is named Frequency, so it does not read as the Clock item. The count says how many the search and the chips hide, as "139 sensors · 34 hidden", and a "Show all" chip beside it shows them too, until the catalog closes.
- R180. A sensor can be renamed from its catalog row, with F2 or the row's pencil: Enter or leaving the box keeps a name of up to 40 characters, Esc goes back, and an empty name gives back the library's. The name goes into the settings by the sensor's id, as one step that Ctrl+Z undoes, and shows wherever the window names that sensor: the catalog, whose search finds it by that name, the Sensor and Warn by dropdowns and the fan finder. Every item that shows that sensor alone under the name thermi gave it takes the new name, so the list and the overlay's tooltip say it; an item renamed by hand keeps its own, and a new item of that sensor is named by it. A reset keeps the sensors' names, as it keeps the language.

### Finding the CPU fan

- R19. "Find it", on the Sensor row of the CPU fan item, first asks: "This loads the CPU for up to 30 s, so your fans speed up and may be loud.", with "Load the CPU" and Cancel. Once asked to, it says that the fans will speed up for up to 30 s, then first waits, saying so, for 3 s of fresh readings in which no fan fell by 100 RPM or more, as one does for a while after a run, nor rose as much as R21 asks of an answer, at most 30 s, then loads every logical core at idle priority, in a process of its own, for at least 8 s and at most 30 s, while the sensor service and the overlay run above normal priority, so the readings keep coming under the load. Once past 8 s, it stops when one fan has met the rule of R21 for 3 s in a row. After the load it watches the fans for up to 40 s more, saying so, and a fan that meets the rule for 3 s in a row then is picked too: a fan-control curve may answer a load only once it has ended, and a fan already up from an earlier load may hold its speed through this one and fall only once it ends, so once the load has ended a fall counts as a rise does. A pause of a few seconds in the readings only leaves it fewer to average; readings gone for longer than 8 s end the load, and when they stay gone for 8 s more, or no fan answers once they are back, it says the readings stopped.
- R20. It can be cancelled at any time, and the load stops within a second.
  Release check: The fan finder's load.
- R21. It picks the fan whose speed, averaged over its last 3 s, rose by at least 100 RPM and 20 % over its average in the 3 s before the load, or, once the load has ended, fell by as much, and by at least twice as many RPM as any other fan answered at any time since the load started, so two fans that rose alike stay alike however they fall once it ends. It then says which fan, and how much it rose when it rose, and "Use it" makes the CPU fan item show that fan, as one undo step, keeping what it warns by; when the item already shows it, it says so instead.
  Hardware report: A board whose CPU fan follows the load.
- R22. Otherwise it picks nothing and says why: no fan rose, two rose alike, or the CPU load, averaged after its first 2 s, stayed under 80 %. When no fan rose and the load raised neither the CPU's temperature by 5 °C nor its power by 20 %, each averaged through the load against the 3 s before it, something else already held the CPU busy and hot: it says so, and to close what loads the PC and try again. Otherwise, when no fan rose, it adds that the fans may follow a curve set by fan-control software, and that the fan can be picked by hand in the Sensor dropdown. With no fan sensor outside the GPUs, it cannot start. It says the driver may be missing when the CPU temperature also reads zero, and that the board reports no fans otherwise.

### An item's page

- R109. An item's page shows the item's name as its title, where it lives under it ("Taskbar · CPU pill"), its chart with its "…", and then the Sensor, Label, Graph (where its thresholds judge something, R90), "Notify me when critical", Separate pill and Tray icon rows, and "More options" with what it shows (now, minimum, maximum or average), smoothing, decimals, Warn by (R28), only on alert, the offset, the value color and "Combine…". An item without a numeric reading, as Clock or Local IP, offers none of what it shows, smoothing, decimals, the graph, the offset or Combine. Every choice a dropdown offers can be chosen, its default included, and the page stays where it was scrolled through an edit, an undo or a redo, new readings, a switch, a dropdown opened or picked from, by keys or pointer.
- R195. What an item's value is, "Shows" and "Smoothing", sits in its page's rows under Sensor, never in "More options". An item that shows its minimum, maximum or average, or smooths its value, says so with a short tag, as "avg", "max" or "5s avg", translated, small and quieter right after its value, on the overlay and in the window's list alike, as "81 °C max", whatever its label and wherever it sits in its pill; labels never carry it, so a pill of several items says which of them is a maximum.
- R194. Wherever the window shows an item's value, as its row in the list or a look's sample, it is the text the overlay draws for that item, with its units: its minimum, maximum, average or smoothing (R88, R89), offset, decimals, unit and bits, from the same history, which the overlay sends the window as it opens and after each reset. A sensor's own reading shows only where the window names a sensor, as the catalog and the Sensor dropdown do, never beside an item's name. While an item has no label of its own, its Label box offers the label the overlay draws for its run.
- R28. What an item's thresholds judge is its own reading, unless "Warn by", under More options, picks another reading of the item itself, never another device's or another kind's: for a fan its own duty, for a duty its own fan, where the service reads it, and for the RAM in use the RAM's load, which it starts warned by. Thresholds judge a temperature, load, duty, fan speed or speed; Warn by's first choice is "Its own reading", or "Off" for an item of another type, as the RAM in use, and the row shows only when it offers more than that one. The other choices are named by what they read, as "Speed (RPM)", "Duty" or "Load", never "This value". A reading chosen brings its default thresholds. An item whose thresholds judge nothing, as power or clock, has no thresholds, no Graph row (R90), no "only on alert", charts only its own reading (R110), and never shows a level.
- R83. An item's value can take a color of its own, in its "More options", over the look's value color, with the 3:1 rule of R62, and can go back to the look's.
- R87. An item can combine several sensors of one type, as their highest or average, or their sum for any type but temperature, picked with "Combine…" in its "More options", which starts with the sensors the item reads now checked, names each sensor with its device, and whose button, "Use these", makes the item read them in place of its own; its Sensor box then says how it combines which sensors, as "Highest of CCD1 (Tdie), CCD2 (Tdie)", and their devices under it. It can also add a fixed offset in its unit, from −20 to +20 for a temperature, a load or a duty, −2000 to +2000 for a fan, −500 to +500 for power, −10,000 to +10,000 for a clock, and −100 to +100 for memory. For a temperature, the offset is a difference: it is kept in °C and shown in °F as 9/5 of it, without the 32. A sensor without a value is left out; with none left, the item shows as missing.
- R88. An item shows its value now (the default), or its minimum, maximum or average since the overlay started or was last reset; missing values are left out. "Reset min and max", in the overlay's menu, thermi's menu and on its hotkey, starts them again.
- R89. An item can smooth its value as the average of its last 2 to 10 s, off by default; missing values are left out, and with none in the span the item shows as missing.
- R91. An item can show 0, 1 or 2 decimals instead of its type's own, and the room it keeps (its widest value) follows.
- R92. An item shows always (the default), or only on alert, while what it warns by is at warning or critical, whatever its Graph draws; an item whose thresholds judge nothing cannot be set so, and where Warn by could change that, the window says why. A pill with nothing to show disappears, and the overlay closes the gap from its snapped edge. While the window is open, every item shows, so each can be selected.
- R114. "Notify me when critical", offered on an item with a critical line and off by default, shows one Windows notice once the item has been critical for 10 s, "CPU temperature is critical. 98 °C for 10 seconds. thermi tells you once until it cools down.", and no other until the item leaves critical. While a full-screen app is in front, that notice waits; once it leaves, one notice says "While you played, CPU temperature reached 98 °C (critical) for 1 min.", with the peak and how long it lasted.

### The chart and its lines

- R24. The item's chart is its page's hero: the last ten minutes of what it warns by as a smooth line over a soft fill, with no frame or grid, and "Min · Avg · Max" of those minutes under its axis, its "Chart options" at their end. It spans from its first reading of those minutes to now, so a window just opened fills the chart with the seconds it has, and its axis says how long ago it starts, as "2 min ago" or "40 s ago"; a lone reading between gaps draws no line. The line and its fill speak the level by color, as the overlay's meters do (R61): green below the warning, and for a chart without lines, the warning color from the warning, and the critical color from the critical, each part of the line by its own height, so the ten minutes show where it crossed; the fill fades from the line down. Those three colors are `#6CCB5F`, `#FEC84B` and `#F05A50` in dark mode, and `#0F7B0F`, `#9D5D00` and `#C42B1C` in light mode, each at least 3:1 against the window. The band from the warning to the critical is tinted with the warning color at 7 %, and the band above the critical with the critical color. Each threshold is a line with a knob that holds its value. The chart's top and bottom say the ends of its range, small and quiet. A text summary gives screen readers the range, the value now and the lines. When the lowest line was reached for more than half of the ten minutes and the lines are not the meter's defaults, the chart says "Fires most of the time", quietly, with a button that brings the default lines back and says what they are, as "Use 90/95 °C", or "Remove the lines" when the meter has none.
- R25. The chart holds the last ten minutes from the window's first frame, also when the window has just opened. It only ever draws seconds of the reading it draws now: once what the item warns by or reads changes, by an edit, an undo or a redo, the seconds of the reading before are dropped, on the chart and in the item's minimum, maximum and average, and the chart starts again from what the window read of the new reading since it opened, an automatic pick's being the seconds of the sensor it picks now, never of one an item named meanwhile. Gaps (the service stopped, or its data went stale) stay empty, never filled with the last value. Without readings, the chart's place says why, and its lines and knobs stay: "Sensors stopped: the chart comes back when they start." while the service is stopped, "Needs thermi's driver: the chart starts once it is installed." for a CPU sensor that needs it, and "No readings to draw yet. The thresholds apply as soon as this sensor reads." otherwise.
- R26. The warning is always below the critical: moving one past the other pushes the other 5 beyond it, 100 RPM for a fan, and the window says which moved, as "Warning moved to 80 °C to stay below Critical." or "Critical moved to 90 °C to stay above Warning."
- R27. Thresholds start calm: a CPU temperature warns 10 °C under the CPU's limit and is critical 5 °C under it (90 and 95 °C on AMD, TjMax − 10 and − 5 on Intel); a GPU temperature warns at 80 and is critical at 88 °C; any other temperature at 70 and 80 °C; a fan's duty warns at 85 %; loads, power, clocks, memory and fan speeds have none. "Reset thresholds", in the chart's "…", brings them back.
- R110. The chart takes 40 % of the pane's height, at most half its width, between 140 and 640 px; beside the rows, in a pane of two columns, it fills the pane's height but for its heading and foot, at most as high as it is wide. An item whose thresholds judge nothing charts its own reading, without lines, from 0 to its highest plus 15 % on a 1-2-5 step; a time, an address or a duration charts nothing. A percentage's chart runs from 0 to 100 %. A temperature's runs from the lowest of its readings and lines less 6, rounded down to tens and never under 0, to the highest plus 3, rounded up to fives and never over 100 °C. A fan's runs in RPM from 0 to the highest of its readings and lines, at least 500, plus 15 %, rounded up to 500. Thresholds are set in the unit of what the item warns by: a fan item warned by its own speed charts and warns in RPM, in steps of 50 from 0 to 10,000; warned by a duty, in % of full speed, with the chart titled "Fan duty, % of full speed". RAM used keeps its value in GB, is warned by RAM load, and charts in % under a title that says so. The CPU fan item starts warned by its own speed, with no lines.
- R111. A line moves by a drag of the line or its knob, as one undo step; a click on a knob opens a box to type its value, and a click in the plot moves the nearest line there. On a knob, the arrows move it one step, ten with Page Up and Page Down and five times as far with Shift, Home and End go to the ends, a digit, Enter or F2 open its box, and Delete turns the line off and leaves the focus on "Add warning line" or "Add critical line". The box keeps a value with Enter, Tab or by leaving it, and Esc puts the knob back. A value out of range says "Between 0 and 100 °C", in the meter's unit, and text that is not a number says "Type a number, like 90, or leave it empty for Off"; neither is written. While a line is dragged, the chart keeps the range it had when pressed, so the knob stays under the pointer, and the line stops at that range's ends; once let go, the range takes the line in again. A line added to a fan's or a throughput's chart, whose track ends far past any reading, comes above the highest reading of its ten minutes, the warning 15 % over it and the critical 30 %, on the knobs' step; dragging selects no text.
- R200. A point of the chart says what it read then. The pointer over the plot shows a thin line across it at that second, a dot on the chart's line at its value, and a small label with that second's reading as the item's value says it, in Windows' regional format, the chart's unit and, for a chart of the item's own reading, the item's decimals, and how long ago it came, to the second, as "1,412 RPM · 3 min 20 s ago", "3 min ago" on a whole minute and "now" at the end, or "No reading" for a second in a gap; the axis's start says the first reading's age rounded to minutes. The chart takes the focus by Tab, as a slider whose value is its point: Left and Right move the point a second, Home and End to the chart's ends, and Esc hides it, as leaving the plot or the chart does; a screen reader hears the label after each of those keys, never on a pointer's move. The line and the label take the theme's colors in light and dark, add no control and nothing that looks clickable, stay inside the plot, never over Min · Avg · Max, and leave the lines, their knobs and a click in the plot as R111 says.
- R141. Loads, duties and every other percentage stay between 0 and 100: readings, minimums, maximums, averages, charts and thresholds.

### Pills

- R54. A pill is a run of items with the same label. "Separate pill", on an item's page and in its row's menu, puts the item and the items after it with the same label in a pill of their own, which shows its label. The first item of a pill starts one already, so neither its page nor its row's menu offers it there, unless the item was itself set to start its own. The window's list groups the items under the pills the overlay labels, in every layout of R55, a single bar under each run of one label. Merging overlays, or moving a pill into another overlay or out of its own, never joins two pills that showed apart: an item that started a pill and lands after one of its label starts its own.
- R55. A layout setting shows the pills of R54 (the default), one pill per value, each with its label, or all the items in one bar, with a label where each run of the same label starts. In one bar, as CleanMeter draws it, each run is a pill of its own inside the bar, 4 px inside its edge and 4 px from the next at 100 %, its corners the bar's less those 4 px, in a color that stands at least 1.5:1 from the bar's and no more than 2:1, lighter on dark pills and darker on light ones; under high contrast it takes the bar's color with a border. The last two ignore which items start a pill, and keep it for when the layout comes back.
- R29. A pill's label can be changed, and the change applies to every item in that pill and to no other.
- R56. The overlay can be horizontal (the default) or vertical, where the pills stack from top to bottom, all as wide as the widest; in one bar, the bar stands, its pills stacked inside it the same way, 4 px apart. No choice is offered that does nothing: with one pill, or one bar of one run, there is nothing to stack, so the menus leave "Vertical" out and the window grays Direction and says why, unless the overlay is vertical already, so it can be turned off. While vertical, the taskbar place of R30 is not offered, and an overlay on the taskbar shows just above the work area's bottom at its offset, or in its bottom right corner without one, which the window calls "Above the taskbar (vertical doesn't fit in it)".

### Looks

- R57. The Look is Default or one of the user's saved looks, the tile checked being the look the overlay draws as, none once it was changed in any way, and Default worn as one step, each a tile with a sample of three pills in that look, CPU temperature and load, GPU load and RAM used with their values now, painted as the overlay paints them (R197). Default is Standard text (13 px semibold labels and 13.5 px bold values at 100 %) on pills that match the taskbar, with green meters at normal. The text sizes and weights sit under "Text and shape"; changing one makes the look the overlay's own, keeping the rest.
- R197. Appearance starts with a preview of the overlay: its pills, labels, graphs and values now, painted by the overlay's own painter as "Copy as image" paints it (R188), at its size and its monitor's scale, one pixel of the picture on each of the screen's, so it is as sharp as the overlay; in a column narrower than the overlay it is painted smaller to the column, never shrunk as a picture. It shows each change to the overlay as it is made, and its values once a second; on the taskbar it sits on the taskbar's color, and anywhere else on nothing but the page.
- R58. Labels and values each have a text size, from 9 to 36 px at 100 % in steps of 0.5, and a weight: regular, semibold or bold. A pill is 38 px high at 100 %, and for text over 20 px 1.9 times its larger text, so no text leaves its pill.
- R59. The pills' background has an opacity from 0 % to 100 %, 100 % by default; below 30 %, the text gets a shadow so it stays readable on any wallpaper, unless the look's text effect (R93) says otherwise, and Light, Dark or own-colored pills follow the taskbar's mode as System's do, since what shows behind their text is then what is behind the overlay.
- R60. The pills' theme is Dark, Light, or Match taskbar, the default, which follows the mode of the taskbar the overlay sits on within a second of it changing. Choosing a theme, in the window or by an agent, gives the pills back its own color (R203). With several overlays, "Use on all overlays" chooses this theme on every overlay, as choosing it on each would, and changes nothing else.
- R61. Meters speak the level by color, as CleanMeter's do: green at normal, Windows' success green `#6CCB5F`, and the warning and critical colors at those levels; the values' text stays in its own color at normal, so only the meters turn green. Each of the three colors can be changed, the normal one's default choice named "Green", and "Reset colors" brings them back; a color chosen is the overlay's, while the window's chart keeps the window's own (R24), which hold 3:1 against it. On light pills, the default colors are drawn in their darker forms, `#0F7B0F`, `#9D5D00` and `#C42B1C`. Each default keeps 3:1 against its pill and the meters' unlit track, which stays faint.
- R62. Labels and values each have a text color, Auto by default: light colors on dark pills, and dark ones on light pills. A color with a contrast under 3:1 against its pill, taken as opaque, is drawn in its Auto color instead, and the window says so, so text never disappears when the pills change.
- R203. The pills can take a color of their own, under Colors with the same swatch as the others, Auto by default, which is the theme's. A chosen color fills the pills; their border, the meters' unlit track and a single bar's inner pills (R55) are drawn from it, and the background opacity still applies. Auto text then takes light or dark text, whichever reads on it: values and labels at least 4.5:1 against it, a label taking the values' color where its own would not, and the default level colors keep 3:1 against it and the unlit track, drawn toward the text color until they do. A chosen text color is held to R62's 3:1 against it. A look carries it, a look file and an agent's edit set it, Ctrl+Z takes it back, and high contrast replaces it as every color (R96).
- R82. "Show labels" and "Show units", under "Text and shape", can hide an overlay's labels or its units. Without labels, each pill keeps its items and shows their values alone; the labels are the overlay's, as its layout is, so no look carries them. Without units, values show without them, and labels stay as they are. The tooltip of thermi's icon follows the overlay; an item icon's tooltip keeps its unit.
- R93. "Text and shape" also chooses the font (Segoe UI Variable, the default; Bahnschrift; Consolas), the corners (round, the default, a radius of half the pill's height; soft, a quarter; square), the gap between pills (0 to 16 px, 8 by default), and the text effect: Auto (the shadow of R59), shadow, outline (1 px at 100 %, in the pill's color) or none.
- R96. A "Colorblind-safe" switch, under Colors, sets the meter colors to Okabe-Ito blue `#0072B2`, orange `#E69F00` and vermilion `#D55E00`, written as R61's three colors, and turning it off brings back the defaults. Under Windows' high contrast, the overlay draws its pills in the system's window color, and their text and borders in its window-text color; the level marks of R138 take the same two colors.

### Saved looks

- R63. A look is the theme, the background opacity, the colors, and the text and shape: sizes, weights, font, corners, gap, text effect and units. It holds no position, size, layout or direction. It remembers the name of the saved look it came from until anything else changes it.
- R64. "Save as my look…" saves the current look under a name of 1 to 40 characters, unique whatever the case, and says what a look keeps: "Saves colors, theme, opacity, text and shape. Not position or layout." Saved looks sit beside Default; each one's "…" renames, exports or deletes it, and with several overlays uses it on all of them; renaming the one worn renames it in the settings too. Saving, renaming and deleting change the saved looks, not the overlay, so Ctrl+Z does not touch them; choosing a look is one step that Ctrl+Z undoes.
- R65. A look exports to a `.thermi-style` file that holds the look and its name, and no sensors, items, placement, language or paths, so it works on any PC.
- R66. A look file chosen with "Import…", dropped on the window, or its text pasted with Ctrl+V when no text field has the focus, applies to the overlay at once, as one step that Ctrl+Z undoes. A toast then says "Applied “Ocean” (not saved)" with "Save as my look" and Undo; saving asks for another name when that one is taken.
- R67. A look file that is broken, from a newer thermi, or with a value out of its range is refused whole with the reason, naming the field, and nothing changes. Unknown fields change nothing and are kept as they came, and missing ones take their defaults.

### On the overlay

- R90. One control, Graph, decides what an item draws on the overlay before its value, 6 px from it, as CleanMeter's does: None, Bars or Line. It never changes what the item warns by, its thresholds or its alerts (R28, R92). The overlay page sets it for the whole overlay: Auto (the default), None, Bars or Line, where Auto draws a line for a load warned by its own reading, as the default CPU and GPU loads and any load added from the catalog, and bars for the rest. Each item's page overrides it: "Like the overlay" (the default), None, Bars or Line. An item whose thresholds judge nothing (R28) draws nothing, and its page offers no Graph. Bars are five segments stacked a pixel apart, 12 px wide at 100 % and together as tall as the value, scaled with the monitor and the overlay's size, lit from the bottom as far as what the item warns by rounds to, a half up, at least one for any value above zero and none at zero or while it reads nothing; the lit ones take R61's color for its level, and the rest a faint track. A line is its last minute, 24 px wide and as tall, a fan's speed or a throughput on the range the window's chart gives the same readings and lines (R110): a line over a light fill, each second in its level's color, on the same track, with gaps where values were missing; the seconds of one level are one unbroken shape, so a second narrower than a pixel still shows whole. A critical level shows on the value too (R138).
- R138. A pill is one flat shape in its theme. A value warned by its own reading is judged as it shows, rounded as the overlay rounds it, so one that reads as its line is at it. At normal a value shows nothing more; at warning a 2 px underline in the warning color runs under it, unless the item draws bars or a line (R90), which show the warning in that color already, so only an item whose Graph is None underlines it; at critical it is drawn reversed, black on the critical color on dark pills and white on light ones. The first time an item goes critical, its pill glows once, for 600 ms, never with animation effects off. In the window, as on the overlay, a level never rests on color alone: nothing at normal, a 2 px underline in the warning color under the value at warning, and the value reversed on the critical color at critical.
- R139. Pointing at a value shows a tooltip with the item's name, value and level (RAM used with its total, as "27.2 of 61.6 GB"), its minimum and maximum since thermi started, and "Double-click to edit". A missing value says why and what to do: "CPU temperature needs thermi's driver. Double-click to fix.", "Sensors stopped. Double-click to see why.", or "CPU fan reads nothing. Double-click to change its sensor." The CPU fan's, picked by its input's name (the board chip's CPU fan input: its first, or its second on Nuvoton's NCT67xx chips, whose first is a system fan's), says it is likely the CPU fan and that "Find it" in its settings checks. The tooltips are rounded and padded as Windows 11's, and follow the apps' light or dark mode, as thermi's menus do, and always show whole, above the overlay.
- R140. While the sensor service is not running, each overlay shows one pill, "Sensors stopped", with thermi's mark, in place of the items it reads; the items that read Windows itself (R182) never depend on the service and keep showing live beside it, on the overlay and in their tray icons, while thermi's mark and tooltip still say the sensors stopped.
- R190. While thermi's driver may be missing (R16), a missing value of the CPU's temperature, power or clocks shows "Driver" in place of "–", translated, once per pill: its first such value says it, and the others show "–"; its tooltip says why and what to do (R139), and its double-click opens the window, whose driver bar offers the fix (R145).
- R185. The tooltip of a value read from a CPU or a GPU names the device's model as the service reads it, as "AMD Ryzen 9 9950X", in a line after the value.
- R186. The CPU is throttling while, in one snapshot, CPU clock (the average of its cores) reads under the CPU's base clock, the nominal speed Windows gives for the processor, and CPU temperature is at or above R27's warning for that CPU. Then every value that reads the CPU's temperature or clock shows a dashed 2 px line in the critical color over it, at any level, and its tooltip adds "Throttling: 3.1 GHz, under its 4.3 GHz base clock, at 92 °C." Nothing throttles while either reads nothing or the base clock is unknown. A GPU never shows it: the sensor library exposes no thermal limit for a GPU.
- R187. The tooltip of a critical value read from a CPU or a GPU adds what is busiest there now, as "Busiest now: chrome, 23 % of the CPU. Open Task Manager from the overlay's menu.": for a CPU, the process with the most processor time over the last 2 s, as a share of every logical processor; for a GPU, the one with the highest use of any engine of it, from Windows' GPU counters; processes of one name count as one, and the idle process never. Windows' counters are read only while such a value is critical, and Task Manager cannot be opened on one process, so the tooltip points to R184's entry.
- R182. Three items read Windows itself, with no sensor, driver or administrator rights: Uptime, the time since Windows started, in hours and minutes as R170 shows a time; Local IP, the IPv4 address of the adapter Windows' default route goes through, missing without one; and Clock, the time now with its seconds, in the regional format. The catalog lists them under PC, a device of its own, and they take the labels UP, IP and TIME, translated like the other default labels. Thresholds judge none of them, so they have no thresholds, graph, chart or level. While the service is stopped, they give way to the "Sensors stopped" pill with the rest (R140).
- R157. Without click-through, the whole of every pill catches clicks, at any background opacity.

### Placement and size

- R30. The overlay can sit on the taskbar of any monitor that has one, anywhere along it, centered across it, where it was dropped. It never moves by itself: not for the app buttons, Start, the notification area or another overlay, for which thermi keeps no room and decides no fit. An overlay moves only when the person moves it. One dropped, shown again, or grown by its size or its items into another on its taskbar never covers it: it pushes it along, a margin away, toward the notification area only, never back toward the taskbar's start and the app buttons, and the pushed one keeps the place it was pushed to as its own offset, written in the same undo step as what pushed it, so hiding, shrinking or moving the one that pushed it never moves it back, and no two ever swap places. The last keeps to the notification area's edge, or to where it was dropped past it. None is ever pushed off its taskbar, back over the app buttons or onto another monitor: one that grows past the room the others leave toward that edge shows at that room, smaller, but never smaller than at 100 %, or its own size when smaller, and its size applies again once there is room; a move onto a taskbar, by a drop, the window's map or Alt+arrows, where the others leave the overlay no room at its own size is refused, changing nothing, and says so where it was made: a drag lights no mark there and the pointer shows it is refused, the window's map says it in a note. Where the room shrinks by itself, as when the notification area grows or one is shown again on a taskbar nearly full, no overlay shows smaller than that: the one before is held back toward the taskbar's start, over the app buttons, the lesser evil next to one too small to read, and keeps its own place, which it shows at again once there is room; one beside the notification area grows toward the taskbar's start, up to the one before it. It moves only to stay on its taskbar: when the taskbar moves to another edge or monitor, starts or stops hiding, or Explorer restarts, or the resolution or scale changes, it keeps its offset from the taskbar's start, held whole on the taskbar. Without an offset, as on a new install, after a reset, or placed by the window's map, it sits a margin before the notification area or, on other monitors, the clock, and follows it until it is moved; where that cannot be found from its window, it keeps a fixed reserve of 220 px from the taskbar's end, times the monitor's scale.
- R31. The overlay can snap to any corner of any monitor's work area. The top corners sit 64 px below the work area's top, times the monitor's scale, so they never cover a maximized window's title bar and its buttons; a drop between a top corner's mark and the work area's top snaps to it. In the window's Position map, the spot pointed at or focused, else the overlay's, is named in words under the map, as "On the taskbar, display 1"; the taskbar's spot sits at the middle of the overlay where it shows.
- R32. A snapped overlay keeps its snapped edges in place when its width, its height or the taskbar changes: in a corner its corner's, on the taskbar its left edge at its offset, or its right edge beside the notification area without one, which a drop on the mark beside the notification area keeps, so the overlay follows the notification area as it grows. The computed position is never written to the file.
- R33. Moving a snapped overlay by more than the system's drag distance, times the monitor's scale, unsnaps it, and it stays where it was dropped. A click or a double-click keeps the snap, and a free drop is kept where the overlay then shows, inside its work area. Dropped with its middle on a horizontal taskbar, an overlay stays on that taskbar where it was let go along it, centered across it and whole on it, over the app buttons or the notification area too, since a free overlay never sits on a taskbar. Two overlays may sit anywhere on a taskbar, touching included; dropped onto another, an overlay merges into it (R148). The marks are magnets, at the taskbar's start and beside its notification area, and at the corners. Snaps reach 96 px, times the monitor's scale: an overlay dropped on a taskbar within 96 px along it of one of its marks goes to that mark; dropped off the taskbars with its edge nearest a corner's mark within 96 px of it, to that corner, the mark filling as soon as it is in reach, measured where the overlay would show, so one pushed past the monitor's edge into the corner reaches it; and one whose edge facing a taskbar is within 96 px of it goes onto that taskbar the same way. Dropped farther, it stays free where it was let go; with Alt held no mark, no reach and no other overlay pulls it, so it stays where it was let go, on the taskbar or free. Where two marks' places overlap, the one beside the notification area is offered.
- R34. A snap to a monitor that is not connected falls back to the same spot on the primary monitor, and goes back when the monitor returns.
- R35. A monitor is known by the maker, model and serial in its EDID, which survive restarts and a change of port; a monitor without a serial is known by its connection.
  Release check: Monitors and taskbars.
- R36. The size is one slider in Appearance, from 75 % to 400 % over the monitor's own scale, 100 % by default, so a big screen read from afar is served. The look never changes it. On a taskbar the overlay shows at most as high as the taskbar, never cut, its pills and their text with it; the size kept applies again off it, and the Size row says so under it while the overlay sits on a horizontal taskbar. Off a taskbar, free or in any corner, an overlay never shows larger than its monitor's work area less a corner's margin on each side: one that would shows smaller, whole within it, and the Size row says so under it.
- R204. The overlay's menu has "Size ▸": "Bigger" and "Smaller", each one step of the Size slider, 5 %, from the size the overlay shows; then 75 %, 100 %, 125 %, 150 % and 200 %, as radio choices with the overlay's own checked; then "Custom…", which opens the window on that overlay with the focus on its Size slider, or brings the open window there. No entry is offered that would change nothing the overlay shows: "Bigger" at 400 % and "Smaller" at 75 %, and on a taskbar, where it shows at most as high as the taskbar (R36), "Bigger" once it shows that high and every size above that, the Size row's "On the taskbar it never grows taller than the taskbar." closing the submenu, grayed, while it caps it; "Smaller" there steps down from what it shows. - R143. Labels show as "Show labels" says (R82), never hidden or shown by thermi on its own. An overlay on the taskbar sits where the person put it, over the app buttons, Start or the notification area too: thermi reads no app buttons, keeps no room beside them, decides no fit and says nothing about one, and never moves an overlay to make room for another, but for one dropped, shown or grown into it on its taskbar, which pushes it toward the notification area, where it then stays (R30). The only fit it decides is between overlays: a move onto a taskbar where the others leave no room for the overlay at its size is refused (R30).
- R181. The overlay sits on a taskbar at the top of its monitor as on one at the bottom. On a taskbar at the left or right, as Windows 10 and StartAllBack allow, or on one that hides itself, an overlay on the taskbar shows just above the work area's bottom at its offset from the monitor's left edge, or in its bottom right corner without one, as on a monitor without a taskbar, and a hiding taskbar's band is kept free, so it never slides over the overlay. - R95. OLED care, off by default, moves an overlay 1 px every 3 minutes through four spots, the corners of a 1 px square, and back. On each axis, the square lies inward of a snapped edge, and up or to the left where there is none, as for a free position or an overlay on the taskbar. The offset is never written to the file.

- R128. While the window is open, an overlay that its own Hide, "Hide overlays" or "When to show" hides stays off the desktop, the one being edited included; the window shows it only in its Position map and its list, dimmed, with "Hidden".

At 4 overlays nothing makes a fifth, and says so rather than doing something else: "New overlay" is off, "Move to a new overlay" is not offered, the overlay's menu shows "Separate" grayed with "4 overlays at most" beside it, and a pill held on the desktop lifts nothing: the pointer turns to Windows' unavailable sign until it is let go, and the drag moves nothing (R148).

### Desktop gestures

- R148. A drag moves the whole overlay, wherever it is pressed, with snap marks on the taskbar and the corners; dropped on another overlay, it merges into it. A drag is on another overlay, anywhere, on a taskbar or the desktop, whatever either holds, one pill or many, while the cursor is on it or what the drag carries, the overlay or a lifted pill, covers at least half of it or of itself; with Alt held it is on none, and drops where it is. From a taskbar, an overlay and a lifted pill leave it as from anywhere else, and drop anywhere on the desktop of any monitor, free or onto a mark in reach. A pill pressed and held still for 500 ms, never leaving the drag distance, lifts (on an item's value, in a pill of several, the item alone does, R199), shown a little above its place with an empty slot left where it was, and its drag then takes it off its overlay: dropped on another overlay, it joins it where it was let go, before the pill it lands in front of; dropped back on its own overlay, it moves there, and stays put on its own place; dropped elsewhere, it becomes an overlay of its own, which snaps to the marks like any overlay. With 4 overlays a pill held still lifts nothing and its drag moves nothing, the pointer showing Windows' unavailable sign until it is let go (R130), never a move of the whole overlay the hold did not ask for. A drag begun before the hold, however slowly, moves the whole overlay, and an overlay dropped on another joins it where it was let go, as a pill does, and the pill of an overlay of one pill moves its overlay. In the window, an item's "Move to a new overlay" and "Move to …" do the same by keys. A floating overlay has a corner that resizes it from 75 % to 400 %, where the drag's shape turns it horizontal or vertical; a double-click on that corner brings its size back to 100 % and keeps its direction. Alt+arrows on a floating overlay's row in the list move it 8 px, 1 px with Shift; on one dropped on the taskbar, left and right move it along it; on another snapped one they say why it does not move. An overlay held in a drag shows opaque, without its fade, and the overlay a drop would join shows whole, ringed in the accent color with a bar where the drop joins it, before the pill the cursor, brought onto it, is in front of; an overlay no drop would join shows nothing. Esc during a drag, which the overlay holds while pressed so no other app gets it, or another window taking the mouse, puts the overlay back where it was; after a drop, no value's tooltip shows until the pointer leaves the overlay or 1.5 s pass; once a drag ends, nothing of it stays on screen, no mark and no carried pill.
- R199. A hold lifts what it is pressed on, with no modifier key: on a pill's label, the whole pill, as R148 says; on an item's value, its number and what it draws before it, in a pill of several items that shows its label, that item alone, carried as its own picture as it lands off its pill, with its pill's label, and an empty slot left where it was. In a pill of one item, or one that shows no label, a hold anywhere on it lifts the pill; in one bar, a run's label lifts the run and a value its item. A lifted item dropped on its own pill moves there, before the item it lands in front of or after the pill's last, and stays put on its own place, the bar marking where between the items; dropped anywhere else on an overlay, its own or another, it joins it as a pill of its own before the pill it lands in front of, as a lifted pill does; dropped on the desktop, or on a taskbar's mark, it becomes an overlay of its own. The pill it leaves keeps its label and its place, and every other pill shows as it did. As with a pill, at 4 overlays a held item lifts nothing (R130), a locked overlay lifts nothing, and each drop is one step (R150); by keys, the list moves items as it does (R11, R47).
- R205. Ctrl and the mouse wheel over an overlay make it bigger or smaller, a step for each notch, as "Bigger" and "Smaller" do (R204) and within the same bounds, on a taskbar, in a corner or free; a precision touchpad's smaller turns add up to a notch. Notches less than 1 s apart are one step, as a key held on a slider is (R8). The wheel alone does nothing to the overlay. A locked overlay keeps its size to the wheel, as it keeps its place to a drag and its size to its corner; a click-through overlay never gets the wheel. The overlay never takes the focus, so the wheel reaches it while Windows scrolls the inactive window under the pointer, as it does by default; with that turned off, the menu and the window resize it.
- R150. Each desktop gesture is one undo step: in the window's history while it is open, and, for 30 s, as "Undo" with its name in the overlay's menu. So is each edit chosen from a menu (R196).

### Visibility, click-through and lock

- R68. "When to show", in an overlay's Placement, shows it always (the default), hides it in full screen (games, videos), or shows it only in full screen. It follows a change within a second.
- R70. "Hide overlays", in thermi's menu, in the overlay's menu when there is one overlay, and on its hotkey, hides every overlay until they are shown again: it is a flag that is never saved, and every start of thermi begins without it. Showing them (the hotkey again, a click on thermi's icon, or "Show overlays") clears only that flag, so an overlay hidden on its own (R127) stays hidden. Hiding never touches tray icons.
- R84. Click-through, in an overlay's "Lock, click-through and OLED care", in thermi's menu and on its hotkey, never in the overlay's own menu, lets every click on the overlay pass to what is below.
- R85. Lock position, in the overlay's menu, its Placement and thermi's menu ("Lock all overlays" with several), keeps a drag from moving the overlay; clicks and double-clicks work as always.
- R189. "Fade near the pointer", an overlay's switch in "Lock, click-through and OLED care", off by default, makes the overlay fade as the pointer comes within 96 px of it, times its monitor's scale, from 100 % down to 25 % on it, and come back as it leaves; it still takes clicks (R157). It never fades while the window is open, while it is dragged, or under click-through. The pointer is checked ten times a second, only while the switch is on.

### Hotkeys

- R69. Four hotkeys, all off by default, are set in Settings: "Hide or show the overlays"; "Next look on all overlays", offered once a saved look exists; "Click-through on all overlays"; and "Reset min and max", offered once an item shows a minimum or maximum. A combination that another app holds is refused with that reason, also when it was written by hand in the file. Without the overlay running, the window says the hotkeys work only while it runs.
- R133. A hotkey needs Ctrl or Alt, except F13 to F24, which work alone. Each of these is refused, with its reason in its row: any combination with Win; Alt with a letter or a digit; Ctrl or Ctrl+Shift with C, V, X, Z, Y, A, S, F, N, W or T; Alt+F4, Alt+Tab, Ctrl+Alt+Delete and Ctrl+Shift+Esc; the window's own shortcuts; Ctrl+Alt with a key that types a character with AltGr on the active keyboard layout; and another hotkey's combination.
- R134. A hotkey's row records the next combination pressed; Esc cancels, Backspace or the row's × clears it, leaving the focus on it, and thermi's own hotkeys rest while it records.

### The settings file

- R37. The window never writes invalid settings.
- R38. A write never loses a change the other process made meanwhile.
- R39. A read that finds the file locked, empty, cut short or missing is retried before it counts, so an editor's save in progress never shows as defaults or as a broken file, and a missing file is recreated only if it is still missing after the retry.
- R40. While the file is broken by hand, the window shows only a page with the line and the reason, "Open in editor" and "Restore last good settings", and the overlay's and thermi's menus say "The settings file is broken" at their top.
- R41. "Restore last good settings" first keeps the broken file beside it under a dated name, then writes the last settings read well in this session, or the defaults if there were none.
- R42. A change made by hand while the window is open shows in it at once, and the window's own writes never come back to it as outside changes.
- R43. The file is at version 6. Version 1 files are migrated when read, and version 2 to 5 files once; a file of an older version is written in this one as soon as it is read, its old text kept beside it as `config.v{version}-{time}.json`, so the file on disk always says what the window shows. Lines whose critical is still v0.1's default for their meter take this version's, names thermi gave (an overlay's place, numbered or not, or a metric item's own metric name, in any language) are dropped, and a custom look with 10 px labels takes Standard's label. A load metered by itself without lines, as thermi made it, shows its line (R90), as a new load does. Version 6 splits versions 2 to 5's meter in two, what an item warns by (R28) and what it draws (R90), and an item draws and warns as it did: a meter of the item's own reading becomes its own, another stays what it warns by, a graph switched on becomes a line, a meter without it bars, no meter none, each written only where it differs from what its overlay's Auto would draw. Default and migrated items store no name, so they read in the window's language. The taskbar's three places of versions 2 to 4 become its one place of R30: the right one beside the notification area, the left one a margin in from the taskbar's start, and the center one, which the app buttons decided, beside the notification area.
- R44. Every item has an id, unique in the whole file, that every read of the same file gives back the same, including for items added by hand without one or with a repeated one.

### When something fails

- R45. When the sensor service is not running, a bar says "The sensor service stopped. Live values come back as soon as it runs." with "Start it", which asks Windows for administrator rights once; thermi's menu offers "Start sensors" too. The window recovers on its own when the service starts. When the service's data goes stale, the window says so and stops showing live values until fresh data arrives.
- R145. When a CPU temperature, power or clock reads exactly zero, a bar says "CPU temperature, power and clocks need a small signed driver. Windows asks for permission once." with "Install driver", which shows the administrator shield, and "What is this?". "Install driver" asks Windows for permission once, then shows "Installing the driver…" with its progress, then "Driver installed. CPU temperature is reading now.", which goes after 8 s. Refused, it says "The driver was not installed. Windows did not get permission, so nothing changed." with "Try again". "What is this?" explains, in a dialog, that the driver only reads sensors and never changes clocks, voltages or fan speeds, that it is removed from Windows' Installed apps, and that some anti-cheat software refuses to run beside it; the dialog has its own "Install driver", with the administrator shield, and Close. No text of thermi names the driver's product.
- R198. One device slow to read never holds back the others (ADR 0015): when a device takes longer than half a second, as a board whose bus another program, such as a fan controller, holds, the service sends the other devices' readings each second all the same. The slow device's sensors keep their last values for up to 3 s from when its read came due, then show as missing until it reads again, as a reading that stopped does, and so do those of a device whose read fails, a drive read every 5 s too; the service writes how long it took, and how it failed, to the event log once it returns, at most once a minute for each device.
- R201. A snapshot the window cannot read, as one Core throws on, never closes it: the window goes on showing the last snapshot it read, logs the failure once until a snapshot reads again, and shows the next one it can read.
- R202. An overlay that crashed or hung after running a minute or more is started again by Windows, as it ran, `--trace` included, once Windows has asked, as it does for any program that stopped working (ADR 0017). Not when it was ended by hand or by "Exit thermi", nor when an update of thermi or of Windows closed it, which start it themselves; `thermi settings`, `preview` and `cpu-load` are never started again.

### Network and disk

- R159. The sensor service also reads network adapters and drives: each adapter's download and upload speed, data received and sent, and utilization; each drive's read and write rate, total activity, used space and temperature. A drive's temperature is a temperature like any other: it shows, charts and warns as one.
- R160. A throughput, a type of sensor of its own, shows in bytes per second, in the largest of B/s, KB/s, MB/s and GB/s that keeps three significant digits, with 1 KB = 1000 B, as 812 KB/s, 12.4 MB/s or 1.05 GB/s, in the regional number format, with its units translated.
- R161. A throughput's tray icon fits its value in 4 characters with its scale letter, as 812K, 12M or 1.1G, and with units hidden the overlay keeps that letter too, as 12.4M.
- R162. Network download and upload are metrics picked per machine: they follow the adapter that has moved the most data since the service started.
- R163. Disk activity, read and write are metrics picked per machine: they follow the drive whose total activity, averaged over the last minute, is highest, chosen again at most once a minute.
- R164. An adapter or a drive picked in the catalog or in the Sensor dropdown stays the item's own; the dropdown's Auto names the adapter or drive it follows now, as "Auto · Intel I226-V".
- R165. The catalog lists adapters under Network and drives under Disk, each one a device of its own, and its type chips gain Throughput; "net", "internet", "ethernet", "wifi", "bandwidth" and "disk" find them.
- R166. A throughput and a disk activity start with no lines, and thresholds judge a throughput, as they do a fan's speed. A throughput's chart runs from 0 to the highest of its readings and lines plus 15 %, rounded up to a 1-2-5 step of its unit (1, 2, 5, 10, 20, 50 …), with Min · Avg · Max as any chart.
- R167. Download and upload added from the catalog share the label NET, so together they make one pill, as "NET ↓ 12.4 MB/s ↑ 1.2 MB/s": the arrows are symbols drawn before each value, the same in every language, and no part of the label. A drive's read and write rates take its drive's label, so they join that drive's pill. The default overlay does not change.
- R183. A network throughput item, and no other, can show its value in bits per second, in its "More options", off by default: in the largest of bps, Kbps, Mbps and Gbps that keeps three significant digits, with 1 Kbps = 1000 bps, as 99.2 Mbps, in the regional format and with its units translated, and with units hidden or in a tray icon with its scale letter, as R161 says. Its lines, its chart and the file stay in bytes per second.
- R168. With network adapters and drives read, the sensor service stays within ADR 0011's budget for it at rest, under 80 MB of private memory, on a PC with two drives and two adapters.
  Release check: Costs at rest.

### Battery, sleep, adapters and CPU load

- R169. The sensor service also reads batteries: the charge level, the charge or discharge rate, and the time remaining when Windows estimates it. A PC without a battery reads none, and nothing about a battery shows, warns or fails.
  Hardware report: A laptop.
- R170. A battery's charge is a percentage; its rate is in watts, with a minus sign while it discharges, as "−12.4 W"; its time remaining reads in hours and minutes, as "2 h 14 min", with units translated, and as missing while the battery charges or the PC is plugged in.
- R171. The catalog lists a battery under Battery, a group that does not show on a PC without one. Battery items added from the catalog take the label BAT, translated like the other default labels, and start with no lines, since a line warns above a value and a battery's trouble is below.
- R172. After the PC wakes from sleep or hibernation, no reading from before it slept shows as live: until fresh data arrives, values show as missing as R45 and R140 say, and minimums, maximums, averages and charts leave the time asleep out instead of joining across it.
- R173. Within 5 s of waking, the pipe, the readings and the network and disk speeds come back on their own, with no click, and no speed is computed across the time asleep.
- R174. When the PC wakes with different monitors, each overlay goes back to its snap within 5 s of the new layout, as R34 says.
- R175. Auto for network download and upload skips adapters that are not physical: loopback, tunnels and VPNs, Hyper-V and WSL switches, and any other that Windows marks as not a hardware interface, unless no other adapter moves data. Any adapter can still be picked by hand.
- R176. CPU load reads within 3 points of the CPU utilization on Windows 11's Task Manager, at rest and under a full load: busy time over elapsed time across all logical processors, Windows' "% Processor Time".
  Release check: CPU load against Task Manager.

- R51. While the window is open and idle, the overlay stays within its budget (spec 001's R9, as `docs/adr/0001-architecture.md` amends it).

## Design

### The pieces

| Piece | Where | What it does |
| --- | --- | --- |
| The window's process | `src/Thermi.Windows/Ui` | `thermi settings` runs the window in a process of its own of `thermi.exe`, on an STA thread: one WebView2 control in a native frame (`docs/adr/0005-settings-window-process.md`, `docs/adr/0007-settings-window-in-webview2-and-react.md`). |
| The page | `src/Thermi.Settings.Web` | React, TypeScript and Fluent UI React v9, built with Vite and embedded in `thermi.exe` by the .NET build. It holds no rule. |
| The bridge | `src/Thermi.Core/Bridge/IWindowBridge.cs` | The one typed interface between the page and C#. `src/Thermi.Settings.Types` writes its TypeScript and the texts' keys in the build, so a change that breaks either side fails it. |
| The window's logic | `src/Thermi.App/Window`, `src/Thermi.Core` | The edits, undo and its step names, the readings and charts the window keeps. |
| The settings file | `src/Thermi.App/SettingsFile/ConfigStore.cs` | Every read and write of `config.json`, by the window and the overlay alike. |
| The overlay | `src/Thermi.Windows/Overlay`, `src/Thermi.Windows/Painting`, `src/Thermi.Windows/Gestures`, `src/Thermi.Windows/Tray` | The overlays, their gestures, thermi's icon and the tray icons, and the history it hands the window. |
| The sensors | `src/Thermi.Sensors.Windows` | Network, storage and battery hardware on, and each adapter's kind from IP Helper. |

### The window and its page

- **The frame is Windows' own**: Mica, the caption buttons, snap layouts, the system menu and Win+arrows. The page draws the title row's content in WebView2's non-client region, which marks the rest of the row as caption. Where Windows 10 refuses `DWMWA_SYSTEMBACKDROP_TYPE`, the background is opaque in the system's colors.
- **Nothing from the network.** The embedded files are served from a virtual host name; a strict Content Security Policy allows only that host.
- **Fluent only through the kit** (`src/Thermi.Settings.Web/src/kit`): an ESLint rule forbids importing Fluent anywhere else, and another forbids text literals in JSX, so every text comes from the translations through the bridge. npm installs run from the lockfile without install scripts.
- **First size and place** come from plain geometry in Core (R116), remembered per setup of monitors in `%LOCALAPPDATA%\thermi`. While active, the window sits above thermi's overlays (R118).
- **The page's tests** run in Edge against the built page with the C# side faked from recorded snapshots. The fake never decides what C# decides: its answers to edits, undos, looks and searches come from the real bridge's, in `src/Thermi.Settings.Web/tests/oracle/edits.json`.

### Writes, reads and undo

- **Writes.** Every writer holds a named mutex from its re-read of the file until its write is moved into place. The work under it is synchronous, and the mutex is polled every 50 ms on the injected clock, giving up after 2 s; the write is then tried again through the throttle until it lands. The overlay writes off its UI thread, so it never waits. A writer applies its own change to what it just read, under a temporary name of its own, and deletes temporary files left beside the settings. A re-read that finds the file broken writes nothing (spec 001, R7).
- **Reads.** A read that finds the file locked, empty, cut short or missing is retried every 50 ms for up to 500 ms; only then is it a problem, defaults, or a missing file to recreate. Readers share read, write and delete, so they never block a move into place.
- **Throttle** (`src/Thermi.Core/Throttle.cs`): window writes, overlay reloads and the overlay's paints go out at most once every 100 ms, the last value always. With `--trace` both processes log on one monotonic clock, input and paint, which is how R7 is measured.
- **Item ids.** Ids already in the file are reserved first. An item without one, or with one taken, gets its metric or sensor id, with the first free suffix (`cpu.temperature-2`). Every read of the same file gives the same ids.
- **Undo** keeps the window's changes as operations on ids, each with what it found and what it left. A field goes back only if it still holds what the window wrote; an added item or overlay goes only if still as added; a deleted one comes back at its place, or at the end, unless its id exists again; a move goes back only if the item is still where it was moved; a reset is one step of these. Redo checks the same way, and a step that cannot apply is skipped, saying so. The window recognizes the watcher event its own write causes. A desktop gesture or a menu edit (R150) reaches the window as a message naming its write, and the window takes that write's difference as a step; the overlay keeps its last gesture for 30 s for the "Undo" of its menu.

### The window and the overlay

They talk through the file for settings, and through window messages for the rest (`docs/adr/0009-overlay-and-window-messages.md`, `src/Thermi.Core/Messages/WindowMessage.cs`):

| Message | From → to | What for |
| --- | --- | --- |
| history | overlay → window | Each item's ten minutes, as the window opens and after "Reset min and max", by `WM_COPYDATA` to the window's beacon. |
| select | overlay → window | A click on a value or an overlay's edge selects it (R99); "Custom…" of the Size menu asks for the overlay's Size row (R204). |
| edited | window → overlay | The overlay and item being edited, for the marks and fades (R104, R128). |
| gesture | overlay → window | A desktop gesture's or menu edit's write, as an undo step (R150). |
| raise | second thermi → window | Bring the window to the front, on an overlay and item (R151). |
| hotkey status | window → overlay | Which hotkeys the overlay could not register, with an FNV-1a hash of the four combinations, so the window trusts only an answer about the hotkeys it holds. |

The overlay's process has one hidden top-level window, class `thermi-host`, which owns the tray icons and hears `TaskbarCreated`; the window's has one of class `thermi-settings`. Message ids come from `RegisterWindowMessage`, and each waits 500 ms. A second `thermi settings` finds the window, calls `AllowSetForegroundWindow` for it, sends "raise" and exits; the overlay does the same before it starts a process from a click.

- **History** lives in the overlay: ten minutes of what each item warns by, 600 one-second slots per item with gaps kept, its last minute of values, its minimum, maximum and average (`src/Thermi.Core/Look/ItemHistory.cs`). The window then keeps its own from the pipe, and a minute for each catalog sensor's sparkline. The service keeps none.
- **Visibility.** An overlay shows unless its own Hide (`hidden`, saved), the "Hide overlays" flag (never saved) or "When to show" hides it. "When to show" asks `SHQueryUserNotificationState` and whether the foreground window covers the overlay's monitor, once a second; a game in exclusive full screen draws over every window. The window is open while its named mutex exists, which the overlay checks on its tick, so a window that closes or crashes ends its marks within a second.
- **Hotkeys** are registered by the overlay (`RegisterHotKey`), the process that always runs. Which are refused is Core's (R133); for AltGr, the window reads what the keyboard layout types with Ctrl+Alt (`ToUnicodeEx`).
- **The driver hint** (R16, R22, R145) is inferred from zeros, since a snapshot carries no driver state. Installing the driver and starting the service run as SYSTEM through `thermi-elevated` (`docs/adr/0010-driver-and-service-from-the-window.md`).
- **The tray** is `Shell_NotifyIcon` in the overlay's process. Each icon's GUID comes from the item's id, or "thermi", and the executable's path. An add first deletes any icon left with the same GUID; one that fails is tried again every 5 s. What each icon shows, and the state of thermi's mark, is decided in `src/Thermi.Core/Tray`; the mark is drawn from hand-placed pixels at 16 and 24 px and a vector above.
- **A crash or a hang** is restarted by Windows through `RegisterApplicationRestart` (`src/Thermi.Windows/Win32/CrashRestart.cs`, `docs/adr/0017-windows-restarts-the-overlay.md`).
- **Clicks.** A layered window passes clicks through fully transparent pixels, so every pill is painted at an alpha of at least 1/255; only click-through (`WS_EX_TRANSPARENT`) lets them pass.
- **Leaks.** Every GDI object, icon and brush is released where it is made; fonts are made once per look. `tests/Thermi.Windows.Tests/Acceptance/LeakTests.cs` runs R86's rounds.

### The fan finder

The finder (`src/Thermi.App/Finder`) treats every fan sensor as a candidate and reads `cpu.load` during the run. Its tests replay series recorded with `thermi-sensors --dump <file> --seconds <n>`, one snapshot per second, 5 s before a 30 s CPU load and 10 s after, in `tests/Thermi.Tests/Recordings`. On a replay, the load starts at the first second whose CPU load passes 50 %. The author's PC has fan-control software that barely answers during the load and rises after it; a board that answers the load is covered by series derived from the real one, and by hardware reports (`.github/ISSUE_TEMPLATE/hardware-report.yml`).

### The settings file, version 6

Fields are named, never inferred from a string's shape; a choice at its default is left out.

| Level | Fields |
| --- | --- |
| thermi | `version`, `overlays` (1 to 4), `hotkeys` (`toggle`, `nextStyle`, `clickThrough`, `resetMinMax`, each like `Ctrl+Alt+T`), `language` (left out to follow Windows), `temperature` (`c` or `f`), `windowTheme` (`system`, `light`, `dark`), `sensorNames` (the user's names, by sensor id), `agents` (spec 003) |
| overlay | `name` (only one the user typed), `items`, `snap` (`monitor`, `spot`, and on the taskbar `offset` from its start, in physical pixels) or `position`, `size` (0.75 to 4), `graph` (`auto`, `none`, `bars`, `line`), `style`, `visibility` (`always`, `hide-in-fullscreen`, `only-in-fullscreen`), `hidden`, `clickThrough`, `locked`, `oled`, `fade` |
| item | `id`, `name`; `metric`, `sensor`, or `sensors` with `combine` (`max`, `average`, `sum`); `auto` (the metric it came from); `label`, `own`, `tray`, `color`; `warnBy` (`metric`, or `sensor` with `auto`) and `threshold`, in the unit of what it warns by; `offset`, `stat`, `smooth`, `decimals`, `bits`, `graph`, `alertOnly`, `notify` |
| style (the look) | `name` (the saved look it came from); `layout` (`pills`, `each`, `one`), `orientation` and `noLabels`, which stay with the overlay when a look is worn; `preset` (`standard` or `custom`; `compact` and `large` read from hand-written files), `label` and `value` (`size`, `weight`); `opacity` (`background`, and `overlay` from 0.2, which only hand edits and look files set); `pills` (`dark`, `light`, `system`); `colors` (`normal`, `warning`, `critical`, `label`, `value`, `background`); `units`, `font`, `corners`, `gap`, `effect` |

The file says "style" where the window says "look". Presets at 100 %: Standard is 13 px semibold labels and 13.5 px bold values; Compact is 11 and 12 px, Large 16 and 17 px. The pills' outer, border and unlit meter colors are `#20201E`, `#31312F` and `#2E2E2C` when dark, `#F3F3F1`, `#DADAD8` and `#D5D5D3` when light; Auto text is `#A9A9A7` labels and `#EFEFEE` values on dark pills, `#5C5C5A` and `#1A1A1A` on light ones. A pill color of its own (R203) counts as light where black stands farther from it than white; its border mixes it 12 % toward the values' color, the unlit track 8 %.

A look file (`src/Thermi.Core/Look/StyleFile.cs`) is `{ "thermiStyle": 1, "style": { ... } }`, with the look's fields and its name. A saved look is one such file in `%APPDATA%\thermi\styles`; an export is the same file.

**Migration** (`src/Thermi.Core/Settings/ConfigMigration.cs`). A version 1 file becomes one overlay: its `sources` go to the items and meters that show those metrics, each keeping its metric as `auto`, a saved `position` stays free, and an item just as thermi 0.1 made it becomes this version's default of its metric. Versions 2 to 5 are written as version 6 once read, the old text kept beside it (R43).

### Sensors and readings

- **Network and disk.** Core has a `Throughput` sensor type, in bytes per second, and the metrics `network.download`, `network.upload`, `disk.activity`, `disk.read` and `disk.write`: an adapter picked by the data it moved since the service started, a drive by its activity over the last minute, picked again at most once a minute. Drives update every 5 s. Units follow Windows: decimal KB/s, MB/s and GB/s.
- **Battery.** The metrics `battery.charge`, `battery.rate` and `battery.time`, with a `Duration` type for the time. A desktop's recordings prove the group stays hidden.
- **Physical adapters.** The service reads each adapter's interface type and Windows' hardware flag from IP Helper (`GetIfTable2`, in `src/Thermi.Sensors.Windows/Reading/NetworkAdapters.cs`), matched by interface id, never by name, since names are translated and chosen by vendors.
- **Sleep** is a gap in the snapshots' times longer than the stale limit: the history marks it, and values stay missing until a snapshot newer than the wake. The service and the overlay also listen for Windows' resume event.
- **CPU load** is the library's CPU Total, busy time over elapsed time across all logical processors, which Windows 11's Task Manager shows since its 24H2 update of May 2025. Older Task Managers show "% Processor Utility", which reads higher while cores boost.
- **Windows' own readings** (R182) are sensors of a device of their own, `/system/0` (`src/Thermi.Core/Sensors/SystemSensors.cs`), that both processes add to every snapshot: Uptime from Windows' tick count, Local IP from Windows' best route to the internet, read again when the network changes, and Clock from the injected `TimeProvider`.
- **Throttling and the busiest process** read the processor's `~MHz` base clock from the registry once, and PDH's per-process CPU and GPU engine counters only while a value is critical. None needs administrator rights.

### Translations and testing

- **Translations** are .NET resource files in `src/Thermi.Core/Translations`, English the fallback, shared by both processes; the page gets them through the bridge. The long pseudo-language of R75 is built from English by `thermi settings --pseudo`.
- **Testing.** Each behavior is tested once, at the cheapest layer that proves it: Core, then the Windows tests, then Playwright. Near-identical cases are one table. No test asserts a UI text, the DOM's structure or that something was called. Layout is one Playwright test over sizes, text scales and the pseudo-language; axe runs in every state, both themes and forced colors; the focus contract (R123, R124) is one test of a table of steps. A Playwright test is titled as one PascalCase word, so `acceptance.json` names both kinds alike.

### Rejected

Editing on the overlay itself, with flyouts anchored to its pills. The overlay is small, sits over the taskbar and must stay light; precise controls such as the chart need room, and a flyout has no keyboard path to it. The overlay stays clickable to select, and the window edits. `docs/adr/0007-settings-window-in-webview2-and-react.md` records the rejected ways to build the window.
