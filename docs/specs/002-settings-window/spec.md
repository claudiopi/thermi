# 002. A settings window where every change shows on the real overlay

**Status**: approved

## Why

Today thermi is configured by editing JSON: picking the fan that cools the CPU means knowing sensor ids, and thresholds are guesses made without seeing the values they guard. Version 0.9 makes it visual, live and impossible to break, without making the overlay any heavier.

The window follows four rules:

1. **The overlay is the preview.** Every change shows on the real overlay at once, which shows while the window is open. There is no Save button: undo replaces confirmation.
2. **Real data everywhere.** Every choice shows its live value: each sensor in the catalog, each threshold over the values it would have colored.
3. **Nothing can break it.** The window only writes valid settings, hand edits keep working, and a broken file is explained and kept.
4. **Free when closed.** The window lives in its own process; the overlay pays nothing for it.

Simple first, deep on demand: a look and a drag cover most people; every size, weight and color is one expander away for those who want it.

This text describes the window the design prototype settled on, after six rounds of review: a list of layers beside a pane, a chart as each item's page, and the real overlay as the preview and the index. The prototype supersedes the mockups in `docs/specs/002-settings-window/mockups`, which show the first window, built in WPF, and stay as history. The window is now React on WebView2 (`docs/adr/0007-settings-window-in-webview2-and-react.md`).

Spec 001 is done before this one starts: its by-hand steps use the "Edit settings" item that R1 replaces.

## Requirements

Opening

- R1. "Settings…" in the overlay's menu and in thermi's tray menu opens the window. In the overlay's menu it is the default entry, in bold, the one a double-click runs. It replaces "Edit settings"; opening the file moves into the window.
- R2. A double-click on an overlay opens the window with the item under the pointer selected, or the overlay when the pointer is on no value.
- R3. `thermi settings` opens the window.
- R4. Only one window exists: asking again brings it to the front.
- R5. The first frame shows within 1 s of the request when the window was opened before in this sign-in, and within 2 s the first time.
- R6. Without the overlay running, the window still works, and offers to start it.

Live editing

- R7. A change shows on the real overlay within 300 ms of the input, also while a slider moves. There is no Save button.
- R8. Ctrl+Z and Ctrl+Y, and the Undo and Redo buttons of the title row, undo and redo the window's changes since it opened, also while a slider has the focus. One gesture is one step: a drag from press to release, typing until the field loses focus, and repeated changes of one control within 1 s.
- R9. Undo never reverts a change made outside the window's history, a hand edit of the file or a drag while the window was closed, even of the same item: a step whose target no longer holds what the window left there is skipped, and the window says so.

The list

- R11. Items move with a drag of their row, or with Alt+Up and Alt+Down on the focused row, within their overlay; Delete on a row removes the item, from the list only; "Add item" and Ctrl+N add one. A move is announced, as "CPU power moved, 2 of 4, in its own CPU pill".

The catalog

- R13. "Add item" opens the catalog, which lists every sensor the service reads, one row each, grouped by device, with its live value, and says how many it lists. With several overlays, it names the overlay the item goes to, and another can be picked there.
- R14. Typing filters the catalog by words in any order, each matching where a word starts in a sensor's name, its second line, its device, its type, or a common synonym, as "temp", "graphics", "ssd" or "rpm"; a word that names one item, as "uptime", finds that item, not every item of its device; chips filter it by type, and in a panel too short for them, as at 200 % text in a small window, a Types dropdown does. With no match, it says so and suggests one word close to what was typed that finds something, or none. Esc first clears the search, then closes the catalog. Enter in the search adds the first match, Down moves into the rows, and Ctrl+Enter on a row adds it and keeps the catalog open; as the search changes, the count is announced, as "12 sensors. Down arrow to browse, Enter adds the first." or "No sensor matches. Try one word, like gpu."
- R15. Each sensor shows a sparkline of its values since the window opened, up to the last minute, drawn over at least its type's least span (10 °C, 20 %, 20 W, 300 RPM, 500 MHz), so a small change looks small.
- R16. A sensor without a usable value says why in its row: "Needs the driver" for a CPU temperature, power or clock of exactly zero, "Stopped or not connected" for a fan at 0 RPM, and "Reads nothing" for any other. A GPU's fan at 0 RPM is no fault: a GPU stops its fans while it is cool, so its row shows its 0 RPM as any value, with the quiet note "Stops while the GPU is cool". The overlay uses the same rule, so only those CPU sensors treat zero as missing.
- R17. Any sensor can be added as an item, shown in the unit of its type. It joins the pill of its device's kind (CPU, GPU, RAM, BOARD or SSD) after that pill's last item, or goes at the end when the overlay has none; it is selected, brought into view and announced. When its type can have a meter, it is metered by its own reading, with its type's thresholds (R27), as a GPU temperature's 80 and 88 °C.
- R18. An item's sensor is changed in its Sensor dropdown, which lists Auto first, for an item made from a metric, then every sensor of the item's type with its live value, with a filter when there are more than 6. It leaves out what the catalog hides whatever was seen, as a GPU's D3D loads, and a second sensor of a device with the type and name of one before it, but keeps the item's own. Each sensor reads by the name the catalog gives it (R178), as "CPU fan", with its device after it in a quieter color; a name the device gives sensors of other types too says its type after it, as "GPU Core (load)". When a fan item metered by a fan's duty changes its fan, by hand or by the finder, the meter becomes the new fan's own duty, or shows as missing if that fan has no duty sensor.

Finding the CPU fan

- R19. "Find it", on the Sensor row of the CPU fan item, first asks: "This loads the CPU for up to 30 s, so your fans speed up and may be loud.", with "Load the CPU" and Cancel. Once asked to, it says that the fans will speed up for up to 30 s, then first waits for 3 s of fresh readings, then loads every logical core at below-normal priority, for at least 8 s and at most 30 s. Once past 8 s, it stops when one fan has met the rule of R21 for 3 s in a row. A gap in the readings during the run stops it, and it says so.
- R20. It can be cancelled at any time, and the load stops within a second.
- R21. It picks the fan whose speed, averaged over its last 3 s, rose by at least 200 RPM and 20 % over its average in the 3 s before the load, and by at least twice as many RPM as any other fan. It then says which fan and how much it rose, and "Use it" makes the CPU fan item show that fan, as one undo step, keeping its meter; when the item already shows it, it says so instead.
- R22. Otherwise it picks nothing and says why: no fan rose, two rose alike, or the CPU load, averaged after its first 2 s, stayed under 80 %. When no fan rose, it adds that the fans may follow a curve set by fan-control software, and that the fan can be picked by hand in the Sensor dropdown. With no fan sensor outside the GPUs, it cannot start. It says the driver may be missing when the CPU temperature also reads zero, and that the board reports no fans otherwise.

An item

- R24. The item's chart is its page's hero: the meter's last ten minutes as a smooth line over a soft fill, with no frame or grid, and "Min · Avg · Max" of those minutes under its axis, its "Chart options" at their end. It spans from its first reading of those minutes to now, so a window just opened fills the chart with the seconds it has, and its axis says how long ago it starts, as "2 min ago" or "40 s ago"; a lone reading between gaps draws no line. The line's color follows its value: cool up to 20 of the meter's unit under the warning, the middle color at 8 under it, warm at the warning, and hot at the critical and above; without a critical, hot starts 10 above the warning, and without a warning the critical takes its place; without lines, the line runs from cool to the middle color. Those four colors are `#7088FF`, `#A57BFF`, `#FF8A3D` and `#FF5A4F` in dark mode, and `#3D5BFF`, `#7A3DF0`, `#C25200` and `#D92D20` in light mode. The band from the warning to the critical is tinted with the warning color at 7 %, and the band above the critical with the critical color. Each threshold is a line with a knob that holds its value. The chart's top and bottom say the ends of its range, small and quiet. A text summary gives screen readers the range, the value now and the lines. When the lowest line was reached for more than half of the ten minutes and the lines are not the meter's defaults, the chart says "Fires most of the time", quietly, with a button that brings the default lines back and says what they are, as "Use 90/95 °C", or "Remove the lines" when the meter has none.
- R25. The chart holds the last ten minutes from the window's first frame, also when the window has just opened. Gaps (the service stopped, or its data went stale) stay empty, never filled with the last value. Without readings, the chart's place says why, and its lines and knobs stay: "Sensors stopped: the chart comes back when they start." while the service is stopped, "Needs thermi's driver: the chart starts once it is installed." for a CPU sensor that needs it, and "No readings to draw yet. The thresholds apply as soon as this sensor reads." otherwise.
- R26. The warning is always below the critical: moving one past the other pushes the other 5 beyond it, 100 RPM for a fan, and the window says which moved, as "Warning moved to 80 °C to stay below Critical." or "Critical moved to 90 °C to stay above Warning."
- R27. Thresholds start calm: a CPU temperature warns 10 °C under the CPU's limit and is critical 5 °C under it (90 and 95 °C on AMD, TjMax − 10 and − 5 on Intel); a GPU temperature warns at 80 and is critical at 88 °C; any other temperature at 70 and 80 °C; a fan's duty warns at 85 %; loads, power, clocks, memory and fan speeds have none. "Reset thresholds", in the chart's "…", brings them back.
- R28. An item's meter, which its thresholds judge, is Off or a reading of the item itself, never another device's or another kind's: the item itself when it is a temperature, load, duty, fan speed or speed, and for a fan also its own duty, for a duty its own fan, where the service reads it. An item of another type, as power or clock, has no meter, so its Meter row does not show, nor "only on alert". Each choice is named by what it reads, as "Temperature", "Speed (RPM)" or "Duty", never "This value". A meter chosen brings its default thresholds. An item without a meter has no thresholds, charts only its own reading (R110), and never shows a level.
- R29. A pill's label can be changed, and the change applies to every item in that pill and to no other.

Placement

- R30. The overlay can snap to the left, center or right of the taskbar of any monitor that has one. Left starts a margin in from the taskbar's left end; right ends a margin before the notification area or, on other monitors, the clock; center is as near the taskbar's middle as the app buttons allow, never over them. Where the notification area or clock cannot be found from its window, the right spot keeps a fixed reserve of 220 px times the monitor's scale, as today.
- R31. The overlay can snap to any corner of any monitor's work area. The top corners sit 64 px below the work area's top, times the monitor's scale, so they never cover a maximized window's title bar and its buttons. In the window's Position map, the spot pointed at or focused, else the overlay's, is named in words under the map, as "Right of the taskbar, display 1".
- R32. A snapped overlay keeps its snapped edges in place when its width, its height or the taskbar changes, and the computed position is never written to the file.
- R33. Moving a snapped overlay by more than the system's drag distance unsnaps it, and it stays where it was dropped. A click or a double-click keeps the snap, and a free drop is kept where the overlay then shows, inside its work area. Dropped in a taskbar's row, an overlay snaps to that taskbar's nearest spot with room, the only ones its marks offer, since a free overlay never sits on a taskbar, so a drag sideways along it keeps it in the taskbar.
- R34. A snap to a monitor that is not connected falls back to the same spot on the primary monitor, and goes back when the monitor returns.
- R35. A monitor is known by the maker, model and serial in its EDID, which survive restarts and a change of port; a monitor without a serial is known by its connection.
- R36. The size is one slider in Appearance, from 75 % to 200 % over the monitor's own scale, 100 % by default. The look never changes it.

The settings file

- R37. The window never writes invalid settings.
- R38. A write never loses a change the other process made meanwhile.
- R39. A read that finds the file locked, empty, cut short or missing is retried before it counts, so an editor's save in progress never shows as defaults or as a broken file, and a missing file is recreated only if it is still missing after the retry.
- R40. While the file is broken by hand, the window shows only a page with the line and the reason, "Open in editor" and "Restore last good settings", and the overlay's and thermi's menus say "The settings file is broken" at their top.
- R41. "Restore last good settings" first keeps the broken file beside it under a dated name, then writes the last settings read well in this session, or the defaults if there were none.
- R42. A change made by hand while the window is open shows in it at once, and the window's own writes never come back to it as outside changes.
- R43. The file moves to version 3. Version 1 files are migrated when read, and version 2 files once; a file of an older version is written in this one as soon as it is read, its old text kept beside it as `config.v{version}-{time}.json`, so the file on disk always says what the window shows. Lines whose critical is still v0.1's default for their meter take this version's, names thermi gave (an overlay's place, numbered or not, or a metric item's own metric name, in any language) are dropped, and a custom look with 10 px labels takes Standard's label. Default and migrated items store no name, so they read in the window's language.
- R44. Every item has an id, unique in the whole file, that every read of the same file gives back the same, including for items added by hand without one or with a repeated one.

The rest

- R45. When the sensor service is not running, a bar says "The sensor service stopped. Live values come back as soon as it runs." with "Start it", which asks Windows for administrator rights once; thermi's menu offers "Start sensors" too. The window recovers on its own when the service starts. When the service's data goes stale, the window says so and stops showing live values until fresh data arrives.
- R47. Every action of the window, of thermi's menu and of the overlays' menus can be done with the keyboard alone, and so can every desktop gesture's result, through the list: Alt+arrows move a floating overlay, "Move to a new overlay" takes an item off, "Merge into" joins overlays, and the Size slider resizes.
- R48. Narrator reads a name and a role for every control of the window, and its value where it has one: a level in words ("CPU temperature 96 °C, critical"), a color button its color, a shortcut its keys.
- R49. The window follows Windows' light or dark mode, accent color and high contrast; under high contrast every part of it, the chart and the level marks included, takes the system's colors.
- R50. With animation effects off in Windows, nothing animates.
- R51. While the window is open and idle, the overlay stays within its budget (spec 001's R9, as `docs/adr/0001-architecture.md` amends it).
- R191. Open and idle, the window itself and its page's renderer stay under 1 % of one core together: each second's readings draw once, and only what they change, sent with the view and status they give so the page asks C# only for what reads them live, as a chart. Minimized, it draws and reads nothing, and once it shows again it shows the latest readings.
- R52. A "Start with Windows" switch applies at once and survives a reinstall. It changes Windows, not the settings, so Ctrl+Z does not touch it.
- R53. "Reset…" asks "Reset to defaults?" in a dialog whose Cancel is the focused accent button. Reset brings back one overlay with the default items, labels, meters, thresholds, placement (with click-through and lock off), size, look and visibility; the language, the hotkeys and the temperature unit stay. Undoing it restores every overlay, item and field that still holds its default.

Pills

- R54. A pill is a run of items with the same label. "Separate pill", on an item's page and in its row's menu, puts the item and the items after it with the same label in a pill of their own, which shows its label. The first item of a pill starts one already, so neither its page nor its row's menu offers it there, unless the item was itself set to start its own.
- R55. A layout setting shows the pills of R54 (the default), one pill per value, each with its label, or all the items in one bar, with a label where each run of the same label starts. The last two ignore which items start a pill, and keep it for when the layout comes back.

Style

- R56. The overlay can be horizontal (the default) or vertical, where the pills stack from top to bottom, all as wide as the widest. While vertical, the taskbar spots of R30 are not offered, and a taskbar snap shows at the bottom corner of the work area on its side, center going right, which the window calls "Above the taskbar (vertical doesn't fit in it)".
- R57. The Look is Default or one of the user's saved looks, each a tile with a sample pill in its own theme and colors. Default is Standard text (13 px semibold labels and 13.5 px bold values at 100 %) on pills that match the taskbar, with neutral meters. The text sizes and weights sit under "Text and shape"; changing one makes the look the overlay's own, keeping the rest.
- R58. Labels and values each have a text size, from 9 to 20 px at 100 % in steps of 0.5, and a weight: regular, semibold or bold.
- R59. The pills' background has an opacity from 0 % to 100 %, 100 % by default; below 30 %, the text gets a shadow so it stays readable on any wallpaper, unless the look's text effect (R93) says otherwise.
- R60. The pills' theme is Dark, Light, or Match taskbar, the default, which follows the mode of the taskbar the overlay sits on within a second of it changing. With several overlays, "Use on all overlays" gives every overlay this theme and nothing else.
- R61. Meters are neutral at normal by default, and take the warning and critical colors at those levels. Each of the three colors can be changed, and "Reset colors" brings them back. On light pills, the default warning and critical colors are drawn in their darker forms, `#9D5D00` and `#C42B1C`.
- R62. Labels and values each have a text color, Auto by default: today's colors on dark pills, and dark ones on light pills. A color with a contrast under 3:1 against its pill, taken as opaque, is drawn in its Auto color instead, and the window says so, so text never disappears when the pills change.

Your own looks

- R63. A look is the theme, the background opacity, the colors, and the text and shape: sizes, weights, font, corners, gap, text effect and units. It holds no position, size, layout or direction. It remembers the name of the saved look it came from until anything else changes it.
- R64. "Save as my look…" saves the current look under a name of 1 to 40 characters, unique whatever the case, and says what a look keeps: "Saves colors, theme, opacity, text and shape. Not position or layout." Saved looks sit beside Default; each one's "…" renames, exports or deletes it, and with several overlays uses it on all of them; renaming the one worn renames it in the settings too. Saving, renaming and deleting change the saved looks, not the overlay, so Ctrl+Z does not touch them; choosing a look is one step that Ctrl+Z undoes.
- R65. A look exports to a `.thermi-style` file that holds the look and its name, and no sensors, items, placement, language or paths, so it works on any PC.
- R66. A look file chosen with "Import…", dropped on the window, or its text pasted with Ctrl+V when no text field has the focus, applies to the overlay at once, as one step that Ctrl+Z undoes. A toast then says "Applied “Ocean” (not saved)" with "Save as my look" and Undo; saving asks for another name when that one is taken.
- R67. A look file that is broken, from a newer thermi, or with a value out of its range is refused whole with the reason, naming the field, and nothing changes. Unknown fields are ignored, and missing ones take their defaults.

Visibility and hotkeys

- R68. "When to show", in an overlay's Placement, shows it always (the default), hides it in full screen (games, videos), or shows it only in full screen. It follows a change within a second.
- R69. Four hotkeys, all off by default, are set in Settings: "Hide or show the overlays"; "Next look on all overlays", offered once a saved look exists; "Click-through on all overlays"; and "Reset min and max", offered once an item shows a minimum or maximum. The next look goes through the saved looks in name order, from the first when the first overlay wears none, and does nothing when there are none. A combination that another app holds is refused with that reason, also when it was written by hand in the file. Without the overlay running, the window says the hotkeys work only while it runs.
- R70. "Hide overlays", in thermi's menu, in the overlay's menu when there is one overlay, and on its hotkey, hides every overlay for now: it is a flag that is never saved, and every start of thermi begins without it. Showing them (the hotkey again, a click on thermi's icon, or "Show overlays") clears only that flag, so an overlay hidden on its own (R127) stays hidden. Hiding never touches tray icons.

Language

- R71. Every text a user reads comes from the translations: the window, the overlay's menu and messages, the tray tooltips and the default labels. Sensor and device names, units and messages from Windows itself are shown as they come; the command line, the log and the service stay in English. English and Spanish ship.
- R72. thermi uses Windows' display language when it has a translation for it, English otherwise. The window can choose another, which applies to the window and the overlay at once, and is undone like any change.
- R73. Numbers follow Windows' regional format, whatever the language.
- R74. Every translation has every text the English one has, and no others.
- R75. The window holds texts 40 % longer than English without cutting or overlapping them. With text at 200 % in Windows, nothing in the window is cut or overlaps: names wrap between words, a value that does not fit beside its name goes under it, and the chart's knobs fit their widest value, as "203 °F".

The tray

- R76. thermi's own icon always shows in the notification area while thermi runs. Its tooltip, which is also its name for Narrator, gives the hottest value with its level, then what is hidden and whether click-through is on, as "thermi · CPU 78 °C, warning · Top right hidden · click-through on", or "sensors stopped" in place of the value; it stops at Windows' limit of 127 characters, with "…" counted in.
- R77. Any item can also show as a tray icon of its own: its value as the overlay rounds it, without unit or thousands separator, with the decimal sign of R73, in up to 4 characters. A decimal is dropped when it does not fit, and 10,000 and over shows in thousands, rounded, as 12k for 12,345. Its tooltip is the item's label, value and unit. An item icon's digits take the taskbar's text color while its level is normal or it has no meter, and its level's color at warning and critical. A color under 3:1 against the taskbar is drawn in that level's default for the taskbar's mode, darker on a light taskbar. With the service stopped or its data stale, every item icon shows "–" in the text color, and every tooltip says which, in the words the window uses for R45.
- R79. Each tray icon keeps its identity across restarts, so Windows remembers where the user pinned it; new icons start in the hidden area, as Windows decides. thermi's own icon is thermi's mark: asleep, cool and with its eyes closed, while all is well; awake and warm at a warning; alarmed and hot at critical; a gray one-color glyph while the service is stopped or stale; and the one-color glyph in the system's text color under high contrast. The window's title row shows the mark in the same state. Right-clicking an item's icon opens its overlay's menu, and double-clicking it opens the window on that item.
- R80. Tray icons follow the taskbar's mode and scale, refresh with the overlay once a second, and are redrawn only when their text or color changes. They come back on their own when Explorer restarts, and an icon that Windows does not take, as at sign-in, is tried again until it shows; a change a busy Explorer drops is tried again at the next refresh, never by taking the icon off and adding it anew. Every icon keeps Windows' own tooltip, which pointing at it shows. With three item icons, the overlay stays within spec 001's budget.

More control

- R81. Temperatures show in °C (the default) or °F, set in Settings. Thresholds and the chart show in the chosen unit; in °F the knobs move in steps of 1 °F, and the file keeps °C rounded to a tenth.
- R82. "Show labels" and "Show units", under "Text and shape", can hide an overlay's labels or its units. Without labels, each pill keeps its items and shows their values alone; the labels are the overlay's, as its layout is, so no look carries them. Without units, values show without them, and labels stay as they are. The tooltip of thermi's icon follows the overlay; an item icon's tooltip keeps its unit.
- R83. An item's value can take a color of its own, in its "More options", over the look's value color, with the 3:1 rule of R62, and can go back to the look's.
- R84. Click-through, in an overlay's "Lock, click-through and OLED care", in thermi's menu and on its hotkey, never in the overlay's own menu, lets every click on the overlay pass to what is below.
- R85. Lock position, in the overlay's menu, its Placement and thermi's menu ("Lock all overlays" with several), keeps a drag from moving the overlay; clicks and double-clicks work as always.

Light and lasting

- R86. However many times the overlay paints, refreshes its tray icons, reloads the settings and sees the window open and close, its GDI and USER handles stay where they were, and its managed heap, after a full collection, stays within 1 MB.

Power features

- R87. An item can combine several sensors of one type, as their highest or average, or their sum for any type but temperature, picked with "Combine…" in its "More options", and add a fixed offset in its unit, from −20 to +20 for a temperature, a load or a duty, −2000 to +2000 for a fan, −500 to +500 for power, −10,000 to +10,000 for a clock, and −100 to +100 for memory. For a temperature, the offset is a difference: it is kept in °C and shown in °F as 9/5 of it, without the 32. A sensor without a value is left out; with none left, the item shows as missing.
- R88. An item shows its value now (the default), or its minimum, maximum or average since the overlay started or was last reset; missing values are left out. "Reset min and max", in the overlay's menu, thermi's menu and on its hotkey, starts them again.
- R89. An item can smooth its value as the average of its last 2 to 10 s, off by default; missing values are left out, and with none in the span the item shows as missing.
- R90. An item with a threshold can draw its meter on the overlay as a graph of its last minute, as tall as the value and 30 px wide at 100 %, colored by the same thresholds, with gaps where values were missing. Without it, the pill draws no meter, and the level shows on the value (R138).
- R91. An item can show 0, 1 or 2 decimals instead of its type's own, and the room it keeps (its widest value) follows.
- R92. An item shows always (the default), or only on alert, while its meter is at warning or critical; an item without a meter cannot be set so, and the window says why. A pill with nothing to show disappears, and the overlay closes the gap from its snapped edge. While the window is open, every item shows, so each can be selected.
- R93. "Text and shape" also chooses the font (Segoe UI Variable, the default; Bahnschrift; Consolas), the corners (round, the default, a radius of half the pill's height; soft, a quarter; square), the gap between pills (0 to 16 px, 8 by default), and the text effect: Auto (the shadow of R59), shadow, outline (1 px at 100 %, in the pill's color) or none.
- R94. There can be up to 4 overlays, each with its own items, placement, size, look, visibility, click-through, lock and OLED care. They are managed from the list: "New overlay" in the title row's "…" menu, and in each overlay's row menu Rename, Duplicate, "Move to display", "Merge into" another, Hide or Show, and Delete; each is one step that Ctrl+Z undoes. Each overlay's menu opens the window on it. The hotkeys, the language and the temperature unit belong to thermi; the next-look hotkey moves every overlay to the saved look after the first overlay's.
- R95. OLED care, off by default, moves an overlay 1 px every 3 minutes through four spots, the corners of a 1 px square, and back. On each axis, the square lies inward of a snapped edge, and up or to the left where there is none, as for a free position or a taskbar snap's horizontal axis at center. The offset is never written to the file.
- R96. A "Colorblind-safe" switch, under Colors, sets the meter colors to Okabe-Ito blue `#0072B2`, orange `#E69F00` and vermilion `#D55E00`, written as R61's three colors, and turning it off brings back the defaults. Under Windows' high contrast, the overlay draws its pills in the system's window color, and their text and borders in its window-text color; the level marks of R138 take the same two colors.

The window's layout

- R97. The window is a list beside a pane. The list holds each overlay as a row, each of its pills as a row under it, named as "CPU pill, 4 items", and each item under its pill; "Settings" is a row of its own below the list. The pane shows what is selected: an item's page, an overlay's page with its Appearance and Placement, or Settings.

- R177. thermi works on Windows 10 22H2, 64-bit, with what Windows 10 lacks falling back: the window's background is opaque in the system's colors where Mica is missing, corners stay square, Segoe UI stands in for Segoe UI Variable, and the overlay sits on Windows 10's taskbar as it does on Windows 11's.

- R179. Then every value that reads the CPU's temperature or clock shows a dashed 2 px line in the critical color over it, at any level, and its tooltip adds "Throttling: 3.1 GHz, under its 4.3 GHz base clock, at 92 °C." Nothing throttles while either reads nothing or the base clock is unknown. LibreHardwareMonitor exposes no thermal limit of a GPU on the recorded PCs (their RTX 5060 Ti reports clocks, loads, temperatures and power only), so a GPU shows none.
- R187. The tooltip of a critical value read from a CPU or a GPU adds what is busiest there now, as "Busiest now: chrome, 23 % of the CPU. Open Task Manager from the overlay's menu.": for a CPU, the process with the most processor time over the last 2 s, as a share of every logical processor; for a GPU, the one with the highest use of any engine of it, from Windows' GPU counters; processes of one name count as one, and the idle process never. Windows' counters are read only while such a value is critical, and Task Manager cannot be opened on one process, so the tooltip points to R184's entry.
- R188. "Copy as image", in every overlay's menu, puts a PNG of that overlay on the clipboard, with its values as it shows them now, at its scale and in its look, painted as `thermi preview` paints, without the window's marks.
- R189. "Fade near the pointer", an overlay's switch in "Lock, click-through and OLED care", off by default, makes the overlay fade as the pointer comes within 96 px of it, times its monitor's scale, from 100 % down to 25 % on it, and come back as it leaves; it still takes clicks (R157). It never fades while the window is open, while it is dragged, or under click-through. The pointer is checked ten times a second, only while the switch is on.
- R190. While thermi's driver may be missing (R16), a missing value of the CPU's temperature, power or clocks shows "Driver" in place of "–", translated, once per pill: its first such value says it, and the others show "–"; its tooltip says why and what to do (R139), and its double-click opens the window, whose driver bar offers the fix (R145).

## Design

**Two processes, one file** (`docs/adr/0005-settings-window-process.md`, `docs/adr/0007-settings-window-in-webview2-and-react.md`). `thermi settings` runs the window in its own process of the same `thermi.exe`, on an STA thread of its own (the overlay's entry point is async). The window is one WebView2 control filling a native frame; the page is a React app, and every rule lives in C#. The window reads the sensors from the pipe like the overlay does, and talks to the overlay through the settings file for settings and through window messages for the rest.

**The web app** lives in src/Thermi.Settings.Web, beside the .NET projects: React with TypeScript and Fluent UI React v9, built with Vite, with its own `package.json`, lockfile and README. npm installs run with the lockfile and without install scripts (`npm ci --ignore-scripts`). Fluent components are used only through a thin kit of thermi's own, and an ESLint rule forbids importing Fluent anywhere else; another forbids text literals in JSX, so every text the page shows comes from the translations through the bridge. The .NET build runs the web build and embeds its output in `thermi.exe`.

**The host** is in `src/Thermi/Ui`. Its frame is Windows' own: Mica, the caption buttons, snap layouts, the system menu and Win+arrows. The page draws the title row's content (the mark, the list's button when it folds, Undo, Redo and "…") in WebView2's non-client region support, which marks the rest of the row as caption, so Windows hit-tests it and the frame stays native. The embedded files are served from a virtual host name mapped to the program's resources; a strict Content Security Policy allows only that host, and the page loads nothing from the network. The host computes the first size and place (R116) from plain geometry in Core, remembers them per setup of monitors in `%LOCALAPPDATA%\thermi`, logs the first frame as before, and raises the window above thermi's overlays while it is active (R118).

**The bridge** is one typed interface between the page and C#: read the settings, apply an edit, undo, redo, the snapshots, the history, the texts, pick a sensor, the fan finder, the driver and the service. The C# interface is the source; its TypeScript is generated from it in the build, so a change that breaks either side fails it. The page holds no rule: `WindowEditor` and the window's other C# classes in `src/Thermi/Ui` decide, and keep their tests. Undo's step names ("Critical 84 → 85 °C") and its grouping of one control's changes within 1 s are the editor's.

**Writes.** Every writer (the window, and the overlay when dragged or changed from its menus) holds a named mutex for the settings file from the moment it re-reads the file until its write is moved into place. The work under it is synchronous, never across an `await`, and the mutex is released by the thread that took it. It is polled every 50 ms on the injected clock, never waited on with the real one. If the re-read under it finds the file locked, empty, cut short or missing, the writer releases it, waits and tries again, as a read does; a file still missing after that is written fresh. If it finds the file broken, it writes nothing, as spec 001 (R7) requires. A move into place that fails counts like a timeout. Waiting for it gives up after 2 s, and the write is tried again through the throttle until it lands; the overlay writes off its UI thread, so the overlay never waits. A mutex left behind by a writer that died is acquired by the next one. Every writer, on taking the mutex, deletes temporary files left beside the settings file, since no live writer can have one then. The writer applies its own change to what it just read, and writes under a temporary name of its own. Readers open the file sharing read, write and delete, so a reader never blocks a move into place.

**Reads.** A read that finds the file locked, empty, cut short or missing is retried every 50 ms for up to 500 ms. Only then is it a problem, or defaults, or a missing file to recreate.

**Throttle.** Window writes and overlay reloads both go through one throttle in Core: at most one every 100 ms, and the last value always goes out. The overlay's paints, its once-a-second refresh included, go through the throttle too. With `--trace`, both processes log on the same monotonic clock: the window logs each input, the overlay each paint. That is how R7 is measured, from input to paint.

**Item ids.** An item's id is kept in the file. Every id already in the file is reserved first, and going down the list the first item with an id keeps it. An item without one, or with one already taken, gets its metric or sensor id, or that id with the first free suffix (`cpu.temperature`, `cpu.temperature-2`). So every read of the same file gives the same unique ids, and the next write stores them. Default items, and so a reset, get ids the same way.

**Undo** keeps the window's changes as operations on item ids, each with what it found and what it left:

- **A field:** goes back only if it still holds what the window wrote.
- **An added item:** removed only if it is still as added.
- **A deleted item:** comes back at its old place, or at the end if that place is gone, unless an item with its id exists again.
- **A move:** goes back only if the item is still where it was moved.
- **An added or duplicated overlay:** removed only if it is still as added.
- **A deleted overlay:** comes back at its old place, or at the end, unless one of its item ids exists again.
- **A reset:** one step made of these operations, overlay by overlay, item by item and field by field.

Redo checks the same way. A step that cannot apply is skipped, and the window says so. The window remembers the content of its own last write, so the watcher event it causes is recognized and ignored. While a gesture is in progress, outside changes wait until it ends. A desktop gesture (R150) reaches the window as a message from the overlay naming its write, and the window takes the difference that write made as a step of its own history; the overlay keeps its own last gesture for 30 s, for the "Undo" of its menu, and undoes it the same way, through the file.

**History** lives in the overlay: the last ten minutes of each item's meter, 600 one-second slots per item, with gaps kept as gaps, so its memory is fixed. The window asks for it as it opens and gets one block per item; from then on it keeps its own from the pipe, and a minute for each catalog sensor's sparkline. The service keeps none, so its budget does not move, and the pipe protocol does not change.

**The window and the overlay** talk through the file for settings, and through window messages for what is not a setting, sent with `SendMessageTimeout` to the overlay process's one hidden top-level window, class `thermi-host`, found by that class. It owns the tray icons and receives `TaskbarCreated`, so it lives whatever shows; the overlays' own windows only draw. ADR 0005's two messages stay: "show" (the window opening) and "hotkey status", whose result says which hotkeys the overlay could not register, with a hash of the hotkeys it tried. The status's low four bits say which hotkey failed (hide, next look, click-through and reset min and max, in that order), and its upper 32 bits are the FNV-1a hash of the four combinations as written, joined by line breaks; both sides hash through one function in Core, an off hotkey being the empty string. The window asks once a second while the hotkeys show, and trusts an answer only when its hash matches the hotkeys in the settings it holds. The redesign adds, by a new ADR before its code: the overlay's history for the window, sent with `WM_COPYDATA` to the window's beacon; "select", from a click on a value or an overlay's edge to the window; "gesture", naming a desktop gesture's write; "edited", from the window to the overlay, naming the overlay and item being edited, for R104 and R128; and a second thermi opening the window instead of sending "show" (R151). The message ids come from `RegisterWindowMessage`, and each waits 500 ms for an answer.

**Bringing the window forward.** The window's process also makes a hidden top-level window of class `thermi-settings`, as the overlay does. A second `thermi settings` finds it with `FindWindow`, calls `AllowSetForegroundWindow` for its process, sends it the registered message `thermi-raise`, and exits; the window then brings itself to the front. `thermi settings --overlay <n>` opens the window on overlay n, counted from 1, or on the first when there is no overlay n, and the request carries n, 0 for none, and the item to select, if any, as `WM_COPYDATA` with the item's id in UTF-8, as `docs/adr/0009-overlay-and-window-messages.md` says. The overlay calls `AllowSetForegroundWindow` for any process before it starts one from a click, while it still holds the right the click gave it.

**Visibility.** An overlay shows unless its own Hide (`hidden`, saved), the "Hide overlays" flag (in the overlay's memory, never saved) or its "When to show" hides it, the window open or not: the window shows a hidden overlay in its own map and list. "When to show" asks Windows whether a full-screen app is in front (`SHQueryUserNotificationState`) and whether the foreground window covers the overlay's monitor, once a second on the existing tick; a game in exclusive full screen draws over every window, so there the overlay cannot show at all. The flag starts clear at every start. The window is open while its named mutex exists: the window acquires it with `WaitOne(0)`, an abandoned one counting as acquired, and the overlay only checks that it exists with `TryOpenExisting` on its tick, so a window that closes, or crashes, ends its marks and fades within a second. The hotkeys are registered by the overlay (`RegisterHotKey`), since it is the process that is always running, again whenever they change in the file.

**Hotkeys.** Which combinations are refused, and why, is Core's (R133): it takes the combination and, for AltGr, the characters the active keyboard layout types with Ctrl+Alt, which the window reads from Windows (`ToUnicodeEx`), so Core stays free of Windows.

**The driver hint** in R16, R22 and R145 is inferred from zeros, because a snapshot carries no driver state; adding it would change the pipe protocol. Installing the driver and starting the service from the window run elevated, behind one UAC prompt each, and so get an ADR before any code (R45, R145).

**The fan finder** treats every fan sensor as a candidate, the GPU's included, and reads `cpu.load` during the run. Its tests replay a series recorded on a real PC. `thermi-sensors --dump <file> --seconds <n>` records one snapshot per second, one line each, in the pipe's line format. The series starts 5 s before a CPU load, holds it for 30 s, as long as the finder can run, and runs 10 s after. The series recorded on the author's PC has fan-control software driving the fan, which barely answers: the case where nothing is picked. Closed, that software leaves the fan at its last speed, so the case where the board answers the load is a series derived from the real one, and a check by hand on a PC whose board drives the fan. `AGENTS.md` gives the load command. In a replay, the load starts at the first second whose CPU load passes 50 %.

**Settings file, version 2.** Fields are named, never inferred from a string's shape. The file holds `overlays`, a list of 1 to 4, and thermi's own fields: `hotkeys`, `language` and `temperature`. Each overlay holds its `name`, `items`, `snap` or `position`, `size`, `style`, `visibility`, `hidden`, `clickThrough`, `locked` and `oled`:

- `name`: the overlay's name, only when the user typed one (R102).
- `items`: each has an `id` and a `name`, then either `metric` (picked per machine, as today), `sensor` (a sensor id), or `sensors` (a list of ids of one type) with `combine` (`max`, `average` or `sum`); `offset`, `stat` (`now`, `min`, `max` or `average`), `smooth` (seconds, 0 for off), `decimals`, `graph` (true for a graph meter), `alertOnly` and `notify` are optional. An item made from a metric keeps it as `auto` when it names a sensor, so it can go back.
- `label` (optional): the label of a run of items. A sensor item gets its device kind's when it is added.
- `own` (optional): true when the item starts a pill of its own.
- `meter` (optional): `{ "metric": ... }` or `{ "sensor": ..., "auto": ... }`. `threshold` as today, in the meter's unit, RPM for a fan speed.
- `snap` (optional): `monitor` (left out for the primary monitor) and `spot`, one of `taskbar-left`, `taskbar-center`, `taskbar-right`, `top-left`, `top-right`, `bottom-left`, `bottom-right`. With both, `snap` wins. With neither, the overlay snaps to the right of the primary monitor's taskbar.
- `size` (optional): 0.75 to 2, 1 by default.
- `style` (optional), the look, every field optional:
  - `name`: the saved look it came from, left out once anything else changes it;
  - `layout`: `pills` (the default), `each` or `one`, and `orientation`: `horizontal` or `vertical`, which belong to the overlay and stay when a look is worn;
  - `preset`: `standard` (the default) or `custom`; `compact` and `large` still read, for files written by hand. Unless it is `custom`, it sets `label` and `value`, and those fields are ignored;
  - `label` and `value`: each a `size` and a `weight`;
  - `opacity`: `background` (0 to 1), and `overlay` (0.2 to 1), which the window no longer shows but hand edits and imported looks still set;
  - `pills`: `dark`, `light` or `system`, the default;
  - `colors`: `normal` (left out for neutral, the default), `warning` and `critical`, and `label` and `value` (left out for Auto), as `#RRGGBB`;
  - `units`: true (the default) or false;
  - `font`: `segoe`, `bahnschrift` or `consolas`; `corners`: `round`, `soft` or `square`; `gap`: 0 to 16; `effect`: `auto`, `shadow`, `outline` or `none`.
- `visibility` (optional): `always`, `hide-in-fullscreen` or `only-in-fullscreen`.
- `hidden` (optional, per overlay): true while it is hidden on its own.
- `tray` (optional, per item): true when the item has a tray icon of its own.
- `hotkeys` (optional): `toggle`, `nextStyle`, `clickThrough` and `resetMinMax`, each like `Ctrl+Alt+T`.
- `language` (optional): a language code, or left out to follow Windows.
- `temperature` (optional): `c` (the default) or `f`.
- `clickThrough`, `locked` and `oled` (optional, per overlay): true or false, false by default.
- `color` (optional, per item): the value's own color, as `#RRGGBB`.

The file keeps the word "style" where the window says "look", so version 2 keeps one set of names. The presets, at 100 %: labels are semibold and values bold; Standard is 13 and 13.5 px, as today; Compact, 11 and 12 px, and Large, 16 and 17 px, read from hand-written files only.

The pills' colors, as outer, border and unlit meter: dark is `#20201E`, `#31312F` and `#2E2E2C`, as today; light is `#F3F3F1`, `#DADAD8` and `#D5D5D3`. A pill is flat: its outer color inside its border, with no inner layer; where a rule names the pill's color (R62, the outline), it is the outer one. Auto text is `#A9A9A7` labels and `#EFEFEE` values on dark pills, as today, and `#5C5C5A` and `#1A1A1A` on light ones. A neutral meter, as in a graph, is the value's color at 35 %.

**A look file** is `{ "thermiStyle": 1, "style": { ... } }`, with the look's fields of `style` above and its `name`. A saved look is one such file in `%APPDATA%\thermi\styles`, named from its name with the characters Windows refuses replaced and a number added if the name is taken; the name inside is what counts. An export is the same file. Plain JSON, small enough to paste in a chat, readable by people and agents.

**The migration from version 1:**

- `sources` go to the items that show those metrics, and to the meters that name them, each keeping its metric as `auto`. A fan duty meter on a named fan becomes that fan's own duty; no meter is added where there was none.
- A source goes over as it is, even of the wrong type. An item whose sensor is not of its metric's type shows as missing, as in version 1, and the window marks it.
- A saved `position` stays a free position; without one, the overlay gets the default snap.
- The version 1 file becomes one overlay, without a name of its own, so it reads by where it sits (R102), and each item is named as its metric's default.
- An item just as thermi 0.1 made it by default, which 0.1 wrote to the file the first time it saved anything, becomes this version's default of its metric: the CPU fan metered by its own speed, with the calm lines of R27.
- An item that keeps something the user chose, as its sensor, but whose lines are still 0.1's defaults for its metric, takes this version's calm lines of R27 for its meter, as 90 and 95 °C for the CPU or none for a load. Lines the user moved stay.

A v0.1 build reading a version 2 file reports it as broken or as written by a newer thermi, depending on its fields, and never overwrites it (spec 001, R7). Version 2 has not shipped, so its new fields need no migration of their own; its recorded file and round-trip test hold every field, as ADR 0001 asks of every version.

**Files that change:**

- In `src/Thermi.Core`: the defaults (R27, the default look), the thresholds' push and units (R26, R110), the edits for names, Hide, moves, merges and desktop gestures, the search's synonyms, the top corners, whether an overlay fits beside the taskbar's apps, the hotkey refusals, the notices (Notify me, hidden, first run, click-through), the tray's creature state, tooltip and menus, the overlay's menu, the value tooltips, the percentages, and the window's first size and place, as plain geometry.
- In `src/Thermi`: the overlay draws flat pills with their level marks, the "Sensors stopped" pill, the fades of R104, the measure that puts an overlay off the taskbar when it does not fit and that the window's fit notice asks for (the app buttons' extent comes from UI Automation on the taskbar, read off the window's thread when the shell says a button may have come or gone, and every 30 s, leaving out thermi's own), the desktop gestures, its ten minutes of history and the new messages; the tray draws thermi's mark at the icon's size, from hand-placed pixels at 16 and 24 px and the vector above; `Program.cs` opens the window when thermi already runs.
- In `src/Thermi/Ui`: the WebView2 host, the bridge and the window's C# logic; the WPF views, `UseWPF` and their theme go.
- New: the web app in src/Thermi.Settings.Web, its Playwright tests with axe, and its CI job in `.github/workflows/ci.yml`; `scripts/check.ps1` runs its checks too.
- `Thermi.Ui.Tests` goes once the window is replaced; the tests of the window's C# logic that still hold move to `tests/Thermi.Windows.Tests`.
- `scripts/install.ps1` checks for the WebView2 runtime and installs it only when it is missing.
- Docs: `docs/QUICKSTART.md`, `docs/ARCHITECTURE.md`, the READMEs of `src/Thermi` and `src/Thermi.Core`, and `AGENTS.md`, whose map gains the web app and whose rule "only `src/Thermi/Ui` uses WPF" becomes "no WPF".

**Testing.** Acceptance proves behaviors and flows, not one step per requirement, and each behavior is tested once, at the cheapest layer that proves it: Core before the Windows tests before Playwright. Pure logic is tested only in Core, never again through the bridge or the page. Near-identical cases are one table-driven test, a `[Theory]` with a row per case or one Playwright test looping over a table: the defaults, the refused hotkeys, the menus' shapes, the window's sizes. No test asserts a UI text, the DOM's structure, or that something was called: texts are held by the translation rule and read by a person, and layout by one Playwright test over a matrix of sizes, text scales and the long pseudo-language, and a person's look. The page's tests run in Edge against the built page, with the C# side faked behind the bridge from the recorded snapshots, and find elements by role; axe runs in every state, in both themes and under forced colors; the focus contract (R123, R124) is the design prototype's 102 steps, ported into one test. A Playwright test is titled as one word in PascalCase, like the .NET tests, so `acceptance.json` names both alike.

**Test-first.** The first test of a behavior is written at the edge of its unit (a Core function or use case against a fake port, the bridge's contract, the page by role), red before the code, and it is that behavior's acceptance step. Inner unit tests are only for pure logic with real decisions (rules, parsing, calculations), as one table with a row per rule. A test written to drive a small step is deleted at the refactor when an edge test already covers it: removed, and mutation testing run again, it goes if no new mutant survives. A bug's reproduction is a new row in the table of the behavior's test when that test exists, not a new test. A characterization test or an oracle, such as a replayed recording kept only to pin today's behavior, is deleted when its spec passes. Mutation testing measures the tests' quality, Stryker.NET on `src/Thermi.Core` and StrykerJS on the web app's own logic; line and branch coverage stay only as a floor.

**Network and disk.** The service turns on the library's network and storage hardware beside the CPU, GPU, memory, motherboard and controllers, and the pipe carries their sensors as it carries the others. Core gains a sensor kind, `Throughput`, kept in bytes per second, and five metrics (`network.download`, `network.upload`, `disk.activity`, `disk.read`, `disk.write`) that `SensorMap` picks as it picks the others: an adapter by the data it has moved since the service started, from its received and sent counters, so it does not jump between adapters with each burst; a drive by its total activity over the last minute, picked again at most once a minute. Their tests read a new admin recording that holds two adapters and two drives, and join the existing tables: formatting, metric choice, the catalog, the thresholds and the new items, so they add no test of their own. Units follow Windows: bytes, as Task Manager shows a drive's rates and a file copy, and decimal multiples written KB/s, MB/s and GB/s.

**Battery.** The service turns on the library's battery hardware too. Its charge level, its rate and its estimated time remaining become the metrics `battery.charge`, `battery.rate` and `battery.time`; Core gains a sensor kind, `Duration`, for the time. A desktop's recording has no battery, so the existing recordings prove the group stays hidden; a laptop's recording proves the rest.

**Waking from sleep.** Core sees sleep as a gap in the snapshots' times on the injected clock, longer than the stale limit: the history marks the gap, so charts, minimums, maximums and averages skip it, and values stay missing until a snapshot newer than the wake arrives. The service and the overlay also listen for Windows' resume event, so the pipe reconnects and the library updates at once instead of at the next tick; a snap's monitor is looked up again when the display layout changes, as on any monitor change.

**Physical adapters.** The library names adapters but does not say which are physical. The service reads each adapter's interface type and Windows' hardware interface flag from IP Helper (`GetIfTable2`), matched by the interface id in the library's identifier for the adapter, and sends them with its sensors. Auto skips loopback and tunnel types and any adapter without the hardware flag, which takes in Hyper-V and WSL switches and most VPNs; names are not matched, because they are translated and chosen by vendors.

**CPU load as Task Manager shows it.** From Windows 8, Task Manager showed "% Processor Utility": busy time scaled by the clock against the base clock, so it read higher than busy time while cores boosted, held at 100. Windows 11 24H2's update of May 2025 moved every page of Task Manager to the standard formula, busy time over elapsed time across the logical processors, which is "% Processor Time", and kept the old value only as an optional "CPU Utility" column of Details. The library's CPU Total is that same busy time, so CPU load keeps reading it, with no counter of its own. Windows 10, out of support, and Windows 11 before that update still show Utility, and under boost thermi reads lower than they do. If T108's measurement finds CPU Total more than 3 points off, the service reads `\Processor Information(_Total)\% Processor Time` through the Windows performance counters (PDH, which needs no administrator rights) and sends it as a CPU sensor that `SensorMap` picks before CPU Total; that touches neither the driver nor administrator rights, so it needs no ADR.

**More from the overlay.** The taskbar's side is read from its window against its monitor, and a taskbar that overlaps the work area is one that hides; no position of Explorer's is guessed from its version or from other programs, so StartAllBack's and TranslucentTB's taskbars, which keep Windows' windows, need nothing of their own. The three Windows items are sensors of a device of their own, `/system/0`, that both processes add to every snapshot they read, under the hardware type `System` with the types `Duration`, `Address` (an IPv4 address held as its 32-bit number) and `Time` (seconds since midnight, local time): so the catalog, the items, the names and the history take them as any sensor, and the pipe does not change. The clock comes from the injected `TimeProvider`, the uptime from Windows' tick count, and the address from Windows' best route to the internet, read again when the network changes, never every second. The base clock is the processor's `~MHz` in the registry, read once at start, and the per-process counters are PDH's `\Process(*)\% Processor Time` and `\GPU Engine(*)\Utilization Percentage`, opened when a value turns critical and closed when none is; none needs administrator rights, so none needs an ADR. Bits are a view of an item's value, `bits` in the file, as `decimals` is; fading is the layered window's whole alpha (`fade` per overlay), so the overlay paints nothing again for it. The clipboard is reached through the host's environment, so tests never touch the real one.

**Later.** These are future specs, not this one's: FPS, and items fed from the CLI or MCP (weather, ping, AI usage, any outside value). Network speed per process is out of scope.

**Test budget.** This spec adds at most 80 unique tests, counting each `[Fact]`, each `[Theory]` and each Playwright test as one; the tests of the WPF window it deletes count against that. A ratchet in `scripts/check.ps1` holds the count to a committed baseline.

**Power features** are computed in Core, in the overlay's process: combining, the offset, min, max and average, smoothing and the graph's last minute come from each item's history; the service and the pipe do not change. Each overlay is a layered window of its own in the one overlay process, sharing the sensor client, the tray and the throttle.

**Clicks.** A layered window lets clicks through its fully transparent pixels, so every pill is painted at an alpha of at least 1/255, even at a 0 % background: the pill keeps catching clicks, and only click-through (`WS_EX_TRANSPARENT`) lets them pass.

**Leaks.** Every GDI object, icon and brush is released where it is made, through `using` or a `SafeHandle`; fonts are made once per look and released when it changes. A Windows test runs R86's rounds and compares `GetGuiResources` and the managed heap after the warm-up and at the end.

**Pills and looks** live in Core as data: the layout groups the items into pills from `own`, the labels and the layout, and the look resolves its preset into sizes and weights, and Auto or unreadable colors into readable ones. The painter only draws what it is given. An imported look is applied like any change, so the overlay stays the preview and Undo is the way back.

**The tray** lives in the overlay's process, with `Shell_NotifyIcon`: thermi's own icon, always, and one per item that asks for it. Each icon's GUID is made from the item's id, or "thermi" for its own icon, and the executable's path, because Windows ties a GUID to the path that first used it. Each add first deletes any icon left with the same GUID, as after a crash; an add that still fails is logged once and tried again every 5 s. Icons are `GetSystemMetricsForDpi(SM_CXSMICON)` square at the DPI of the primary monitor, checked at every refresh. An item's digits are Bahnschrift SemiBold Condensed, at the largest size that fits; which text, color and tooltip each icon shows, and which state thermi's mark is in, is decided in Core. The taskbar is taken as `#1C1C1C` with `#FFFFFF` text in dark mode, and `#EEEEEE` with `#1A1A1A` text in light mode; an accent-colored taskbar counts as dark. The light taskbar's level colors are `#1E7F3E`, `#8A5A00` and `#B42318`; the dark one's are the overlay's. Gray is `#8A8A8A` on a dark taskbar and `#6E6E6E` on a light one. thermi's mark is a capsule creature over a line: a gradient from cool `#3D5BFF` through `#8A4DFF`, with its eyes closed, when calm; `#FF9F1A` to `#FF7A1A`, eyes open, when warm; `#FF7A1A` to `#FF3B2F`, eyes wide, when hot; and its app form, cool to warm, eyes open, for the program's own icon.

**Translations** are .NET resource files in `src/Thermi.Core`, one per language, with English as the fallback, so both processes share them; the page gets them through the bridge. The window and the overlay read the language once at start and again when the setting changes. A repo rule checks that every translation has every key of the English one and no others. The long pseudo-language for R75 is not shipped: `thermi settings --pseudo` builds it from English when it starts.

**The look of the window** is Windows 11's, through Fluent UI React v9: Mica behind the title row and the list, the pane as a layer above, Segoe UI Variable, 4 px cards, 32 px controls, the system accent, light, dark and high contrast, and Fluent's motion, which reduced motion turns off.

**Rejected:** editing on the overlay itself, with flyouts anchored to its pills. It is small, sits over the taskbar and must stay light; precise controls, such as the chart, need room, and a flyout has no keyboard path to it. The overlay stays clickable to select, and the window edits. ADR 0007 records the rejected ways to build the window.
