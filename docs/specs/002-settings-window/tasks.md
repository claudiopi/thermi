## Decisions

- The series was recorded with fan-control software running, so its fan barely answers the load: the case where the finder must pick nothing and point to the catalog. A second one with that software closed was tried: the fan stayed at 546 RPM through the load, because the software leaves it at its last speed, so the positive case is covered by series derived from the real one, and by hand.
- The acceptance tests live in `Acceptance` folders, one class per area of the spec, so each block un-skips its own file.
- The whole file is `ThermiConfig` and one overlay is `OverlayConfig`, the spec's own words; fields whose default is not zero or false (size, gap, units, opacity) are always written, since 0 or false is a valid value for some.
- Version 2 reads strictly: an unknown choice, a snap without its spot, or 0 or more than 4 overlays marks the file broken; version 1, and a file without `version`, read as leniently as before, so a source written by hand as null is left out and its metric picked as if it had none.
- Item ids are based on `metric`, then `auto`, then `sensor`, then the first of `sensors`, so migrated items keep ids like `fan.cpu`.
- The throttle sends the first value at once and a waiting one on the timer; disposing it sends what waits, so the last change is never lost.
- Until B2, the overlay draws the first overlay. A sensor item shows its own sensor, with or without `auto`, so two items that keep the same metric as auto each show theirs, and so does a meter that names a sensor; a sensor of another type than its auto metric shows as that metric, missing, as version 1 showed it. Combined items show since T17.
- An edit gives `EditResult`: the new settings, or the settings it was given with a typed `Refusal`, an enum the translations task maps to one key per member; `Refusal.Invalid` also carries the English rule from `ConfigRules`, naming the field. A typed reason keeps Core free of the texts, and a repo rule can check that every member has a key.
- Undo is computed, not hand-written per edit: `ConfigDiff` compares the settings before and after an edit or a gesture, so every edit, the reset included, is undoable the same way. Overlays have no id: an overlay that keeps any item id is the same overlay, and the others pair up in order between those, so a reset changes the first overlay field by field.
- What an item shows (metric, sensor or sensors, combine, auto) is one field for undo, its meter with what needs it (threshold, graph and alert-only) is another, and so are an overlay's snap and position together: undoing half of one after a hand edit or a drag would leave a mix nobody chose, and undone one by one, a graph or alert-only would come back before its meter and the rules would refuse it. Every other field of an item, an overlay, its style and thermi is a field of its own. Each operation also passes `ConfigRules`, or it is skipped. `UndoRulesTests` sets each property of the settings' records in turn and fails when undo cannot take it back, so a new field cannot be forgotten in `ConfigFields`.
- An item's type comes from its metric or auto, else from any of its sensors the service reads. With none of them read, `ChangeSensor` refuses with `Refusal.TypeUnknown`, a new member with its texts: R18 wants the same type, and nothing says which that is.
- A sensor item's meter, when it follows its fan's duty, names that duty even when the board does not report it, so it shows as missing and comes alive if the board starts reporting it; a fan id that has no duty id at all turns the meter off.
- A new meter brings its type's default thresholds when the item had none, and turning the meter off also drops the threshold and alert-only. Threshold edits take values from 0 to 100 in the file's units; °F is the window's to convert.
- The library reports two sensors under one id (`/gpu-nvidia/0/load/3` is both "GPU Bus" and "GPU Memory" in the recording). The catalog lists both: the first keeps the id and each repeat is the id, `#` and its place among them (`SensorMap.Named` and `Find`), so "GPU Memory", the VRAM in use, can be an item too; the library's order of sensors is fixed, so the place is stable, and if a later library gives it an id of its own, the item shows as missing, as any renamed sensor does.
- The next-style hotkey's Core step is `OverlayEdits.NextStyle`, over a list of saved styles passed in, in case-insensitive ordinal name order; reading the saved styles from their folder is T16's.
- The zero rule is one function, `SensorMap.ZeroIsMissing` (a CPU temperature, power or clock at exactly zero), used by the metrics, sensor items and the catalog alike, as R16 asks: so a GPU's temperature or power at zero now shows 0 on the overlay, and a CPU clock at zero shows as missing.
- The catalog groups sensors by the device part of the library's id, not the device's name, so two GPUs of one model stay apart; devices come in the service's order and sensors by type within each. Search wants every typed word in the sensor's name, its device or its type; the type chips are a set, none meaning all. A sensor of a type thermi does not show has no row, since it has no unit to show.
- Why a sensor has no value is `NoValue`, an enum the translations map, as `Refusal` is. A fan at 0 RPM keeps its 0 beside "stopped or not connected", since that zero is real.
- The history keeps any id the window gives it (a sensor's catalog id or a metric), from fresh readings only: a ring of 600 one-second slots per id, so memory is fixed per id and the ids are only those the service reports. Seconds count from the last reading, rounded, so a service whose second drifts never makes a false gap; reads follow the clock, so an outage shows as empty seconds before the readings come back.
- The fan finder is `FanFinder`, a state machine the window feeds every new snapshot once (`Add`) and ticks often (`Tick`), and whose `Loading` says when the cores spin. The snapshot it starts with counts as a reading, the load starts on the first reading 3 s later, and the baseline is the readings of the 3 s up to it, so the replay's load lines up with the recorded one. The rule is first judged once 3 s of load can be averaged; `Tick` also ends a run at 30 s, so the load never outlives it for want of a reading.
- A gap is more than 2.5 s without a reading: one lost reading still leaves two in each 3 s average, and halfway between whole seconds, jitter never decides. It counts from the start, so a silent service also ends the baseline.
- When nothing is picked, a CPU load under 80 % (or unread) is said first, since then the fans had nothing to answer; then a fan that rose but not twice as much as another (`TwoRoseAlike`); else `NoFanRose`, whose translation carries the fan-control software and catalog hint. Core has no texts, so its tests check the outcome.
- With no fan outside the GPUs the finder cannot start; the driver hint shows when any CPU temperature reads zero, by the same zero rule.
- The finder's pick is applied by `ItemEdits.UseCpuFan`, through the gate like every edit, so it is one undoable step: the first item whose metric (or auto) is `fan.cpu` names the fan, metered by its own duty with `fan.cpu.duty` as auto; it keeps its thresholds only when it was already metered by a duty, since another meter's would color the duty on another scale. Without such an item, one made from `fan.cpu` is added at the start. The redesign changes this (R21, R110): the pick names the fan and keeps the item's meter, whatever it is, and no item is ever added; the CPU fan item starts metered by its own speed, with no lines.
- The finder's positive path is tested on series derived in the test from the recorded one (the fan spinning three times as fast, and one that answers at once), named as derived; A32 and A35 check them.
- The snap math is `Snaps`, over plain geometry the overlay reads from Windows (`Screen`: bounds, work area, scale, taskbar and notification area), so Core stays free of Windows. One margin of 8 px at 100 % keeps every spot off its edge, its end and the notification area alike.
- A taskbar counts only when it lies across its monitor and outside the work area: one on a side is too narrow for the overlay, and an auto-hidden one slides over the work area and back, which would make the overlay jump with it. A taskbar snap on a monitor without one shows at the bottom corner on its side, as a vertical overlay's does, so it stays on the monitor it names.
- A notification area that does not lie on its taskbar counts as not found, and keeps the reserve. The overlay finds it as `TrayNotifyWnd` in `Shell_TrayWnd`, and another taskbar's clock as `ClockButton` (Windows 10); Windows 11 draws the other taskbars' clock without a window of its own, so they keep the reserve.
- Until the overlay reads monitor EDIDs (T32), it names each monitor by its GDI device name (`\\.\DISPLAY2`), so a snap that names an EDID id falls back to the primary monitor, as R34 says of any monitor that is not there.
- The overlay works out where it goes at every paint (once a second, and when monitors, DPI or the taskbar change) and moves and resizes in the one `UpdateLayeredWindow` call, so a snapped edge never jumps as the overlay grows; during a drag it stays where the drag has it. A free position that touches no monitor goes to the default snap, as before.
- R33's rule is one function, `Snaps.Dragged`: from the press (where the cursor went down and where the overlay was) and the cursor now, it gives where the overlay goes once past the drag distance on either axis, or null for a click and on a locked overlay. The overlay moves itself under capture by it, instead of Windows' move loop, which would start at the press and swallow double-clicks, and on release `OverlayEdits.Release` gives the drop or null, so a click is never written. The drag distance is the system's, `SM_CXDRAG` and `SM_CYDRAG` at the overlay's DPI.
- The mouse is a state machine, `OverlayMouse`, from each message to what the overlay does, so a drag, a lost press and a double-click are tested without a window. The window class has `CS_DBLCLKS`, without which a double-click arrives as a second press, and a double-click runs the menu's "open settings" action, locked or not, which opens the file until T26 opens the window; A158 moved to the Windows tests to check both halves.
- With no monitor at all, as for a moment while the displays change, `Snaps.Locate` gives null and the overlay stays where it is; `Snaps.ScreenOf` gives null too.
- Renaming a pill follows the layout: the run of its label with pills (broken by `own`) or the single bar, the item alone with each. An item after them that showed their label without one of its own gets that label written, so it keeps showing it. "An item without a label takes the one before it" is one function, `OverlayLayout.RunLabels`, for the overlay, the edits and the tray.
- The pills are decided in `OverlayLayout`: `Build` shows a label where a run starts, where an item is `own` (pills only) or on every item (each), and `Groups` splits by the layout, so each and one leave `own` in the file for when pills come back.
- `OverlayLook.Of` turns a style into what is drawn: the preset's sizes and weights, the pills' colors, readable text colors and the effect (Auto is a shadow below 30 % background). It takes the taskbar's mode alone, which the overlay reads from `SystemUsesLightTheme` at every paint, so the apps' mode cannot reach the pills.
- Choosing a preset drops `label` and `value` from the file, since the preset ignores them; choosing custom, or changing a size or weight, starts from the text shown now. Every style edit goes through `StyleEdits.Restyle`, which forgets the saved style's name, so no edit can keep a name on a look that changed; one that leaves the look as it was, as choosing the preset it has, keeps it.
- An item's own color too close to its pill falls back to Auto, not to the style's value color, as R62 says of any text color; colors all back at their defaults leave the file.
- The painter draws from the look: where each pill goes (`OverlayLook.Arrange`, so a vertical overlay stacks), the pills', text and meter colors, and the sizes and weights (regular and semibold are Segoe UI Variable Text's faces, bold is Display drawn bold, as in v0.1). Opacity, the shadow, fonts and corners are B2's. A vertical overlay's height counts the gaps between its pills.
- A96 waits for the painter's opacity (B2) and A154 for the tray tooltips (T15), so T12 closes when they pass.
- The translations are .NET resource files, `src/Thermi.Core/Translations/Texts.resx` for English, built into Core, and `Texts.es.resx` beside it, built into a satellite assembly: MSBuild makes them with no package, a translator edits them as plain XML, in Visual Studio or in any translation tool that reads `.resx`, and both processes share them through Core.
- Every text is a member of an enum marked `[Translated]`, keyed `Enum.Member`: the reasons (`Refusal`, `NoValue`, `FanFinderRefusal`, `FanFinderOutcome`), the names (`SensorKind`, `SnapSpot`, `ServiceState`, `MetricLabel`) and `UiText` for the rest, so code can only ask for a text that exists. The repo rule checks both ways, every member with an English text and every English text with a member, and that each translation has the same keys and the same blanks.
- A language is matched by its code alone, so es-UY is Spanish. A language the file names that thermi lacks follows Windows, as no choice does; the window's `ThermiEdits.SetLanguage` refuses one with `Refusal.UnknownLanguage`, a new member with its texts.
- Numbers and texts are two inputs: `OverlayLayout.Build` takes the regional format (`CurrentCulture`) and, apart, the texts of the picked language (`CurrentUICulture` or the setting), so the language never changes a number. Without texts it is English, which keeps every existing caller and test as it was.
- Default labels are translated (Spanish shows RED for NET), but the edits still compare runs by the English default labels, so which items share a pill never depends on the language.
- `Texts.Pseudo` builds the pseudo-language in Core from English, accented, 40 % longer and in brackets so a cut text shows; reading `--pseudo` is the window's, in B3.
- °F changes only how temperatures show: `ReadingFormatter` takes the unit, `Temperatures` converts thresholds as temperatures and offsets as differences, the track runs 32 to 212 in steps of 1, and the file keeps °C rounded to a tenth, so a file reads the same whatever the unit.
- The visibility rule is `OverlayVisibility`, a state machine with no clock of its own: the overlay feeds it on its once-a-second tick whether a full-screen app covers each overlay's monitor, so "within a second" is the tick's and its tests step a fake clock a second a tick. Any change in those flags clears the override, since a full-screen app came or went; the flags are per overlay because only the overlay knows which monitor each one ended up on.
- `OverlayLayout.Build` leaves an alert-only item out while its meter is normal, which an empty overlay's tray icon needs (A179); the rest of R92, every item shown while the window is open and the edit that refuses an item without a meter, stays T17's (A170).
- The tray is decided whole by `TrayScene.Of`, from the settings, the snapshot and a `ServiceState` (running, stopped or stale), a new enum for `SensorClient` to give in T37; readings without a snapshot count as stale unless the service is known to be stopped, and then no icon shows a number.
- A tooltip line too long alone is cut within it to 127 characters with its "…"; then whole lines are kept while they fit with a last line of "…", so the cut is always seen, and an icon's text drops its decimal past four characters and then shows thousands, as 12k.
- An icon's id is a version 8 GUID from the SHA-256 of the executable's path in capitals, since Windows paths ignore case, and "thermi" or "item" and the item's id, so a hand-written item id "thermi" cannot take thermi's own icon.
- With nothing on any overlay, thermi's own tooltip is `UiText.NothingToShow` ("thermi: nothing to show now"), since an empty tooltip says nothing of what the icon is.
- thermi's own icon takes the color the first item at the worst level gets from its own overlay's style, with the taskbar fallback, since overlays may color levels differently.
- An overlay's name in the menus and notices is its own, or the picker's (`OverlayNames.Of`). A monitor's number counts from 1 in the order Windows gives the monitors and is left out with one monitor; an overlay at a free position reads "where it was dropped".
- `TrayRefresh` tells an icon to redraw only when its text or color changed, and apart those whose tooltip alone changed, so the overlay makes a new icon handle only when the icon looks different. A new icon size starts a new `TrayRefresh`, which draws every icon again, so `TrayIcons` removes then the icons that left the scene, which that refresh cannot know.
- A120's test is a repo rule, in `RepoRulesTests` beside the others `AGENTS.md` lists, not in `TranslationTests`. A114 and A127, the next saved style, pass on `OverlayEdits.NextStyle`, and T16 stays open for its other steps; A154 passes with the tray tooltips, so T12 waits only on A96.
- A saved style is a file in a folder the window passes to `SavedStyles` (`%APPDATA%\thermi\styles`; tests use one under their output), so Core needs no path of Windows and the tests touch no real profile; the name inside counts, and the file name replaces Windows' refused characters, trailing dots and spaces, and device names like CON, with a number for a taken one.
- Saving leaves the settings alone, so the overlay shows custom until the style is chosen: a name written outside undo would make a later undo leave that name on a look that is not the style.
- Renaming writes the new name to the overlays that chose the style and into every undo and redo step (`UndoHistory.RenameStyle`), so undoing the choice still takes back the whole look and neither undo nor redo brings back the old name; deleting leaves the settings, and `SavedStyles.Chosen` shows custom, as for any name no saved style has. `Chosen` wants the name and the look, so a style imported under a saved one's name but of another look shows as custom.
- A style file is checked by the settings' own style rules (`ConfigRules`), so a file and the settings never disagree on a range. It is refused as `BrokenStyle` (not JSON, a wrong type or a value out of range, the reason naming the field, as `style.label.size` or `$.style.gap`, or the line and place of a file cut short) or `NewerStyle`; importing is `StyleEdits.Import`, which chooses it as one undo step like a saved one.
- A combined item is added by `PowerEdits.AddCombined`, of two or more distinct sensors of one type, labeled from the first as a sensor item is, and is read from its sensors even when it keeps a metric as auto. A sum of temperatures is refused by the edits only, since the file alone does not know a sensor's type.
- The offset is added to every item's value; an item metered by itself meters that value, so its thresholds color what it shows. The file holds an item with a metric to its type's range and any other to the widest, ±10,000, since only the service knows a sensor's type.
- Min, max, average, smoothing and graphs come from `ItemHistory`, kept by item, one for all the overlays and one for the window, so deleting, merging or moving overlays or items keeps them, built on `SensorHistory` with a span of a minute, so gaps and late readings follow one rule. Min, max and average are of the smoothed values, which keeps out the one-second spikes the person smoothed away; before any value since the start or a reset they show the value now, so a reset never flashes a dash.
- Without a history, as in `thermi preview`, the tray before T24 passes one, or the stage's first second, items show the value now and a graph only that value.

- Decimals reach `ReadingFormatter.Format`, `Widest` and the tray icon, which drops them one at a time to fit its four characters; tray icons and tooltips follow the item's decimals and, through `TrayInput.Histories`, its stat and smoothing, so they show what the overlay shows.

A taskbar snap's vertical axis has no snapped edge, since it sits in the taskbar's middle, so it moves up.
- The colorblind-safe set is `StyleEdits.UseColorblindSafe`, which writes `StyleColors.ColorblindSafe` as the three meter colors and keeps the text colors; it goes through `Restyle`, so it forgets the saved style's name like any change of the look.

- A file cut short is one whose JSON ends before its root closes; only that, an empty, a locked or a missing file is retried, so a file broken by hand is reported at once instead of after 500 ms. Still empty after the retry, it reads as the defaults, as in version 1; still cut short, it is broken and never written over.
