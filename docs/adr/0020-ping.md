# 0020. The ping: one echo a second to the person's host, only while an item reads it

**Status**: Accepted

## Context

Players ask for their ping beside their FPS, and other overlays, as Kinetik Stats, show it. A ping is the round trip of an ICMP echo, so it is the first thing thermi sends that is not the update check, the driver's pinned installer or the machine MSI. `docs/adr/0008-updates.md` promises that nothing else ever leaves the PC, and the README's Privacy section says the update check is thermi's only connection. Either the ping goes, or those words change, and the rule that keeps them true must say exactly what is allowed.

Per-process traffic, which game talks to which server, would need ETW's network events in the service; it is out of scope.

## Decision

**No echo unless an item asks.** An item of any overlay, shown or hidden, that reads the ping (its metric `net.ping`, or its sensor, alone or combined, or what it warns by) is the only thing that starts echoes. With none, nothing is sent, and the catalog says the ping "pings only while an item of any overlay, shown or hidden, reads it".

**One host, the person's.** The settings hold one `pingHost` for every ping item, `1.1.1.1` (Cloudflare's resolver, near almost any PC) when none is set. The window's More options of a ping item edits it, as `thermi-cli edit` does, through `ThermiEdits.SetPingHost`: a DNS name or an IPv4 or IPv6 address of up to 253 characters, trimmed, or empty for the default; anything else is refused and changes nothing, and undo takes a change back. A name is looked up through Windows' resolver at each echo, as `ping.exe` does.

**One echo a second, from the user's process.** `PingReader` in `Thermi.App` sends one 32-byte echo with `System.Net.NetworkInformation.Ping` each second and waits a second at most, the name's lookup included, since a resolver that answers nothing would hold it for seconds. Each process that shows readings runs its own, through `PingFeed`, and follows the settings it holds: the overlay, the settings window while it is open, and `thermi-cli` while a call reads sensors, following the settings the call reads, once per line of a `watch`. So with the window open, two echoes a second go out. The `thermi-sensors` service never pings: it does not reference `Thermi.App`, and nothing running as SYSTEM sends a packet the person chose.

**Missing, never zero.** A reply is its round trip in whole milliseconds. No reply within the second, a host unreachable, a name that resolves to nothing, or no network up (when no echo is sent at all) reads as "–", and the catalog, the overlay's tooltip and an agent's `why` say which. Until an echo to the host ends, and once none has for two seconds, the ping reads as waiting, never as an older number that looks live; an error no ping names reads as unreachable, is logged, and the next second tries again. A call that reads once waits for its first echo's end, a second at most, so it says what the echo did. The reading is a sensor of a device of its own, Ping, listed under Network; changing the host starts its item's chart and statistics again.

**The rule.** `RepoRulesTests` lists the only files that open a connection or look a name up, each with why: the update check, the driver's and the machine MSI's downloads, the default route's socket, which sends nothing, the owner's test channel in `thermi-releases`, and `src/Thermi.App/Ping/IcmpEcho.cs`. A new one fails the check until it is listed and the README's Privacy section says so.

## Rejected

- **Pinging from the service**, which already runs all the time: an echo to a host any user of the PC names would go out as SYSTEM, the service would need the settings it never reads, and its memory budget (`docs/adr/0011-sensor-service-memory-budget.md`) has no room for a reason this small.
- **A TCP connect to a port instead of ICMP**, which crosses firewalls that drop echoes: it opens a connection to a service on the host, which looks like a scan to whoever runs it, and measures the host's accept queue as much as the path.
- **A default of no host**, so a ping item shows nothing until one is typed: one more step before the first value, for the one choice that is right for most.

## Consequences

- A person sees a ping as soon as they add the item, and their host, or Cloudflare by default, sees one small echo a second from the PC's address while an item of any overlay, shown or hidden, reads it.
- With the service stopped, the ping is the one live reading, and each echo's end is news of its own, so a ping item's graph and statistics follow its value.
- `thermi-cli` logs nothing of its echoes: the agents' log is what agents changed, and a line a call would push that out of the window's view.
- A host that drops echoes reads "no reply within a second", which is what Windows' `ping` says too; the release checks compare the two.
- The window open beside the overlay doubles the echoes to two a second. Sharing one reader across processes would need a channel between them that the ping alone does not justify.
- Agents that may change settings may set the host, as any other field; the agents' log shows the change.

## What it replaces in earlier ADRs

- `docs/adr/0008-updates.md` says nothing else ever leaves the PC. Instead, the ping's echoes do too, only while an item of any overlay, shown or hidden, reads it, to the host the person chose.
- `docs/adr/0010-driver-and-service-from-the-window.md` says a rule bans network APIs outside the updater and the driver's download. Instead, `RepoRulesTests` lists each file allowed to open a connection, the ping's among them.
