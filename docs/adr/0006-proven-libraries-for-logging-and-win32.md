# 0006. Proven libraries for logging and Win32 declarations

**Status**: Accepted

## Context

thermi grew three home-made logs: one for errors, one for `--trace`, and one the overlay's host takes so tests can replace it. Each rotates on its own, and the error log deletes the whole file once it passes 1 MB, so a burst of errors wipes what came before. The overlay also declares about 70 Win32 functions, 90 constants and 12 structures by hand; their layouts, such as the tray's `NOTIFYICONDATAW` with its union, are the code most likely to break silently, and every new Windows call adds more. Its three entry points read their arguments by hand, each its own way, and the agents' command line will add many more.

An audit of the rest found nothing else worth replacing: the settings file, the throttle, retries, undo, JSON, the tray, hotkeys, monitors, the painter, the theme, translations and the pipe are built on the standard .NET and Win32 pieces, or are small code a package would make costlier.

## Decision

- The overlay and the window log through `Microsoft.Extensions.Logging`'s `ILogger`, written by Serilog's file sink to one `thermi.log` shared by both processes, rolled at 1 MB and kept as three files. `--trace` is the debug level of the same log. Timestamps come from the injected `TimeProvider`, as all time does. Tests pass their own logger, so none can write to the user's log.
- The sensor service keeps no logging library: it runs as LocalSystem, where fewer dependencies is a security property, and writes its few errors to the Windows event log.
- Win32 declarations are generated by `Microsoft.Windows.CsWin32` from a `NativeMethods.txt` list of the APIs used, in the overlay and in the Windows tests. It runs only at build time and adds nothing at run time. Its version is pinned, since it has not reached 1.0.
- `thermi` and `thermi-sensors` read their arguments with System.CommandLine, parsed before anything runs, the overlay's mutex included; a word they do not know exits with 2. It is one Microsoft assembly with no dependencies, so the service takes it too.
- Full screen also counts what Windows says through `SHQueryUserNotificationState`: an exclusive Direct3D app or presentation mode hides the overlay on the foreground window's monitor, or on every monitor when that one cannot be told, since such an app may draw no window rectangle that covers it.

## Rejected

- Keeping the home-made logs: they already cost a lost log, and a fourth would come with the next process.
- `Microsoft.Extensions.Hosting` for the service: about twenty assemblies inside a LocalSystem process.

## Consequences

- One log, readable across restarts, that never loses its past to a burst.
- The overlay loads a few more small assemblies: measured, 1.5 MB more idle, about 33 of the 40 MB budget, and up to 34 ms more to start, which publishing both executables ReadyToRun for the PC's processor wins back (`docs/specs/002-settings-window/tasks.md`).
- A new Win32 call is one line in `NativeMethods.txt`; call sites use the generator's typed handles.
- A new command or option is declared once, with its help; `--help` answers for free.
- The full-screen rule stays in Core, which takes Windows' answer as an input, so its tests need no game running.
