# 0010. The window installs the driver and starts the sensor service

**Status**: Accepted, amended by `docs/adr/0016-admin-on-demand.md`

## Context

Spec 002 lets thermi fix the two things that most often stop its sensors (`docs/specs/002-settings-window/spec.md`): the `thermi-sensors` service stopped (R45, also "Start sensors" in thermi's menu), and the driver missing, seen as a CPU temperature, power or clock of exactly zero (R145). Each needs administrator rights, behind one UAC prompt. The window and the overlay run as the user and stay that way (`docs/adr/0003-sensor-service.md`). The driver is PawnIO, which thermi never bundles and installs only with its official installer (`docs/adr/0002-sensors.md`). Its name means nothing to most people, and in thermi's own words it would read as if thermi made it or vouched for it, so no text of thermi names it (R145).

## Decision

- **One elevated mode, run by a service.** `thermi elevated start-sensors` and `thermi elevated install-driver` are modes of the same `thermi.exe`, under Program Files. Nothing of thermi's is ever elevated by UAC: a process UAC starts takes its environment from the user's registry (`HKCU\Environment`), which any of their programs can write, and .NET loads a profiler (`CORECLR_ENABLE_PROFILING`, `CORECLR_PROFILER_PATH`), a startup hook or more assemblies (`DOTNET_ADDITIONAL_DEPS`) from it before Main, where no check of thermi's can run. Instead the install registers a second service, `thermi-elevated`: `thermi-sensors.exe --elevated`, as LocalSystem, started by hand, whose access list lets only administrators and SYSTEM start it and interactive users read its state. The window, or the overlay for "Start sensors", asks with `ShellExecuteEx` and the `runas` verb for Windows' own `sc.exe`, from the system folder Windows reports, to start that service with the verb as its one start argument: one UAC prompt. The service manager starts it with the machine's environment, which only administrators write, and it runs the elevated mode of the `thermi.exe` beside it with Windows' own folders alone, read from Windows, and a `PATH` of System32, so not even a profiler an administrator's monitoring agent set for every process loads into it. The mode takes its verb and nothing else; no path, URL, hash or setting comes from the caller, so whoever starts it cannot steer it, and an administrator who starts the service by hand gets the same. It shows no window, loads no WebView2, reads no settings and exits when done, ended with its children past 5 minutes. The service stops with the mode's exit code, which the caller reads from the service manager, off its UI thread: `sc.exe` exiting with "not installed" answers as a missing service, and one already running is waited for.
- **Start sensors** starts `thermi-sensors` through the service control manager and waits up to 10 s for it to run. The window still recovers by seeing the pipe come back (R45). A missing service has its own exit code, and the window says to reinstall thermi.
- **Install driver.** thermi's build holds one URL of the driver's official installer, on its project's own release page, with its size and SHA-256. The mode downloads it into a folder of its own, new for each install: made by the elevated mode in thermi's folder under Program Files, under a random name, with a protected access list that lets only administrators and SYSTEM write, and failing rather than reusing a folder that is there. Thermi's folder is only read: a real folder, owned by administrators, that nobody else may write. Nothing there is ever taken back, changed or followed by its path, so no user can swap a link in between, as one could in a folder of ProgramData that they made first; and no user can leave a DLL beside the installer, which Windows would load from its own folder as administrator. It checks that the installer is alone in its folder, then the size, then the SHA-256, then a valid Authenticode signature; trust rests on the hash, never on TLS. It keeps the file open, shared only for reading, runs it with the installer's own unattended switch, waits up to 2 minutes, and deletes the folder with it; an installer still running then is ended with its children, so nothing goes on as administrator while the window says it failed. It then restarts `thermi-sensors` so LibreHardwareMonitor opens the driver; an installer that answers 3010, installed but loaded only once Windows restarts, has its own exit code, the window asks for a restart, and the service is left alone.
- **No user's environment.** The mode runs as SYSTEM with the environment the service gave it, and the installer it runs gets the same with its own folder as `TEMP`. `scripts/install.ps1`, a developer's tool whose administrator step is a `pwsh` behind UAC, refuses to ask while the user's or the machine's environment names a variable that loads code into .NET; the elevated `pwsh` still reads the registry as the prompt closes, which no check before it sees, and the MSI of spec 004 replaces it.
- **Its log** is the Application event log, under the sensor service's source, which the install registers: why a download failed (an HTTP status, a proxy, TLS or a name that does not resolve, a timeout, a file too long) and each verb's exit code. A file in the user's folder would be written as administrator where the user can put a link, which sends the writes, and a roll's deletes, anywhere. It tells the window nothing on the way, only its exit code at the end: the window shows "Installing the driver…" with a progress bar that runs on its own until then (R145). Phases (downloading, installing, starting the sensors) would need a message from the elevated process to the window, one more thing to build and trust, for a wait of seconds. The window says the driver is installed only once a CPU temperature reads.
- **Never redistributed.** thermi never ships, mirrors or keeps the installer. It comes from the driver's own release at each install, as if the person had downloaded it. Once installed, the driver is the person's, in Installed apps under its own name; uninstalling thermi leaves it, since other programs use it too, and says so.
- **Never named.** The product's name lives only in the mode's constants and in docs. The UAC prompt names Windows' own tool, and the installer runs unattended, so its own windows never show. A check in `RepoRulesTests` fails on any translation that holds the name; the texts that hold it today change with spec 002.
- A refused prompt starts nothing, so the window can say that nothing changed (R145).

## Rejected

- `thermi.exe` itself behind `runas`, as this ADR first had it: UAC gives it the user's environment, and a profiler or hook set there runs as administrator before thermi can look. Re-starting itself with a clean environment comes too late, since the first process already loaded it.
- A small native helper, compiled ahead of time, behind `runas`, which starts the mode with a clean environment: it closes the same hole with a prompt naming thermi, but building it needs the C++ build tools on every PC that builds thermi.
- Running the driver's installer itself with `runas`: the prompt and the installer's windows name the product, the file waits in a folder the user can write until the prompt, and nothing restarts the service after.
- Letting interactive users start `thermi-sensors`, through its security descriptor: no prompt at all, but any user could start a service an administrator stopped on purpose, and spec 002 asks for the prompt.
- The service installing the driver, through ADR 0008's control codes: no prompt, so any user could add a kernel driver without an administrator's consent. And a stopped service, the other fix, cannot start itself.
- Shipping the installer in thermi's MSI: redistribution, and the driver's version would ride on thermi's releases.
- `winget`: missing from some editions of Windows, it shows its own window, and trust would rest on a community catalog instead of a hash in thermi's code.

## Consequences

- The UAC prompt names Windows' Service Control Manager tool, signed by Microsoft, rather than thermi; "Show more details" shows `sc.exe start thermi-elevated` and the verb.
- The real install, the folder and the service's run as SYSTEM are checked by hand; the tests run the environment the mode gets, the service's exit code, the answer the window reads from it, and the installer's process and its end past the wait as the user.
- A PC missing both fixes can see two prompts, one each. For an administrator each is one click; a standard user needs an administrator's password. The download runs as SYSTEM, so it uses the machine's proxy settings, not a person's.
- A new version of the driver is a thermi PR that changes the URL, size and hash together, after a person checks the release. If the pinned file leaves the release page, the install fails and says so; watch it.
- Anti-cheat software may refuse to run beside the driver (ADR 0002); "What is this?" says so before anyone installs it.
- The mode's steps sit behind interfaces for the service manager, the download and the installer's process, so tests cover a refused prompt, a missing service, a timeout, a wrong hash and a bad signature. The real install is checked by hand, on a PC without the driver.

## What it replaces in earlier ADRs

- `docs/adr/0002-sensors.md` says thermi detects whether PawnIO is installed and offers the official installer. Instead, a missing driver is inferred from zeros (spec 002), and thermi runs the official installer itself, unattended, behind one UAC prompt, from a URL and hash it pins.
- `docs/adr/0003-sensor-service.md` says the overlay never needs admin rights and `thermi-sensors` is the only elevated process. The overlay still never runs with them, but the window and the overlay may ask Windows, one fix at a time, to start the `thermi-elevated` service, which runs thermi's elevated mode as SYSTEM.
- `docs/adr/0008-updates.md` says the update is the only download, and bans network APIs outside the updater. Instead, the elevated driver install downloads one pinned file too, and the rule allows it there.
