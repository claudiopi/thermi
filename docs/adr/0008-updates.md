# 0008. Updates install beside the running version, from a signed manifest

**Status**: Accepted, amended by `docs/adr/0016-admin-on-demand.md` and `docs/adr/0020-ping.md`

## Context

thermi is installed by building the repo (`scripts/install.ps1`). A public release needs an installer that Windows and people trust, and updates that reach every PC without a UAC prompt, a visit to a website, or a gap in what the overlay shows: silent, as Chrome updates. Windows has no store in thermi's way, so everything travels over the air, the service's C# included. The only process that can change Program Files without a prompt is the `thermi-sensors` service, which runs as LocalSystem (`docs/adr/0003-sensor-service.md`). Making it the updater turns it from a process that only publishes readings into one that downloads and runs code as SYSTEM: the most dangerous thing thermi does. Anyone who can steer what it installs owns the PC.

Mi Basket's live update showed what an owner needs on top of a safe download: channels, a gradual rollout that identifies no one, levers to roll back or stop a release within a minute, and a rollback that happens by itself on the device. It also showed the trap: a health check that runs on a clock while the app cannot run (its BUG-509) reverts good releases.

## Decision

**Side by side.** Each version lives whole in a folder of its own, `C:\Program Files\thermi\<version>\`, self-contained, with the .NET runtime it was tested with. Going to a version never changes a file a running process uses, and the previous version's folder stays, so going back is the same switch the other way and downloads nothing.

**What points at a version.** The services' image paths name their version's folder, and a switch changes them with the service manager's own call, one write that either happened or did not. People and Windows start the overlay by a path that must never change, since the Run value, the Start menu, the command line and the tray icons' registration name it: `C:\Program Files\thermi\thermi.exe` and `thermi-sensors.exe` are .NET's own app host, a 200 KB file the SDK builds, written by the build to start `<version>\thermi.dll` rather than a program beside it. Each version carries its own in `<version>\launchers\`. Measured on Windows 11: a process started before the launcher is renamed aside and replaced keeps loading from its own version's folder, one started after runs the new version, and a process whose executable was renamed still updates, removes and adds its tray icons.

**What travels** is one zip per processor holding a version's folder. The service downloads it, checks it, unpacks it into a new folder under a random name and renames that to the version once every check passed. Nothing running changes until the switch.

**The switch** happens at a quiet moment: when the service starts with a version ready, as after a restart of Windows, or when an overlay tells the service its session is quiet: no settings window and no drag, and either three minutes without input, the session locked, or every overlay hidden. A release marked urgent switches the service at once, and each overlay as soon as its window is closed and no drag is under way. The service writes the switch down in its state file, then starts a watchdog and lets it act: its own `thermi-sensors.exe --switch` for a step forward, and for a step back the version it goes back to, which ran here before. The watchdog holds a lock file in `update\`, which only administrators change, while it acts, so no user can make the service believe a switch is under way. The watchdog stops the service, points it at the new version, starts it and points it back at once, so a power cut or a crash of the watchdog leaves Windows starting the old version; it then polls the pipe. When the new version serves a snapshot, the watchdog points both services at it for good, replaces the launchers and marks the switch done; when it does not, it starts the old version again and marks the new one failed, unless a program no administrator started held the pipe, which proves nothing of the version: the switch is then only dropped and tried later. A service that starts and finds a switch written down but not done finishes it or undoes it, and at every start it puts back the launchers of the version it is, if they are missing or another's.

**The overlays** see the new version installed in the state file and switch themselves at their own quiet moment: one removes its tray icons, hides its overlays, lets go of its single-instance mutex and starts the fixed `thermi.exe`, once it is the new version's launcher, whose path the tray icons' ids are tied to. When the new one's host window appears, the old one exits; when it does not, the old one comes back and does not try that version again in its session, which its log says. Whoever is idle sees nothing, and a person who is not sees the overlay redraw.

**Health and rollback** are judged by what happens, never by wall time: the watchdog counts its polls of the pipe and an overlay its own ticks, and neither runs while Windows sleeps, so a version is never failed for the time the PC was asleep. Time only ever ends a probation. The new service passes when it serves a snapshot within 120 polls, one a second; for ten minutes after its switch, a second run of it that ended without stopping sends the PC back. A failed version is never tried again on that PC; the next one is. A start Windows gives up on, error 1053, is a cut too; it, a start refused at shutdown and a pipe another program held each keep the version ready but hold every switch forward for a check's interval, so the old service's own start, a quiet session or an urgent check do not try it again under the same load or the same program. A rollback that is cut twice is dropped, and never counts against the version it went back to. No user can mark a version failed for the PC through thermi: an overlay that cannot switch only stays where it is. A user who floods the sensors' pipe through a switch's probation could keep the new service from serving the watchdog, which fails that one version on that PC; the next release is tried, so the worst is one update withheld from it, accepted against a second, private proof of health.

**The manifest** is one file per channel, `stable.json` and `beta.json`, at `https://updates.thermi.app/v1/`, on Cloudflare R2 behind a custom domain: served with a 60 s cache, so a lever reaches every PC within a minute of its edge, while the zips are immutable and cached for a year. Each file is an envelope holding the manifest's exact bytes and an ECDSA P-256 signature of them. A manifest says: its channel, a sequence number that only grows, when it expires, the version, per processor the zip's URL, size and SHA-256, the rollout percentage, whether it is urgent, whether the channel is turned off, and the versions withdrawn. A manifest expires 45 days after it was signed, so a replayed one cannot keep a PC quiet for longer than that: an expired manifest is not a successful check, and About says so after 14 days without one. The service holds two public keys built in: the release key, and a backup the owner keeps offline. A manifest signed by the backup key may also revoke the release key, which it names by its SHA-256, so a replayed revocation never touches a newer key, and set the sequence back; a manifest whose expiry lies further ahead than 45 days and a day of clock slack is refused, which is how a lost or stolen release key is replaced, through a release signed by the backup key that carries a new one. The .NET class library verifies it; the service gains no package.

**What binds the zip to its version.** After unpacking, the version the new `thermi-sensors.dll` and `thermi.dll` carry must be the manifest's. In a release build, a Windows catalog in the zip, signed by thermi's Authenticode identity, lists the SHA-256 of every file the zip holds, the `.json` files the .NET host reads included, and the service checks the catalog's signature and that every file is in it before the version can run. So a stolen manifest key alone can neither run code nor relabel an older release.

**Levers.** `scripts/updates.ps1` publishes a build to a channel, promotes beta's version to stable without rebuilding, rolls a channel back, turns it off, signs it again before it expires and shows the channels. Each is a new signed manifest with the next sequence. `publish` and `promote` refuse a version below the channel's, and a version reaching stable reaches beta too when beta is behind. `rollback` withdraws the channel's version and offers the one before it; a PC that runs a withdrawn version goes back to the previous version it kept, and a PC without it stays. `disable` keeps every PC where it is. Each publish runs in a GitHub environment that waits for the owner's approval, a merge to main included; a monthly run, approved too, signs the channels again.

**Rollout.** Each PC draws a number from 0 to 99 once and keeps it; it takes a version when its number is below the manifest's percentage, so raising it adds PCs and never reshuffles them. Nothing about the PC is sent, so the owner learns of trouble only from people, as with any release; a small percentage still limits how many PCs a bad release reaches before then.

**Channels and policy.** Stable is the default. An administrator sets `UpdateChannel` = `beta`, or `Updates` = 0 to turn updates off, under `HKLM\SOFTWARE\Policies\thermi`, the place Windows' policies and Intune write. The window shows them and changes neither: a person who wants the beta or no updates is an administrator anyway, and a switch in the window would need a prompt and a second path to trust.

**The service's updater** lives in `src/Thermi.Sensors.Windows/Updates`, apart from the sensors' code, and its decisions in `src/Thermi.Core/Updates`, tested on a fake clock. It checks a minute after it starts, every four hours, and after Windows resumes when the last check is older than that. It downloads with `HttpClient`, as the driver's install does (`docs/adr/0010-driver-and-service-from-the-window.md`); on a metered network it checks but downloads only an urgent version, and it downloads nothing without three times the zip's size free. It verifies in order, before anything installed changes: the envelope's size and signature, the channel, the sequence and the expiry, the version rules, the zip's size and the SHA-256 of the file it holds open, each entry's path, then the versions inside and, in a release build, the catalog. It writes its state to a new file and moves it into place. It keeps the installed, the previous and the ready version, and the one the launcher at the top still starts, and deletes any other: it first renames the folder aside, which Windows refuses while any process runs from it, and deletes only what it could rename. A rename that an antivirus holds back is tried at the next prune, and a launcher it holds at the next check: once a version passed, nothing the watchdog then fails to write is held against it. The state and the marks in `update\` are files no user may open, so none can hold one against a write; the overlay and About read the highest numbered of its copies, `status-<n>.json`.

**Commands** reach the service only as user-defined service control codes, integers Windows carries: 128, "this session is quiet, switch now if a version is ready"; 129, About opened, "check now"; and 130, About's Restart to update, "switch now". Interactive users get query and user-defined control on the service, never its configuration; 128 and 129 are each acted on at most once a minute, and 130 has one restart waiting at a time, so the worst any code does is one more anonymous check a minute or a switch early to a version that passed every check. The service still never reads its pipe, nor any file a user can write. Its state, `C:\Program Files\thermi\update\state.json`, is written only by it and opened by no user: the overlay and the window read the highest numbered of its copies, `update\status-<n>.json`, each a new file, so a user holding one open keeps no one's view old.

**Threat model.**

| Threat | What stops it |
| --- | --- |
| A tampered manifest or zip, at R2, at Cloudflare's edge or on the wire | The envelope's signature by a key built into the service, then the size and SHA-256 it signs, checked on the file held open; in a release build, the signed catalog over every file. |
| A stolen manifest key | Alone it cannot run code or relabel an old release: the catalog needs thermi's Authenticode certificate, and the versions inside must match. It can withhold updates, or withdraw the version PCs run, which sends them one version back and counts the withdrawn one as failed there, until the backup key revokes it; the revocation stays in every manifest after it. If SignPath's certificate turns out to be shared by its projects, the catalog proves only that SignPath signed, and this key alone then runs code: docs/RELEASES.md has the owner ask. |
| Replay of an old manifest, or a downgrade | The sequence never goes back; a version is never taken at or below the installed one; a replayed manifest expires within 45 days, and About says so after 14. A withdrawal sends a PC only to the previous version it ran itself and kept. |
| A man in the middle, DNS spoofing, a hostile proxy | TLS keeps a check private, but trust never rests on it: a man in the middle can only withhold an update or serve bytes the checks refuse. Sizes are capped before reading: 64 KB for an envelope, the signed size for a zip. |
| A zip that writes outside its folder | Every entry's path is resolved and must stay inside the new folder; absolute paths, `..` and links are refused. |
| A non-admin user steering the update | Everything lives under `C:\Program Files\thermi`, which the installer creates and only administrators, SYSTEM and Windows' installer may change, so no user can make a folder or link there first; its owner and access are checked before each use, as for the driver's folder, the watchdog's included. The one control code only moves a switch earlier. A user who takes the pipe's name as a new version starts only puts the switch off, and the watchdog lets the pipe's server identify it, never act as it. |
| A broken release | Beta first, then a gradual rollout; the watchdog rolls back a version that does not serve, by counting what happens; a power cut mid-switch starts the old version; `rollback` and `disable` reach every PC within a minute of the edge. |
| Theft through the release pipeline | Every publish waits for the owner's approval; Authenticode keys never leave SignPath's HSM. A build missing a public value fails rather than ship one that never updates or takes any catalog. The levers open each channel's history only when one of thermi's keys signed it, so whoever can write the bucket cannot have a lever sign what they planted, and a run that would sign over another's upload is refused. |
| Code or UI from the network at run time | None: the update is the only download beside the driver's pinned installer, and the window shows no text from the manifest. |

**Privacy.** A check is one anonymous HTTPS GET of the channel's manifest, no query, no cookie, no identifier, `thermi` as the whole User-Agent. Cloudflare sees the PC's IP address, as any download does. Nothing else ever leaves the PC but the ping an item asks for (`docs/adr/0020-ping.md`): thermi learns nothing about who updated, and a failure stays in the PC's event log.

**The installer** is a WiX MSI per processor, per machine: the Windows Installer service runs it as SYSTEM, so no .NET of thermi's runs elevated from a user's environment (`docs/adr/0010-driver-and-service-from-the-window.md`), and it is the format winget, Intune and administrators expect. It owns only a bootstrap, the version it ships, and has that version's own `thermi-sensors.exe` adopt it into the layout an update keeps, so a repair never fights the updater; the updater keeps the version Installed apps shows. Starting at sign-in is per person: Active Setup turns it on once in each profile, as the overlay's first start used to, so a machine-wide install through Intune or winget reaches every user. Uninstalling removes the whole of `C:\Program Files\thermi`. `scripts/install.ps1` builds the same layout unsigned, with updates compiled off, or on for a test against a manifest address and key it is given.

## Rejected

- **An MSI for every update**, run by the service with `msiexec`, as this ADR first had it: the install replaces files in use, so every overlay must close, and the service must start each user's overlay again with `WTSQueryUserToken`, which needs `SeTcbPrivilege`, a power ADR 0003 took from it. The update would show as thermi vanishing for seconds, and a rollback is a second install that can fail too.
- **A small launcher of our own** at the fixed path, starting `<version>\thermi.exe`: the tray icons would register from each version's path, and Windows keeps a person's choice to show an icon only while that path holds; a native launcher needs the C++ build tools, and one on .NET Framework a second runtime.
- **A junction**, `current`, switched to each version: .NET's host does not resolve it, so a running process would load its later assemblies from the next version.
- **Users reporting a failed overlay to roll the PC back**: any user could then keep a security release off the PC for good.
- **A handover with no redraw**, two overlays shown at once: Windows lets one process hold a tray icon's id, and the switch happens while the person is away.
- **Velopack**: it installs per user into `%LOCALAPPDATA%` and has no service support; a LocalSystem binary in a folder the user can write is what ADR 0003 forbids.
- **MSIX**: a packaged service needs a restricted capability, App Installer updates per user, and LibreHardwareMonitor's driver access from inside a package is unproven.
- **A second service only for updates**: whatever writes Program Files as SYSTEM can do anything, so splitting it buys little isolation for a second service to keep in step.
- **Only the page over the air**, as Mi Basket does for its web bundle: the page decides nothing and most fixes touch C# too.
- **Release notes in the manifest**: the window would show text from the network, for little; the release page has them.
- **A pinned version per PC for administrators**: the channel and turning updates off cover thermi's people; an administrator who needs a pin installs that MSI with updates off.
- **BITS**: it resumes and knows metered networks, but needs its COM interfaces in the service for a download a later check can simply repeat.

## Consequences

- The service's job grows: it downloads, unpacks and switches itself through a watchdog. Its memory at rest stays in ADR 0011's budget, since the updater runs for seconds every four hours.
- Two versions are kept on disk, about 70 MB each, since each carries its runtime. A .NET security release is a thermi release.
- A breaking change to the pipe takes a new pipe name, served beside the old one for a release, since for a while a new service serves an old overlay; a test holds the pipe's lines to a golden file, so such a change is never made by accident.
- A change to the settings file's format keeps a copy of the file in the earlier format, and a rollback reads it: edits made in the newer format do not survive a rollback across it.
- The owner signs the channels again at least every 45 days, through an approved monthly run.
- The release depends on R2, SignPath and a GitHub environment holding the manifest key. If any is gone, PCs stay on what they run and people can install the MSI by hand.

## What it replaces in earlier ADRs

- `docs/adr/0001-architecture.md` says the host accepts no commands beyond sending readings. Instead, it also accepts the update's control code, an integer from the service control manager; its pipe is still write-only.
- `docs/adr/0003-sensor-service.md` rejects a service the overlay sends commands to, and says installing or updating needs admin rights once. Instead, interactive users may send the one code, and updates after the first install need no admin rights. The service keeps its one privilege.
- `docs/adr/0006-proven-libraries-for-logging-and-win32.md` measured a framework-dependent install with a shared runtime. Instead, thermi is published self-contained, a version per folder.
- `docs/adr/0010-driver-and-service-from-the-window.md` says the MSI of spec 004 replaces `scripts/install.ps1`'s elevated `pwsh`. It does for people; `scripts/install.ps1` stays the developers' way to install the same layout.
