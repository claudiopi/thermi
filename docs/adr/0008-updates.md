# 0008. Updates install beside the running version, from a signed manifest

**Status**: Accepted

## Context

thermi is installed by building the repo (`scripts/install.ps1`). A public release needs an installer that Windows and people trust, and updates that reach every PC without a UAC prompt, a visit to a website, or a gap in what the overlay shows: silent, as Chrome updates. Windows has no store in thermi's way, so everything travels over the air, the service's C# included. The only process that can change Program Files without a prompt is the `thermi-sensors` service, which runs as LocalSystem (`docs/adr/0003-sensor-service.md`). Making it the updater turns it from a process that only publishes readings into one that downloads and runs code as SYSTEM: the most dangerous thing thermi does. Anyone who can steer what it installs owns the PC.

Mi Basket's live update showed what an owner needs on top of a safe download: channels, a gradual rollout that identifies no one, levers to roll back or stop a release within a minute, and a rollback that happens by itself on the device. It also showed the trap: a health check that runs on a clock while the app cannot run (its BUG-509) reverts good releases.

## Decision

**Side by side, behind a fixed executable.** Each version lives whole in a folder of its own, `C:\Program Files\thermi\<version>\`, self-contained, with the .NET runtime it was tested with. At the top of `C:\Program Files\thermi` sit `thermi.exe` and `thermi-sensors.exe`: .NET's own app host, a 200 KB launcher the SDK builds, written by the build to start the app in `<version>\` rather than beside it. Every process of thermi's runs from those fixed paths, so the user's Run value, the service's image path, the Start menu, Task Manager, the command line and the tray icons' registrations (which Windows ties to an executable's path) never change. Moving to a version is replacing those two small files: a running executable can be renamed, so the old ones are moved aside and the new ones put in place, and a running process keeps its own version's folder, from which it goes on loading. Measured: a process started before the swap keeps loading its assemblies from its own folder, and one started after it runs the new version.

**What travels** is one zip per processor holding the version's folder, the two launchers for it included; the update downloads it, checks it, and unpacks it into a new folder beside the running one. Nothing running changes until the switch, and the previous version's folder stays for a rollback, so going back is the same switch the other way and downloads nothing.

**The switch** waits for a quiet moment: when the service starts with a version ready, as after a restart of Windows, or when an overlay tells the service its session is quiet: no settings window open and no drag, and either three minutes without input, the session locked, or every overlay hidden. Then the service swaps the launchers, starts its old version's own `thermi-sensors.exe` beside it as a watchdog, and stops; the watchdog starts the service again, now the new version, and waits for it to serve a snapshot on its pipe. Each overlay sees the new version installed and switches itself at its own quiet moment: it lets go of its single-instance mutex and starts the fixed `thermi.exe`, which shows the same overlays in the same places, and the old one exits once the new one has shown them, so the overlays never blink; the tray icons, which Windows lets only one process hold, go and come back in the same second. A release marked urgent does not wait for the user's idle time, only for the settings window and any drag.

**Health and rollback.** The watchdog judges the new service by what it does, never by wall time: it counts polls of the pipe, which do not happen while Windows sleeps, and the new version passes when it serves one snapshot within 120 of them. It fails when it does not start, does not serve, or the service stops with an error twice within ten minutes of the switch. An overlay judges its successor the same way, by its own once-a-second ticks: it passes when the new one shows its overlays within 60, and fails when it exits first or never shows them. Either failure swaps the launchers back, restarts the service as the previous version, and marks the new one failed on this PC; an overlay reports its failure to the service with a control code, so the whole PC goes back together, and the overlay that reported it stays where it was meanwhile. A failed version is never tried again; the next one is.

**The manifest** is one file per channel, `stable.json` and `beta.json`, at `https://updates.thermi.app/v1/`, on Cloudflare R2 behind a custom domain: served with a 60 s cache, so a lever reaches every PC within a minute of its edge, while the zips are immutable and cached for a year. Each file is an envelope holding the manifest's exact bytes and an ECDSA P-256 signature of them. A manifest says: its channel, a sequence number that only grows, the version, per processor the zip's URL, size and SHA-256, the rollout percentage, whether it is urgent, whether the channel is turned off, and the versions withdrawn. The service holds two public keys built in: the release key, and an offline backup that the owner keeps to replace it. The .NET class library verifies it; the service gains no package.

**Levers.** A command-line tool, `scripts/updates.ps1`, publishes a build to a channel, promotes beta's version to stable without rebuilding, rolls a channel back, turns it off and shows the channels. Each is a new signed manifest with the next sequence number. `publish` and `promote` refuse a version below the channel's, and publishing to stable also brings beta up to it when beta is behind. `rollback` withdraws the channel's version and offers the one before it; a PC that runs a withdrawn version goes back to the previous version it keeps, and a PC without it stays. `disable` keeps every PC where it is. A merge to main publishes to beta from CI; stable is the owner's command.

**Rollout.** Each PC draws a number from 0 to 99 once and keeps it; it takes a version when its number is below the manifest's percentage, so raising it adds PCs and never reshuffles them. Nothing about the PC is sent.

**Channels and policy.** Stable is the default. An administrator sets `UpdateChannel` = `beta`, or `Updates` = 0 to turn updates off, under `HKLM\SOFTWARE\Policies\thermi`, the place Windows' policies and Intune write. The window shows them and changes neither: a person who wants the beta or no updates is an administrator anyway, and a switch in the window would need a prompt and a second path to trust.

**The service's updater** lives in `src/Thermi.SensorHost/Updates`, apart from the sensors' code, and its decisions (when to check, what to take, when to switch, what counts as healthy, what to delete) in `src/Thermi.Core/Updates`, tested on a fake clock. It checks a minute after it starts, every four hours, and after Windows resumes when the last check is older than that. It downloads with `HttpClient`, as the driver's install does (`docs/adr/0010-driver-and-service-from-the-window.md`), and on a metered network it checks but downloads only an urgent version. It verifies in order, before anything installed changes: the envelope's signature by a built-in key, the channel and the sequence, the version rules, the size, the SHA-256 of the file it holds open, then, in a release build, Authenticode on every executable and library the zip unpacks, thermi's own pinned to its signer. It keeps the previous and the current version and deletes any other folder that no process runs from.

**Commands** reach the service only as user-defined service control codes, integers Windows carries: 128, "this session is quiet, switch now if a version is ready", and 129, "an overlay could not switch". Interactive users get query and user-defined control on the service, never its configuration; each code is acted on at most once a minute. The service still never reads its pipe, nor any file a user can write. Its state, `C:\Program Files\thermi\update\state.json`, is written only by it and read by the overlay and the window.

**Threat model.**

| Threat | What stops it |
| --- | --- |
| A tampered manifest or zip, at R2, at Cloudflare's edge or on the wire | The envelope's signature by a key built into the service, then the size and SHA-256 it signs, checked on the file held open. In a release build, Authenticode on every unpacked executable too, so a stolen manifest key alone cannot run code. |
| Replay of an old manifest, or a downgrade to an older, vulnerable release | The sequence never goes back; a version is never taken below or at the installed one. A withdrawal can only send a PC to the previous version it ran itself and kept, never to one it downloads. |
| A man in the middle, DNS spoofing, a hostile proxy | TLS keeps a check private, but trust never rests on it: a man in the middle can only withhold an update or serve bytes the signature refuses. Sizes are capped before reading: 64 KB for a manifest, the signed size for a zip. Withholding shows: after 14 days without a check, the window says since when. |
| A zip that writes outside its folder | Every entry's path is resolved and must stay inside the new folder; links and absolute paths are refused, and the folder is made new, under a random name, by the service. |
| A non-admin user steering the update | Everything lives under `C:\Program Files\thermi`, which only administrators and SYSTEM write and the installer creates, so no user can make a folder or link there first; its owner and access are checked before each use, as for the driver's folder. The worst a user's control code does is switch early to a version that already passed every check, or send the PC back to the version it ran before, until the next release. |
| A broken release | Beta first, then a gradual rollout; the watchdog and the overlays' own handover roll back a version that does not start, by counting what happens, never by a clock that runs while Windows sleeps; `rollback` and `disable` reach every PC within a minute of the edge. |
| Theft of the signing keys | The manifest key signs only in a release environment that waits for the owner's approval; Authenticode keys never leave SignPath's HSM. Either alone cannot run code on a release build. A lost manifest key is replaced by the offline backup key. |
| Code or UI from the network at run time | None: the update is the only download beside the driver's pinned installer, and the window shows no text from the manifest. |

**Privacy.** A check is one anonymous HTTPS GET of the channel's manifest, no query, no cookie, no identifier, `thermi` as the whole User-Agent. Cloudflare sees the PC's IP address, as any download does. Nothing else ever leaves the PC: thermi learns nothing about who updated, and a failure stays in the PC's event log.

**The installer** is a WiX MSI per processor, per machine: the Windows Installer service runs it as SYSTEM, so no .NET of thermi's runs elevated from a user's environment (`docs/adr/0010-driver-and-service-from-the-window.md`), and it is the format winget, Intune and administrators expect. It lays down the same layout an update keeps, the launchers, one version's folder and the services, and removes the whole `C:\Program Files\thermi`, versions the updater added included, on uninstall. An MSI newer than the installed version installs as an update would; an older one installs that version, as an administrator chose, and the updater moves on from it. `scripts/install.ps1` builds the same layout unsigned with updates compiled off, or on for a test against a manifest and key it is given.

## Rejected

- **An MSI for every update**, run by the service with `msiexec`, as this ADR first had it: the install replaces files in use, so every overlay must close, Restart Manager shuts down what it can, and the service must start each user's overlay again with `WTSQueryUserToken`, which needs `SeTcbPrivilege`, one of the powers ADR 0003 took away from it. The update would show as thermi vanishing for seconds, and a rollback is a second install that can fail too.
- **A small launcher of our own** at a fixed path, starting `<version>\thermi.exe`: the tray icons would register from each version's path, and Windows keeps a person's choice to show an icon only while its path holds; a native launcher needs the C++ build tools, and one on .NET Framework adds a second runtime.
- **A junction**, `current`, switched to each version: .NET's host does not resolve it, so a running process would load its later assemblies from the next version.
- **Velopack**: modern deltas and a simple API, but it installs per user into `%LOCALAPPDATA%`, has no service support, and a LocalSystem binary in a folder the user can write is what ADR 0003 forbids.
- **MSIX**: clean updates, but a packaged service needs a restricted capability, App Installer updates per user, and LibreHardwareMonitor's driver access and `uiAccess` inside a package are unproven.
- **A second service only for updates**: whatever writes Program Files as SYSTEM can do anything, so splitting it from the sensors buys little isolation for a second service to keep in step.
- **Only the page over the air**, as Mi Basket does for its web bundle: the page decides nothing, most fixes touch C# too, and a second channel would need its own trust.
- **Release notes in the manifest**: the window would show text from the network, for little; the release page has them.
- **BITS**: it resumes and knows metered networks, but needs its COM interfaces in the service for a download of tens of megabytes that a later check can simply repeat.

## Consequences

- The service's job grows: it downloads, unpacks, swaps two files and restarts itself. Its memory at rest stays in ADR 0011's budget, since the updater runs for seconds every four hours.
- Two versions are kept on disk, about 70 MB each, since each carries its runtime. A .NET security release is a thermi release.
- A breaking change to the pipe takes a new pipe name, served beside the old one for a release, since for a moment a new service serves an old overlay; a test holds the pipe's lines to a golden file, so such a change is never made by accident.
- A change to the settings file's format keeps a copy of the file in the earlier format, so a rollback finds its settings.
- The release depends on R2, SignPath and a GitHub environment holding the manifest key. If any is gone, PCs stay on what they run and people can install the MSI by hand.
- The tray icons keep a person's choices across versions because their executable's path never changes.

## What it replaces in earlier ADRs

- `docs/adr/0001-architecture.md` says the host accepts no commands beyond sending readings. Instead, it also accepts the update's two control codes, integers from the service control manager; its pipe is still write-only.
- `docs/adr/0003-sensor-service.md` rejects a service the overlay sends commands to, and says installing or updating needs admin rights once. Instead, interactive users may send the two codes, and updates after the first install need no admin rights. The service keeps its one privilege.
- `docs/adr/0006-proven-libraries-for-logging-and-win32.md` measured a framework-dependent install with a shared runtime. Instead, thermi is published self-contained, a version per folder.
- `docs/adr/0010-driver-and-service-from-the-window.md` says the MSI of spec 004 replaces `scripts/install.ps1`'s elevated `pwsh`. It does for people; `scripts/install.ps1` stays the developers' way to install the same layout.
