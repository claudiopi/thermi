# Thermi.SensorHost

`thermi-sensors.exe`: the only process that loads LibreHardwareMonitor (`docs/adr/0003-sensor-service.md`), and with `--elevated` the `thermi-elevated` service, which runs the window's two fixes as SYSTEM (`docs/adr/0010-driver-and-service-from-the-window.md`).

- `Program.cs` runs it as the `thermi-sensors` Windows service, as LocalSystem. `--console` runs it in a terminal, as administrator; `--dump <file>` saves one snapshot and exits, and `--dump <file> --seconds <n>` a series (`SeriesRecorder.cs`). `SensorCommands.cs` reads those with System.CommandLine, one Microsoft assembly with no dependencies, before the sensors are opened; arguments that make no sense say why and exit with 2. `SensorHostEnvironment.cs` holds what it reaches outside its code, which tests replace: the sensors, the clock, the pipe's name and the terminal.
- `LhmSensorSource.cs`, the `ISensorSource` outside tests, reads CPU, GPU, memory, motherboard, controller, network, storage and battery sensors, and only the types Core can show. One device that fails is skipped; it never silences the rest. `DeviceUpdates.cs` updates the devices one after another on threads of their own, waiting at most 500 ms for each: one that stalls, as a board whose bus a fan controller holds, holds back none after it, keeps its last values for up to 3 s and then sends them as missing, and once it returns how long it took goes to the event log (`docs/adr/0015-a-stalled-device-holds-back-none.md`). Every 10 minutes it looks for GPUs, controllers and drives again, so one plugged in later shows without a restart. Drives are updated every 5 s and send their last values between, since each of their updates reads SMART and opens every volume. `ReadPace.cs` decides when a kind of hardware is updated and whether its speeds hold: an update past its pace and the overlay's stale limit, as after sleep, leaves the speeds missing, since they would be the gap's average, and the next read updates again; on Windows' resume event the service reads once at once, so the next speeds cover a second.
- `NetworkAdapters.cs` tells each adapter's kind by Windows' own flags (`GetIfTable2`, generated by CsWin32 from `NativeMethods.txt`): the snapshot carries the virtual ones' ids, so Core's Auto skips them without guessing from names, and a filter driver's layer, which repeats its adapter's traffic, is neither read nor sent.
- `ElevatedService.cs` is the `thermi-elevated` service: started by an administrator through `sc.exe` with a fix's verb, it runs `thermi.exe elevated <verb>` beside it with Windows' own folders as its only environment, and stops with its exit code, which the window reads.
- `SensorPipeServer.cs` serves the `thermi-sensors` pipe: read-only for interactive users; the whole snapshot goes to each client once and on any change of its sensors, the values alone between (`docs/adr/0012-sensor-pipe-catalog-once.md`); at most 32 clients and 4 from any one Windows session, a snapshot per second, and a client that stops reading is dropped after 2 s. A pipe someone else created first is never joined: it says so once in the event log, tries again every 5 s, and the window says another program holds the pipe. A read of the sensors runs on a thread of its own, and one that takes past 60 s, or a device's update still running past it, ends the process, so Windows' recovery restarts the service rather than leave it running and silent. It reads the sensors only while a client is connected, and writes each line straight as UTF-8 into a buffer it reuses.

A failure stops the service with an error code, so Windows restarts it, and goes to the Application event log under `thermi-sensors`, a source `scripts/install.ps1` registers with the service and removes with it. It takes no logging library: fewer dependencies in a LocalSystem process is a security property (`docs/adr/0006-proven-libraries-for-logging-and-win32.md`). Its tests are in `tests/Thermi.Windows.Tests`.
