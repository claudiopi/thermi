# Thermi.SensorHost

`thermi-sensors.exe`: the only process that loads LibreHardwareMonitor (`docs/adr/0003-sensor-service.md`), and with `--elevated` the `thermi-elevated` service, which runs the window's two fixes as SYSTEM (`docs/adr/0010-driver-and-service-from-the-window.md`).

- `Program.cs` runs it as the `thermi-sensors` Windows service, as LocalSystem, at above-normal priority, so a PC busy on every core still gets its readings each second. `--console` runs it in a terminal, as administrator; `--dump <file>` saves one snapshot, waiting for every device however slow, and exits, and `--dump <file> --seconds <n>` a series (`SeriesRecorder.cs`), and `--frames <file> --seconds <n>` every present for a while (`Frames/FramedSource.cs`). `SensorCommands.cs` reads those with System.CommandLine, one Microsoft assembly with no dependencies, before the sensors are opened; arguments that make no sense say why and exit with 2. `SensorHostEnvironment.cs` holds what it reaches outside its code, which tests replace: the sensors, the clock, the pipe's name, the terminal, the Application log, which only its `Default` writes to, and the traces of presents of the service and of `--frames`.
- `LhmSensorSource.cs`, the `ISensorSource` outside tests, reads CPU, GPU, memory, motherboard, controller, network, storage and battery sensors, and only the types Core can show. One device that never reads is left out; it never silences the rest. `DeviceUpdates.cs` updates the devices one after another, waiting at most 500 ms for each, on a thread of the service's own (`UpdateThreads.cs`), never the pool's: one that stalls, as a board whose bus a fan controller holds, keeps that thread and holds back none after it, which go to a new one; one that stalls or fails keeps its last values for up to 3 s from when its update came due, a drive's too between its reads, and then sends them as missing, and neither a stop nor a scan for new hardware closes the library under it; once it returns, how long it took and how it failed go to the event log, at most once a minute a device (`docs/adr/0015-a-stalled-device-holds-back-none.md`). Every 10 minutes it looks for GPUs, controllers and drives again, so one plugged in later shows without a restart. Drives are updated every 5 s and send their last values between, since each of their updates reads SMART and opens every volume; the first update of a drive the library made, at the start and at each scan, only samples its counters, so the next read updates the drives again. `ReadingRules.cs` mends what the library reads before it is sent: a drive's activity is missing while its rates are, rather than the counters' since Windows started, and a device's name loses what a memory chip left past its part number. `ReadPace.cs` decides when a kind of hardware is updated and whether its speeds hold: an update past its pace and the overlay's stale limit, as after sleep, leaves the speeds missing, since they would be the gap's average, and the next read updates again; on Windows' resume event the service reads once at once, so the next speeds cover a second.
- `NetworkAdapters.cs` tells each adapter's kind by Windows' own flags (`GetIfTable2`, generated by CsWin32 from `NativeMethods.txt`): the snapshot carries the virtual ones' ids, so Core's Auto skips them without guessing from names, and a filter driver's layer, which repeats its adapter's traffic, is neither read nor sent.
- `Frames` reads the frames games present (`docs/adr/0014-frames-from-etw.md`). `PresentTrace.cs` runs the real-time ETW session `thermi-frames` through CsWin32, with only DXGI's, Direct3D 9's and the graphics kernel's present events enabled and filtered by id, on a thread of its own; a session of that name left by a crash is stopped first. `ProcessTable.cs` gives each present's parent from Windows' list of processes, taken again at most once a second, and tells the compositor, `dwm.exe`, whose presents are left out; names are read for that alone and never kept. `FramedSource.cs` adds Core's frame slots to each read: the trace starts with the first read and stops 5 s after the last, so only while a client listens; one that cannot start sends the slots without values, says so once in the event log, and is tried again every minute.
- `ElevatedService.cs` is the `thermi-elevated` service: started by an administrator through `sc.exe` with a fix's verb, it runs `thermi.exe elevated <verb>` beside it with Windows' own folders as its only environment, and stops with its exit code, which the window reads.
- `SensorPipeServer.cs` serves the `thermi-sensors` pipe: read-only for interactive users; the whole snapshot goes to each client once and on any change of its sensors, the values alone between (`docs/adr/0012-sensor-pipe-catalog-once.md`); at most 32 clients and 4 from any one Windows session, a snapshot per second, and a client that stops reading is dropped after 2 s. A pipe someone else created first is never joined: it says so once in the event log, tries again every 5 s, and the window says another program holds the pipe. A read of the sensors runs on a thread of its own, and one that takes past 60 s, or a device's update still running past it, ends the process, so Windows' recovery restarts the service rather than leave it running and silent. It reads the sensors only while a client is connected, and writes each line straight as UTF-8 into a buffer it reuses.
- `Updates/` keeps thermi up to date (`docs/adr/0008-updates.md`): `Updater.cs` checks the channel a minute after the service starts, every 4 hours and when About opens (code 129, once a minute at most), takes a version only when its signed manifest, its zip's hash and its signed catalog all pass, unpacks it beside the running one (`Unpacker.cs`), and has `Switcher.cs` switch at a quiet moment (code 128) or at About's Restart to update (130) through a watchdog, `thermi-sensors --switch <version>`, which points the services back unless the new version serves; what it stops, points and starts is an `ISwitchTarget` (`SwitchTarget.cs`), the services or the user's host. `InstallFolder.cs` is the layout: a folder per version, the launchers at the top, the state in `update\`.
- `User/` is `thermi-sensors --user`, the sensors as the user when the service is not installed (`docs/adr/0016-admin-on-demand.md`): `UserMode.cs` serves the pipe `thermi-sensors-<user SID>`, owned by the user and open only to them, SYSTEM and administrators, ends 10 s after its last client left or when none came within 30 s, and in a per-user install runs the same `Updater` on a folder only the user, SYSTEM and administrators write, steered by named events of its own, one per update code and one to stop, and refusing to run when any was made before it. `SessionEnd.cs` is its hidden top-level window, which hears a sign-out or a restart and writes the Stopped mark before Windows ends the host. `UserTarget.cs` is what its watchdog, `--switch <version> --user`, stops and starts: the host itself, since no service points at a version. `MachineInstaller.cs` is "install for everyone", asked by the window through its own event: the machine MSI the channel's signed manifest offers for a version no older than this one, downloaded into `update\`, checked for its size and SHA-256, and in a release build for thermi's signature, held open for reading alone while Windows' `msiexec /i <msi> ADDDRIVER=1 /passive` runs without runas, under the updater's lock throughout, so no switch begins meanwhile, and what it came to written to the state the window reads; once it worked, the host ends, so its clients come back to the service; a policy that turns updates off, a channel off or no MSI listed sends the person to the download page instead. `UserSetup.cs` is what `--adopt --user` and `--remove --user` change beyond the per-user folder: no service, event source or driver, the user's own host, which it stops, the user's entry in Installed apps, and the user's start at sign-in, turned on by a first install alone and taken off only while it names this install. `FileLog.cs` is its log, `%LOCALAPPDATA%\thermi\thermi-sensors.log`, since only an administrator registers an event source.
- `Install/` lays a version down as the layout an update keeps: `thermi-sensors --adopt`, which the MSI (`src/Thermi.Installer`) runs as SYSTEM and `scripts/install.ps1` as administrator, copies it beside the others, registers both services through Windows' `sc.exe` and places the launchers; `--remove` takes thermi off.

A failure stops the service with an error code, so Windows restarts it, and goes, with what the updater does, to the Application event log under `thermi-sensors` through the sink Main hands down, `ApplicationLog` in `SensorHostEnvironment.cs`, which registers the source as `--adopt` registers the service and removes it as `--remove` removes the service; the user's host never writes there, only to its own file. It takes no logging library: fewer dependencies in a LocalSystem process is a security property (`docs/adr/0006-proven-libraries-for-logging-and-win32.md`). Its tests are in `tests/Thermi.Windows.Tests`.
