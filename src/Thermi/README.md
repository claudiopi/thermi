# Thermi

`thermi.exe`, the overlay and, as `thermi settings`, the settings window in a process of its own; and `thermi-cli.exe`, the same program as a console door for AI agents and other programs. All run as the user, without admin rights.

Each topic is a folder, and its namespace: `Overlay` (the host, its windows and mouse, the settings, the settings file, the hotkeys and the sensor client), `Painting`, `SettingsFile` (watching the settings file and what waits to be written to it), `Gestures` (the overlay's drags on the desktop and what its hotkeys do), `Tray`, `Windows` (the monitors, hidden windows and staying on top), `Logging`, `Commands` (the command line, the preview and the CPU load) and `Agents` (`thermi-cli`); the settings window is `Ui`, with its editor in `Ui/Editor`, what the page reads in `Ui/Views` and the window that hosts the page in `Ui/Web`.

- `Agents` is `thermi-cli.exe`, the same `thermi.dll` behind a second apphost with the console subsystem that `Thermi.csproj` writes, so a shell waits for it (`docs/agents/README.md`, `docs/adr/0013-agents-cli-and-mcp.md`). `Program.cs` tells the door by its process path; `Commands/AgentCommandLine.cs` parses its commands, `Agents/AgentRun.cs` runs one with the standard streams, its log in `thermi-agents.log`, and `Agents/AgentCommands.cs`, `AgentChanges.cs` and `AgentFinder.cs` answer it from Core's `Agents` folder: each read connects to the pipe through `SystemFeed` and hangs up once it has its samples (`AgentSamples.cs`), each edit is replayed on the file as found under its mutex, and the start at sign-in is `Ui/StartWithWindows.cs`. `Agents/McpTools.cs` serves the same calls as MCP tools on stdio with the SDK's `ModelContextProtocol.Core`, with an `UndoHistory` for the session. Nothing there elevates, starts a service or installs (`RepoRulesTests`).
- `Program.cs` starts it: the single-instance mutex, above-normal priority, as the sensor service's, so the overlay keeps painting while every core is busy, the log, the overlay's registration with Windows Error Reporting, which starts a crashed or hung overlay again as it ran but never after an update (`Windows/CrashRestart.cs`, docs/adr/0017-windows-restarts-the-overlay.md), the sensor client, the settings and the host. A second `thermi` asks the first to show and exits. What escapes the overlay or the window is logged before it ends the process (`ThermiLog.RunLoggedAsync`), a failure on a thread of its own, as a timer's, through `AppDomain.UnhandledException`, each once. `Commands/ThermiCommands.cs` reads the command line with System.CommandLine before anything else, the overlay's mutex included, and arguments that make no sense say why on stderr and exit with 2; `Commands/CommandLineOutput.cs` attaches the terminal's console when stderr leads nowhere, since a windowed program has none. `thermi settings [--overlay <n>]` opens the window instead, and `--pseudo` stretches the window's texts; `thermi preview <snapshot> <png> [scale] [settings]` (`Commands/Preview.cs`) paints the first overlay of the user's settings or of the file given, at a scale from 0.25 to 8, from a snapshot that must exist, and never creates a missing settings file; a snapshot it cannot read says why on stderr and exits with 2, a picture it cannot write, with 1; `thermi cpu-load <seconds>` loads every core with `Commands/CpuLoad.cs`, the fan finder's load, to record how the fans answer. `thermi elevated start-sensors|install-driver` (`Commands/Elevated.cs`), started behind one UAC prompt by the window or thermi's menu, takes its verb and nothing else: `Commands/StartSensors.cs` starts `thermi-sensors`, and `Commands/InstallDriver.cs` downloads the driver's pinned installer (`Commands/HttpDownload.cs`) into a new admin-only folder of `Commands/DriverFolder.cs`'s, checks its size, SHA-256 and signature, runs it unattended with none of the user's environment (`Commands/WindowsInstaller.cs`) and starts the sensors again (docs/adr/0010-driver-and-service-from-the-window.md). `Program.Start` starts `thermi.exe` again, passing `--trace` on, for the overlay opening the window and the window starting the overlay.
- `Overlay/SensorClient.cs` reads snapshots from the `thermi-sensors` pipe, after checking that SYSTEM or Administrators own it, for the overlay and, as an `ISensorFeed` that tests replace, for the window. While it is gone, each try waits up to 2 s to connect, then 2 s more before the next. Its `State` tells the service stopped (no pipe) from its data gone stale (a pipe but no fresh snapshot), which the tray icons say. Tests give it a pipe of their own, and trust the owner of the one they made.
- `Windows/SystemFeed.cs` wraps that feed for both processes and adds what Windows itself says to each snapshot, as the sensors of `/system/0`: the uptime, the default route's local address, found again only when the network changes, and the time, and the frames of the app in front as the game's sensors, which `Windows/FrontApp.cs` finds: the foreground window's process, or under a window of thermi's the first shown window below it, and none for the desktop, the taskbar or File Explorer, which starts nearly every app. `Windows/CpuWatch.cs` reads the CPU's base clock once, and what is busiest on the CPU and the GPU from Windows' performance counters only while a value of theirs is critical. `Windows/Clipboard/ClipboardImage.cs` puts an overlay's picture on the clipboard for "Copy as image", through `HostEnvironment`, which tests replace. `Overlay/OverlayFade.cs` fades an overlay as the pointer nears, on a timer that runs only while its switch is on.
- `Overlay/OverlayHost.cs` is the process's one hidden top-level window, of class `thermi-host`: it runs the message loop, receives "show" (`thermi-show`, from a second thermi or the window), "hotkey status" (`thermi-hotkey-status`, from the window), the hotkeys and `TaskbarCreated`, and keeps one overlay window per overlay of the settings, up to four, sharing the sensor client, the settings and one paint throttle. Every paint, the once-a-second one included, goes through it, at most one every 100 ms; it shows each overlay as Core's `OverlayVisibility` says, from where thermi shows, the hide hotkey, whether the window's mutex exists (looked at on the tick and on "show", never held) and whether the window in front covers that overlay's monitor, and hides the others. A fresh snapshot is added to each overlay's history as it comes. `Windows/HiddenWindow.cs` makes it and the window's beacon: the window class, the hidden window, and the find by class and `SendMessageTimeout` of 500 ms another process asks it with. `Overlay/HostEnvironment.cs` holds what it reaches outside the process, which tests replace: the window's mutex, the executable's path, the notification area, the cursor a press on an overlay follows, and opening the window, which starts `thermi settings --overlay <n>` after letting any process take the front, as the click that asked allows.
- `Overlay/HotkeyRegistry.cs` registers the four hotkeys on the host window, again whenever the settings change, the overlay's own writes included, and answers "hotkey status" with Core's `Hotkeys.Status`: the hash of what it tried and which failed. On the window's `thermi-rest-hotkeys` it lets them go while a hotkey's row records, and it says whether another program holds a combination by asking Windows for it. The hide hotkey toggles `OverlayVisibility`'s flag; the next-style one writes the next saved style of the `styles` folder beside the settings file, and the click-through one turns it on or off for every overlay, both through `Settings.Edit`; reset min and max starts each overlay's history again (`Gestures/HotkeyPresses.cs`).
- `Tray/TrayIcons.cs` keeps the tray icons Core's `TrayScene` says, with `Shell_NotifyIcon` on the host window: each under its id, a leftover with that id deleted first, an icon Windows refuses tried again every 5 s and logged once, all added again on `TaskbarCreated`, those that left removed when the icon size changes, each with a callback message of its own. An icon is drawn again only when `TrayRefresh` says it changed or the icon size changed (`SM_CXSMICON` at the primary monitor's DPI), and its old handle destroyed. Right-click opens its overlay's menu, or one submenu per overlay, and double-click the settings on its overlay. Only thermi's own icon's menu has click-through, and that icon shows the Windows notice (`NIF_INFO`) the host asks for as an overlay's click-through turns on, whose click turns it off again. `Tray/TrayPainter.cs` draws them: an item's characters in Bahnschrift SemiBold Condensed, as large as the icon allows, or thermi's own pill with a full meter.
- `Overlay/OverlayWindow.cs` is one overlay's layered Win32 window: painting, hiding, click-through (`WS_EX_TRANSPARENT`, so every click passes), dragging, its menu, opened on the pill under the pointer (Core's `Menus.OfOverlay`, drawn by `Tray/ThermiMenus.cs` with each entry's access key, and chosen in `Tray/TrayChoices.cs`, where each edit is one undo step, as a gesture), which the tray's menus reuse, thermi's own icon's adding click-through, DPI, every item while the window is open, drawn at the monitor's scale times the overlay's size, and moved for OLED care by how long it has run, never written. `Overlay/OverlayMouse.cs` says what each mouse message does: the overlay moves itself under the mouse, only once the cursor passes the system's drag distance and never when locked, so a click or a double-click keeps the snap, and a double-click opens the window on that overlay. Its texts come from Core's translations, in the settings' language or Windows' display language, and its numbers in Windows' regional format. It moves to the place `Snaps` in Core works out at every paint, kept clear of the other overlays on its taskbar and painted no wider than the room they leave it, as Core's `TaskbarRow` says, from what `Windows/Desktop.cs` reads: the monitors, each known by Core's `MonitorIds` from the EDID Windows keeps for it (read once per monitor plugged, through its device interface), their taskbars and notification areas, the taskbar's light or dark mode, which a setting change repaints at once, and the window in front. `Windows/Topmost.cs` keeps it above the taskbar (`docs/adr/0004-above-the-taskbar.md`).
- `Painting/Painter.cs` draws what Core's `OverlayLook` says with GDI+, and nothing it does not: the pills side by side or stacked, the text with its shadow or outline, each item's Graph, five segments of bars or a line of its last minute, of what it warns by, the level marks (a warning's underline where no graph shows it, a critical value reversed on its color), the critical glow Core's `CriticalGlow` times and the "Sensors stopped" pill with thermi's mark (`Painting/PainterShapes.cs`), the fonts, made once per style and size (`Painting/PainterFonts.cs`), and the opacities (`Painting/Alpha.cs`): the pills fade before the text is drawn on them, then the whole overlay, and every painted pixel keeps an alpha of at least 1/255, so a pill catches clicks at any opacity. The same code serves the screen, `thermi preview`, "Copy as image" and the window's preview, lays each pill out as a `Painting/PaintedPill.cs`, a single bar's inner pills included, and keeps where it drew each item, its pill, its label and its value (`Painting/PaintedItem.cs`) for the overlay's tooltips, presses and snap marks, which `Painting/PaintedPlaces.cs` reads: the item and the label or value a press is on, and where a drop joins. `Windows/Desktop.cs` reads high contrast and its colors at every paint.
- `Overlay/ValueTips.cs` is Windows' own tooltip control over each painted item, with Core's `ValueTooltips` text. `Gestures/OverlayGestures.cs` and `Gestures/DesktopDrag.cs` are the desktop gestures Core's `DesktopGestures` decides: a pill held until it lifts, or an item alone held on its value, woken by a Win32 timer and timed by the injected clock, then dragged off or, an item, within its own pill, the whole overlay moved along a taskbar, onto the snap marks `Gestures/SnapMarks.cs` shows or into another overlay, and a floating overlay's corner, with `Gestures/DropPreview.cs` telling the overlay a drop would join, which `Painting/DragMarks.cs` marks, between the items of its pill for an item carried over it, as it does the gap a lifted pill or item leaves; `Gestures/GestureUndo.cs` keeps the last one undoable for 30 s and tells the open window.
- `Overlay/ConfigStore.cs` reads and writes `%APPDATA%\thermi\config.json` for every process: a writer holds the file's named mutex from its re-read to its move into place, taken over from a writer that died, and applies its change to what it found, never over a broken file. A file found locked, empty, cut short or missing is tried again for 500 ms, so an editor's save never shows as the defaults, and a read never blocks a write. It knows the text it last wrote or read, so its own write never comes back as an outside change, and the same text put back after another change is one.
- `Overlay/Settings.cs` is each process's copy, the overlay's and the window's: it reads and writes through the throttle, off the window's thread once it must wait, retries a write until it lands, and writes a press only when it was a drag: a click writes nothing. `SettingsFile/SettingsWatcher.cs` watches the file for both, and `SettingsFile/PendingWrites.cs` keeps the drags and the overlay's own edits until they are written. A write Windows refuses, as on a read-only file, is logged once and, after three quick tries, tried once a second. A file it cannot use is read again every second, in either process, since a lock let go without a write raises no change of the file. What it shows is always the last settings read well, then the drags and edits that wait, so a broken file read again never applies an edit twice. Why a file cannot be used is a `ConfigProblem`, and `Restore` keeps the broken file beside it and writes the last settings read well, one copy however often it is tried, or leaves a file that reads well again by then, fixed by hand or unlocked.
- `Logging/ThermiLog.cs` makes the logs of the overlay, the window and the agents' commands, `thermi.log`, `thermi-window.log` and `thermi-agents.log` in `%LOCALAPPDATA%\thermi`, with Serilog's file sink: a file each, the agents' shared by their short processes, rolled at 1 MB with three files kept, stamped from the injected clock and the performance counter every process shares. Information and up always, as what went wrong and each change an agent made; with `--trace`, read before anything else, each paint, each "open settings", the window's inputs and its first frame too, so the time from the window's input to the overlay's paint can be read off. `Logging/UserFolders.cs` takes `%APPDATA%` and `%LOCALAPPDATA%` from the environment first, so a test's or a trial's thermi has a profile of its own. Every class takes its `ILogger`, and `Logging/LogEvents.cs` holds every event as a `[LoggerMessage]`; the elevated mode's go to the Application event log (`Logging/EventLogger.cs`).
- `NativeMethods.txt` lists every Windows call, which CsWin32 generates at build time into `Windows.Win32.PInvoke` with its typed handles; the files in `Windows` keep only thermi's policy over them. `Windows/Desktop.cs` reads the monitors, their taskbars, high contrast, the window in front and its monitor, and what Windows says the user is doing (`SHQueryUserNotificationState`), for the full-screen rule.

The settings window lives in `Ui`: a plain Win32 window that hosts the page of `src/Thermi.Settings.Web` in WebView2. Neither process loads WPF:

- `Ui/WindowProcess.cs` is `thermi settings`: it reads the settings through `Settings`, watches the file, and runs the window on an STA thread of its own while it holds the window's mutex, reading the sensors from the pipe only while the window is open, `Local\thermi-window`, taken with `WaitOne(0)`, an abandoned one counting as taken. If another window holds it, it asks that one to come to the front, for up to 2 s while a window just started has no hidden window yet, and exits. What fails on the window's thread is thrown again on the caller's, so the process's entry logs it. `WindowEnvironment` holds what the window reaches outside its process, which tests replace: the mutex, the settings file, the executable, the trace, the log, when it was asked for, and the start-up entry "Start with Windows" switches. `WindowStart.Load` is the fan finder's load, which tests replace so they never load the CPU.
- `Ui/Web` is the window as it runs, with no WPF in its process (`docs/adr/0007-settings-window-in-webview2-and-react.md`): `WindowSession.cs` puts together the editor, the bridge, the page, the window, the beacon and the link to the overlay on the window's thread, whose `WindowTurn.cs` runs every await, tick and snapshot through the window's own messages. `WebWindow.cs` is a plain Win32 window in Windows' frame (`WindowFrame.cs`: the caption taken off so the page draws the title row, Mica through the page's transparent background, or where Windows refuses Mica, as Windows 10 does, the page marked to paint Windows' opaque window background, the caption buttons drawn and answered by Windows through a hole cut in the page, topmost while active), shown once the page has loaded, with the first frame logged; `WindowPlace.cs` opens it at Core's `WindowRoom` place, scaled to the monitor and off the free overlays, or where it was, kept per setup of monitors in `window.json` beside the log. `WebPage.cs` hosts WebView2, its profile beside the log too: the page's files, embedded from `src/Thermi.Settings.Web/dist` by `SettingsPage.targets`, served from `https://thermi.invalid` under a strict Content Security Policy, no navigation away, no browser keys, menus or zoom, the developer tools only with `--trace`, and `window.thermi` set before the page runs, which answers through Core's `BridgeCalls`. `WindowBridge.cs` is the C# side of the bridge, `PageEdits.cs` turns each of the page's edits into Core's, `WindowLinks.cs` opens the settings file and About's links through Explorer by its full path, never a program found on the PATH, and `OverlayLink.cs` is the window's side of the messages with the overlay (`docs/adr/0009-overlay-and-window-messages.md`, `Overlay/WindowLink.cs` the overlay's): the overlay's item history, taken into the window's own as it opens and after a reset, the desktop's picks, each gesture as a step of the window's history, and "edited" through the throttle. Closing the window closes WebView2, so no process of it stays.
- `Ui/Views` is what the bridge reads and does beyond plain edits, each from Core: `ReadSensors.cs` the pipe's snapshot once the window has read it, so one Core throws on leaves the window on the last it read, logged once until one reads, instead of ending it; `WindowFixes.cs` installs the driver and starts the service through the elevated mode; `WindowViews.cs` the overlays' pills, values and levels, the catalog and thermi's mark as the tray decides it; `WindowCharts.cs` each item's chart of what it warns by, from the window's item history, and the edits of its lines; `WindowPreviews.cs` each overlay's preview and each look's tile, painted by the overlay's own painter as "Copy as image" is; `OverlayPlaces.cs` where each overlay shows, as its own window places it beside the others on its taskbar, and the pushes an edit stores or the move it refuses; `WindowLooks.cs` the saved looks and the look files, imported or exported through Windows' own dialogs; `WindowFinder.cs` "Find it", Core's `FanFinder` with `Commands/CpuLoad.cs` as its load, a thread per logical core in a `thermi cpu-load` process of its own at idle priority, so the window's runtime never stalls the readings, ended by the finder, a cancel or 30 s at most.
- `Ui/SettingsBeacon.cs` is the window process's hidden top-level window, class `thermi-settings`: a second request finds it with `FindWindow`, lets its process take the front and sends it `thermi-raise`, with the overlay asked for in `wParam`, 0 to keep the one it shows; one above the count opens the first.
- `Ui/Editor/WindowEditor.cs` is the window's side of the settings, which changes nothing while the file cannot be used and restores the last good settings: every edit goes through Core's gate and is written through `Settings` as `ConfigEdits.Replay` of what it changed, applied to what the file holds then, so another process's change meanwhile stays; undo and redo are Core's `UndoHistory`, a gesture is one step, and a change from outside shows at once, or at the end of the gesture under way.
- `Ui/Readings.cs` keeps what the window read since it opened: the catalog of each fresh snapshot, built once, what each overlay reads of it, and ten minutes of every sensor and every metric of the overlay shown in Core's `SensorHistory`, for the catalog's sparklines and so a sensor an item is given later, or warns by, charts its seconds from the window's opening. Each item's own seconds are the item history's, which takes the overlay's.
- `Ui/StartWithWindows.cs` reads and writes "Start with Windows" as the `thermi` value of the user's Run key, the one `scripts/install.ps1` writes, never in the settings, so undo never touches it, and off while Task Manager's Startup tab turned it off, which turning it on clears.

The overlay's and the window's tests that need Windows live in `tests/Thermi.Windows.Tests`, the window's under `Window`; the page's own are Playwright's, in `src/Thermi.Settings.Web/tests`. A repo rule keeps WPF out of every project.
